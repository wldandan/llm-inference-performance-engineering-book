# 写作规则

> 适用范围：`content/` 下的全部正文（`chNN.md`、`partNN.md`）。
> 这些规则约束**怎么写**；章节必须包含哪些交付物见 `book-editorial-blueprint-v1.0.md` 的 4.1 每章通用 DoD。
> 规则在写作过程中持续追加，每条都要写清原因和判断方法，避免变成无法执行的口号。

## 1. 从读者视角写，不从作者视角写

正文描述的应当是**读者此刻的处境和困难**，不是**这段内容在书里承担什么功能**。

小节标题最容易出问题：功能式标题描述这一节做了什么，读者要读进去才知道与自己何干；处境式标题直接点破读者正卡在哪里。

| | 作者视角 | 读者视角 |
|---|---|---|
| 例 | 让等待过程变得可见 | 同步调用只给了你一个数字 |
| 差别 | 说明流式的作用 | 说明读者手里的东西不够用 |

**判断方法**：把标题或段落开头念一遍，问"这句话是在说读者遇到了什么，还是在说这本书安排了什么"。后者就要改。

全书最有力的一类标题是"点破误解"式断言，例如 `Decode 是一串引擎步，不是一段黑盒时间`——它同时给出读者可能持有的错误认识和正确认识。

## 2. 引入新内容要问题驱动

要引入一段新内容、一项新技术或一条新的解决思路时，先把**没有它会卡在哪里**讲透，再引出它。不要先介绍技术、再补充说它有什么好处。

推荐结构：

```text
读者刚做完的一件事
  → 一个他答不上来的问题
  → 追问一层，说明为什么答不上来（找到根源）
  → 引出新内容：它改变的正是这个根源
```

以 Ch1 的 1.7 为例：读者刚跑完同步调用 → 问"刚才那几秒服务在做什么" → 追问"如果慢了一倍你从哪里查起" → 定位根源"观测点只有一个" → 引出流式"把一个观测点变成多个"。

**判断方法**：删掉技术名词之后，这段引入是否仍然成立？如果删掉"流式"二字，前面的问题依然让读者不安，说明问题立住了；如果整段变得没有意义，说明是在给技术找理由。

### 2.1 驱动问题要满足金字塔原则

用来驱动的那组问题，要**列举完整、维度不重复**：

- **完整**：把读者在这个位置可能产生的疑问覆盖住，不留明显缺口。读者想到一个书里没提的问题，信任就打折。
- **不重复**：每个问题占据一个独立维度。两个问题如果换个说法在问同一件事，就合并成一个。

这条同样适用于每章开头的三个问题（见 3.1）。写完后逐条比对：它们是不是在问同一件事的不同侧面？合起来有没有盖住本章要解决的全部问题？

## 3. 章首提出三个问题，章尾逐条回答

### 3.1 章首只留一节

「学习目标」和「核心问题」不要同时出现在章首。即使措辞刻意分开，读者拿到的仍是同一批内容的两种句式；连着读六条只会分散注意力，还没开始动手就先穿过两层承诺。

保留「学习目标」这个标题，内容写成三个问题：

```markdown
## 学习目标

读完这一章，你应该能回答三个问题：

1. 怎样确认服务真的完成了一次生成？调用失败时又怎样判断卡在哪一层？
2. 完成第一次调用，最少需要哪些请求参数和验收证据？
3. 同步调用看不到什么？流式能补上其中哪些，又补不上哪些？

跟着做完，你会得到一个能接受请求的 vLLM 服务，以及同步和流式两份客户端运行记录。
```

- **标题用「学习目标」**，与 `03_Course_Template.md` 的约定一致，读者也熟悉这个位置。
- **引导句是关键**。目标本身是陈述句（能回答），底下列的是要回答的内容（问句），名实相符。而且“能回答一个真问题”比“能够解释某概念”更可检验。
- **末尾补一句本章产出物**。这是问题给不了的信息，读者需要知道跟着做完手上会多出什么。

### 3.2 三个问题就够，压不下去时先找重复维度

控制在三条。列到五六条时读者抓不住重点，每条的分量也被稀释成并列的小点。

**压不到三条，通常不是内容太多，而是几条在讲同一个维度的不同实例。** Ch1 原有六条，其实只有三个维度：

| 原条目 | 维度 |
|---|---|
| “服务已启动”的三种含义 / HTTP 200 不足以说明成功 / 一次调用能支撑哪些结论 | 证据分层 |
| 流式改变了“快”的指向 | 度量结构 |
| 分片数 ≠ token 数 / 客户端与服务端之间隔着什么 | 客户端 ≠ 服务端 |

Ch1 的"怎样确认服务完成了生成"和"失败时怎样定位层级"也是同一个三层模型的正反两面，合成一条即可。

每条只写一句，不展开细节——细节留给正文和本章总结。章首是索引，不是摘要；每条后面再挂一句解释，三条就又变回三段。

这条和 2.1 的金字塔原则是同一件事：压缩过程本身就在检验这些问题是不是真的互相独立。

### 3.3 本章总结逐条回答这三个问题

问题在章首提出，就要在章尾兑现：

```markdown
## 本章总结

回到开头的三个问题。

**怎样确认服务真的完成了一次生成，失败时又怎样定位？** 靠三层证据……

**最少需要哪些请求参数和验收证据？** 请求只有 model 和 messages 是必需的……

**同步看不到什么，流式又补上了什么？** 同步调用只留下一个总时长……
```

读者读完能自己对答案，不必翻回开头猜哪句对应哪个问题。

**判断方法**：某个问题在总结里找不到对应的回答段落，说明要么正文没真的解决它，要么它本来就不该列在章首。反过来也要查——**正文里最花篇幅的那一节，在三个问题里有没有位置**。一章最有价值的内容常常是写作后期才成型的，容易从没被写进章首。

### 3.4 章尾两节的分工

| | 是什么 | 形式 |
|---|---|---|
| 本章总结 | 回答章首的三个问题 | 逐条作答，给出理解 |
| 本章 Checklist | 拿到手上能做出什么 | “能画出/能算出/能运行…”，可逐项打勾 |

总结偏**理解**，Checklist 偏**可操作验证**。同一件事若两处都要出现：总结写“缺失的阶段就写 unavailable，它和 0 ms 是两回事”，Checklist 写“拿到一份报告，能列出哪些阶段必须写 unavailable”。

**症状**：Checklist 每条都在复述总结里的道理、没有一条能真的打勾，说明它写成了第二份总结。


## 4. 首次出现的术语要给出注释

术语第一次出现时，如果周围的句子没有把它说清楚，就在**该段之后**补一条引用块注释：

```markdown
> **NTP**（Network Time Protocol）：网络时间协议，让多台机器的系统时钟保持一致。
> 它能把偏差压到毫秒级，但不消除偏差，所以跨机时间戳相减始终只是近似值。
```

格式要求：

- 用 `>` 引用块，不用脚注——脚注依赖渲染器扩展，引用块在任何环境下都能正确显示
- 首行 `> **术语**（英文全称）：一句话定义`
- 需要的话再补一行说明**它为什么出现在这里**，这比字典式定义有用得多
- 放在含首次出现的那一段之后，不打断句子

### 4.1 哪些术语需要，哪些不需要

**需要**：读者可能不认识，而正文又直接拿它当已知概念用的。典型是相邻领域的术语——`NTP`、`RoPE`、`SwiGLU`、`Prefix Cache`、`Chunked Prefill`、`SSE`。

**不需要**：

- 本章正文要专门展开的概念——它有整节篇幅，不需要注释再讲一遍（例如 Ch3 的 Prefill、KV Cache）
- 上下文已经解释清楚的（例如"以 `data: [DONE]` 结束，这一行不是 JSON"）
- 目标读者的基础词汇——HTTP、JSON、GPU

**判断方法**：把这个词从句子里遮住，问"读者不知道它是什么，还能不能读懂这句话在说什么"。不能，且本章又不打算展开它，就补注释。

注释是为了让读者不必中断阅读去查，不是为了显得严谨。一段里出现两条以上注释，通常说明这段引入了太多新概念，应该先拆段落。

## 5. 正文不写编辑决策

不要在正文里向读者解释这本书为什么这样组织。删减小节后不写"这里只保留两条表格装不下的内容"，调整归属后不写"所以这组数字从第 2 章取而不是第 1 章"。

**原因**：正文是给学员看的，不是给编辑看的。这类句子暴露写作过程，读者既不需要也不关心，还会让章节显得在为自己的结构辩解。

**判断方法**：这句话删掉之后，读者还能不能正确理解和使用这段内容？能，就删。取舍理由写进 `strategy/reviews/chNN/review.md`。

例外：面向读者的**内容指引**不属于编辑决策，应当保留，例如"长上下文与 Prefill 优化放在第 12～14 章"。区别在于前者解释编排动机，后者告诉读者去哪里找。

## 6. 正文不出现分层标签

正文里不写 `Core Track`、`Advanced Track`、`Core Checklist`、`Advanced 延伸`、`Core Demo`。

**原因**：分层是课程设计的组织方式，属于作者视角。读者不需要知道自己在读哪一层，只需要知道内容本身和边界。

**改法**：保留内容实质，只换表述。

| 原表述 | 改为 |
|---|---|
| Advanced Track 可以继续研究 X | X 本章不展开 |
| Core Demo | Demo |
| Core Checklist | 本章 Checklist |
| Advanced 延伸 | 延伸方向 |

**注意区分**：指向 Advanced **附录**或具体章节位置的交叉引用是正常的内容指引，例如"多 GPU 与 NCCL 附录"，保留。

分层本身在 `strategy/course-design/03_Course_Template.md` 里仍然有效，只是不进正文。
