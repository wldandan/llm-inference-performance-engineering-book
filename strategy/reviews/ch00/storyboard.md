## 图0-1 朴素的四步生成循环

### 对应正文

0.2 模型是一摞参数，回答是一个循环

### 核心问题

一段回答是怎样一个 token 一个 token 写出来的，朴素做法浪费在哪里？

### 核心观点

- 四张卡片带回流箭头：切成 token、穿过权重、词表概率、选一个 token。
- 第 ② 步明确写出“输入 + 已写出的全部 token”，右上角标“朴素模型”。
- 下方逐圈列出第 ② 步送进模型的内容，用橙色框标出和上一圈相比没变、却又处理了一遍的部分。

### 不应出现的内容

- Tokenizer、Embedding、LM Head 等七步管线（属于图 3-1 的粒度）。
- KV Cache、Prefill、Decode、Attention、张量形状。
- 真实系统的缓存做法（正文在 0.3 交代）。

### 阅读路径

先读上方四张卡片和回流虚线，再读下方逐圈列表。

### Wireframe

~~~text
[① 切成 token] → [② 穿过权重] → [③ 词表概率] → [④ 选一个 token]
        ↑_______________ 回到 ②，直到写完 _______________|
                                                   (朴素模型)
第 1 圈    输入 | 写出 t1
第 2 圈    输入 | t1 | 写出 t2
第 3 圈    输入 | t1 t2 | 写出 t3
第 500 圈  输入 | t1 t2 … t499 | 写出 t500
           └── 橙色框：没变，却又处理了一遍
~~~

### 图中文字

- 朴素的四步生成循环：每转一圈，只多一个 token
- 朴素模型
- ① 切成 token / ② 穿过权重 / ③ 词表概率 / ④ 选一个 token
- 输入 + 已写出的全部 token
- 稠密模型：全部权重参与
- 回到 ②，直到写完：转多少圈，就写出多少个 token
- 第 1 圈 / 第 2 圈 / 第 3 圈 / 第 500 圈

### 关键结论

一段回答要转很多圈；朴素做法每一圈都在重复处理没变过的历史。

## 图0-2 读题搬一次，答题搬 N 次

### 对应正文

0.3 读题可以一起读，答题只能一个一个写

### 核心问题

同一份权重，读 1000 个 token 和写 1000 个 token，搬运次数和每次的计算量有什么不同？

### 核心观点

- 左右两栏共用同一块“权重 · 约 1 GB”。
- 左栏读题：一条搬运箭头，一个很宽的计算块，标“累在算”。
- 右栏答题：1000 条搬运箭头，每条后面一个很窄的计算块，标“累在搬”；按“历史不再重算”的真实做法画。
- 橙色标签给出纸面推算：Qwen2.5-0.5B 单个请求 0.98 GB × 1000 ≈ 980 GB。

### 不应出现的内容

- 带宽、算力、TB/s 等硬件规格数字。
- 时间线（首 token 边界与生成步属于图 2-5、图 2-6）。

### 阅读路径

先比较两栏从权重引出的箭头数量，再比较计算块宽度，最后看底部“累在算 / 累在搬”。

### Wireframe

~~~text
读题 · 1000 个 token 一起读          答题 · 1000 个 token 一个一个写
[权重 约 1 GB]                        [权重 约 1 GB]
      │ 搬 1 次                         │1 │2 │3 … │1000
[████████ 一次算 1000 个]             [▌][▌][▌] … [▌]
累在算                                 累在搬
                                       0.98 GB × 1000 ≈ 980 GB
~~~

### 图中文字

- 读题 · 1000 个 token 一起读 / 输入全部已知，可以并行处理
- 答题 · 1000 个 token 一个一个写 / 后一个依赖前一个，只能串行
- 权重 · 约 1 GB
- 搬运 1 次 · 每次计算量大 · 累在算
- 搬运 1000 次 · 每次计算量小 · 累在搬
- 每写 1 个 token：整份权重搬 1 遍，只算新的这 1 个（历史不再重算）
- Qwen2.5-0.5B 单个请求：0.98 GB × 1000 ≈ 980 GB

### 关键结论

读题累在算，答题累在搬：同样一个 token，写出来占用的机器时间远多于读进去。

## 图0-3 批量摊薄搬运，满载拉长等待

### 对应正文

0.4 一张卡同时服务很多人：批量摊薄搬运，满载拉长等待

### 核心问题

为什么想省就要把卡跑满，想让每个人少等就要留出余量？

### 核心观点

- 两个小图并排，都是示意曲线，不标刻度和数值。
- 左图横轴“同时服务的人数”：总产出近乎线性上升，每人出字速度在边界内几乎持平、越过边界后下降，边界处标“显存装不下 / 计算追上来”。
- 右图横轴“到来的请求量（越往右越接近处理上限）”，纵轴“排队等待”，曲线在右端陡升。

### 不应出现的内容

- GPU 利用率百分比刻度、倍数、P99。
- Continuous Batching 等调度术语（属于第 20 章）。

### 阅读路径

先看左图得出“批量划算”，再看右图得出“满载危险”，两图合起来就是 0.4 的冲突。

### Wireframe

~~~text
批量：同一次搬运，同时给很多人写        排队：越接近满载，等待涨得越快
产出 │      ／ 总产出                   等待 │                 ╱
     │ ───────╲ 每人出字速度                 │              ╱
     │        ┆边界                          │ ______.──
     └──────────────→ 同时服务的人数         └──────────────→ 到来的请求量
~~~

### 图中文字

- 批量：同一次搬运，同时给很多人写
- 同时服务的人数 / 总产出 / 每人出字速度
- 边界：显存装不下 / 计算追上来
- 边界内几乎白捡 / 越过边界开始变慢
- 排队：越接近满载，等待涨得越快
- 到来的请求量（越往右越接近处理上限）/ 排队等待
- 空闲时多来一些，几乎无感 / 多一点请求，等待成倍增长

### 关键结论

想省就要跑满，想快就要留余量；愿意等的请求，可以放进跑满的卡池。
