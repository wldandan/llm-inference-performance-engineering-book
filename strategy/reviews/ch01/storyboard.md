## 图1-1 第一个 LLM 服务的最小运行链路

### 对应正文

1.1 准备运行环境

### 核心问题

一次 LLM 调用要经过哪几段，本章的实验边界画在哪里？

### 核心观点

- 只画四个环节：客户端、vLLM API、模型、GPU。
- 客户端与服务端在同一台主机上，通过 `127.0.0.1:8000` 连接。
- 环境信息（Python / vLLM / Driver / GPU / Model）作为这条链路的前提标注在旁。

### 不应出现的内容

- Gateway、Router、Scheduler、Worker 等组件划分（属于第 4 章）。
- Queue、Prefill、Decode 等内部阶段（属于第 2、3 章）。
- 任何延迟、吞吐或利用率数字。

### 阅读路径

从左到右单向阅读，四个环节一条直线。

### Wireframe

~~~text
[客户端] --HTTP--> [vLLM API] --> [模型] --> [GPU]
   同一台主机 · 127.0.0.1:8000

环境前提：Python / vLLM / Driver / GPU / Model
~~~

### 图中文字

- 客户端
- vLLM API
- 模型
- GPU
- 127.0.0.1:8000
- 同一台主机
- 环境前提
- Python / vLLM / Driver / GPU / Model

### 关键结论

先跑通本机最短链路，再考虑跨机访问和内部结构。

## 图1-2 三层就绪证据

### 对应正文

1.3 如何确认服务已经就绪

### 核心问题

“服务已启动”至少有三种含义，它们分别证明什么、不证明什么？

### 核心观点

- 三层自下而上：进程、模型列表、真实生成。
- 每层标注“能证明什么”和“仍不能证明什么”。
- 上一层通过不代表下一层通过；三层都通过才算最小闭环。
- 第三层就是 1.4 的第一次请求，图中用箭头指向“下一节动手”。

### 不应出现的内容

- 服务端内部阶段或组件。
- 失败排查步骤（1.9 用表格表达，不重复画图）。
- 性能是否达标的判断。

### 阅读路径

自下而上三层，每层右侧读“能证明 / 不能证明”。

### Wireframe

~~~text
第三层  [真实生成] 发送 Chat Completions   能证明：链路完整可用
        （1.4 动手做）                     不能证明：性能稳定、容量足够
           ↑
第二层  [模型列表] 请求 /v1/models         能证明：API 可访问、模型可发现
                                          不能证明：模型能完成一次生成
           ↑
第一层  [进程]     进程持续运行            能证明：进程已创建
                                          不能证明：模型是否加载完成
~~~

### 图中文字

- 第一层 · 进程
- 第二层 · 模型列表
- 第三层 · 真实生成
- 进程持续运行
- /v1/models
- Chat Completions
- 能证明
- 不能证明

### 关键结论

进程存在只是第一层证据，三层都通过才算服务可交付。

## 图1-3 同步请求字段与响应验收项

### 对应正文

1.5 检查完整响应

### 核心问题

请求里写了哪些字段，响应回来要按什么顺序检查？

### 核心观点

- 左侧是请求的五个字段，标出必需与可选。
- 右侧是响应的五个验收项，按正文顺序编号。
- 中间用一条箭头连接，明确 `stream=false` 意味着一次性返回完整 JSON。
- 箭头上标一句“HTTP 200 只说明服务收下了请求”，它不是验收项之一。

### 不应出现的内容

- 流式分片与 SSE 结构（图1-4 负责）。
- token 数、耗时等具体数值（图中只放字段名）。
- 服务端阶段归因。

### 阅读路径

先读左侧请求字段，经中间箭头，再从上到下读右侧五个验收项。

### Wireframe

~~~text
请求 (stream=false)          一次性完整响应
┌──────────────────┐        ┌────────────────────────┐
│ model      必需  │        │ 1 model 是否为目标模型 │
│ messages   必需  │ ─────► │ 2 role = assistant     │
│ max_tokens 可选  │ HTTP   │ 3 content 非空         │
│ temperature 可选 │ 200 不 │ 4 finish_reason        │
│ stream=false     │ 是验收 │ 5 usage（缺失则留空）  │
└──────────────────┘        └────────────────────────┘
~~~

### 图中文字

- 请求
- stream=false
- model / messages / max_tokens / temperature
- 必需 / 可选
- 一次性完整响应
- HTTP 200 不是验收项
- model
- role = assistant
- content 非空
- finish_reason
- usage
- 缺失则留空

### 关键结论

HTTP 200 不等于验收通过，五项要逐条检查；usage 缺失时留空，不折算。

## 图1-4 流式调用里客户端能记下的四个时刻

### 对应正文

1.7 发出第一次流式请求

### 核心问题

同一次调用，客户端凭什么能从“只记一个总时长”变成“记下一串事件”？

### 核心观点

- 上半部分是 SSE 流的形状：若干 `data:` 行，正文增量在 `delta.content`，末尾是 usage 分片和 `[DONE]`。
- 下半部分是客户端时间线，标出脚本记录的四类时刻：请求发出、首个内容分片、后续每个分片、收到 `[DONE]`。
- 用两条区间线说明客户端能闭合的两段：请求发出到首个内容分片、请求发出到流结束。
- 右侧用两个并列标签强调两种计数分开记：`stream_chunks` 由客户端数，`usage.output_tokens` 由服务端返回。

### 不应出现的内容

- 具体毫秒数（真实数字放在图1-5，这张图只讲结构）。
- 服务端事件（`first_token`、`first_chunk_sent` 属于第 2 章）。
- 把首个内容分片等待标成 TTFT。

### 阅读路径

先读上方 SSE 流的四类行，再落到下方同一条时间线上的四个时刻，最后读右侧的两种计数。

### Wireframe

~~~text
SSE 流：
  data: {"choices":[{"delta":{"role":"assistant"}}]}
  data: {"choices":[{"delta":{"content":"…"}}]}    ← 正文增量
  data: {"choices":[{"delta":{},"finish_reason":"stop"}]}
  data: {"usage":{…}}                              ← 只有 include_usage 才有
  data: [DONE]                                     ← 这一行不是 JSON

客户端时间线 ─────────────────────────────────────────────►
  ① 请求发出   ② 首个内容分片   ③ 后续分片 ③ ③ ③    ④ 收到 [DONE]
      │              │               │  │  │             │
      ├── 首个内容分片等待 ──┤       ├分片间隔┤           │
      ├────────────────── 整次调用时长 ────────────────────┤

两种计数分开记：
  stream_chunks       客户端数到的内容分片数
  usage.output_tokens 服务端返回的输出 token 数
~~~

### 图中文字

- SSE 流
- delta.content
- finish_reason
- usage
- [DONE]
- 客户端时间线
- 请求发出
- 首个内容分片
- 后续分片
- 收到 [DONE]
- 首个内容分片等待
- 分片间隔
- 整次调用时长
- stream_chunks（客户端计数）
- usage.output_tokens（服务端返回）

### 关键结论

流式让客户端在同一次调用上记下四个时刻、闭合两段区间；分片数与 token 数必须分开记。

## 图1-5 一个总时长，两个独立的问题

### 对应正文

1.8 从“多久答完”到“多久开口”

### 核心问题

同一次调用，为什么同步只剩一个数字，而流式能问出两个互相独立的问题？

### 核心观点

- 左右对照：左边同步记录只有一个 `time_total`；右边流式记录有开口时刻、分片节奏和结束时刻。
- 右侧数字取自 GX10 那次真实调用的客户端观测：首个内容分片 29.64 ms，254 个分片平均间隔 9.15 ms，整次调用 2345.26 ms。
- 从右侧引出两个问题框：“多久开口”和“后面出得稳不稳”，分别指向第 5 章的 TTFT 与 ITL。
- 底部注明这是一次调用的客户端观测，不是性能结论，也不能拆成服务端阶段。

### 不应出现的内容

- 服务端阶段（Queue、Prefill、Decode）与任何归因箭头。
- “TTFT = 29.64 ms”这类等号写法；只能写“客户端首个内容分片等待”。
- 平均值、分位数、吞吐等需要多次采样才成立的量。

### 阅读路径

先看左侧同步记录只有一个数字，再看右侧流式记录的三个数字，最后向下读出两个问题及其去向。

### Wireframe

~~~text
同步 stream=false                流式 stream=true
┌──────────────────┐            ┌─────────────────────────────────┐
│ 只有一个数字     │            │ 开口：首个内容分片 29.64 ms     │
│ time_total       │  ───────►  │ 之后：254 个分片，平均 9.15 ms  │
│ 中间没有可记事件 │            │ 答完：整次调用 2345.26 ms       │
└──────────────────┘            └─────────────────────────────────┘
        │                                   │            │
  只能问“多久答完”                   “多久开口”   “出得稳不稳”
                                          │            │
                                    第 5 章 TTFT   第 5 章 ITL

底部：GX10 一次真实调用的客户端观测，不是性能结论
~~~

### 图中文字

- 同步 stream=false
- 流式 stream=true
- 只有一个数字
- time_total
- 中间没有可记事件
- 首个内容分片 29.64 ms
- 254 个分片，平均 9.15 ms
- 整次调用 2345.26 ms
- 只能问“多久答完”
- 多久开口
- 出得稳不稳
- 第 5 章 TTFT
- 第 5 章 ITL
- 一次真实调用的客户端观测，不是性能结论

### 关键结论

交付方式一变，“快”就从一个数字变成两个独立的问题；这两个量由流式才测得到，正式名字在第 5 章。
