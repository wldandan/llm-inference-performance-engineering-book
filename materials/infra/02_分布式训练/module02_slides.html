Ring-AllReduce 通信原理

类比
圆桌传菜：N 个人围坐一圈，每人做一道菜，把自己的菜传给右边，接左边传来的菜加入自己的盘子。 经过 2(N-1) 轮传递，每个人的盘子里最终汇聚了所有人的菜——而不是全部集中到一个人再分发。
两阶段过程
① Scatter-Reduce（N-1步）
每人把自己的部分传出去，同时接收并累加别人的部分，最终每人持有一个完整的"分片求和"
↓
② AllGather（N-1步）
把各人持有的分片结果广播给所有人，每人最终得到完整的汇总梯度
通信量分析
总通信量 = 2 × (N-1)/N × Ψ ≈ 2Ψ
  • Ψ = 参数量，与 GPU 数 N 无关
  • vs Parameter Server：O(N) 通信量
  • 每 GPU 通信量恒定 = 2Ψ
  • Ring 拓扑充分利用双向带宽
Ring-AllReduce 将 AllReduce 的通信复杂度从 O(N) 降为 O(1)（相对每GPU），是 DDP 高效扩展的基石。

通信计算重叠（Overlap）

隐藏通信延迟，让 GPU 永远不等待

类比
边做饭边洗碗：不要等所有菜做完再洗，而是每道菜做完就立刻开始洗这道菜用的锅。 前向计算还在进行时，已完成层的梯度通信就已经开始了。
无重叠（串行）
反向传播（全部完成）
然后 AllReduce（等待）
总时间 = T_backward + T_comm
有重叠（并行）
层 N 反向
层 N 梯度通信（与层N-1反向并行）
总时间 ≈ max(T_backward, T_comm)
通信计算重叠是 DDP 实现接近线性扩展的关键工程手段，PyTorch DDP 默认开启。

Tensor Parallelism：矩阵切分

原理
矩阵乘法 Y = XW 中，把 W 沿列方向切成 [W₁ | W₂]， GPU₁ 算 XW₁，GPU₂ 算 XW₂，各自独立运行，最后 AllGather 拼合结果。
列并行（Column Parallel）
W = [W₁ | W₂]
GPU₁: Y₁ = XW₁
GPU₂: Y₂ = XW₂
Y = AllGather([Y₁, Y₂])
  • 输入 X 广播到两卡
  • 各卡独立计算
  • 最后 AllGather 合并输出
行并行（Row Parallel）
W = [W₁; W₂]ᵀ
GPU₁: Z₁ = X₁W₁
GPU₂: Z₂ = X₂W₂
Z = AllReduce(Z₁ + Z₂)
  • 输入 X 按列切分到两卡
  • 各卡计算部分结果
  • AllReduce 求和合并
MLP 应用

列并行 W₁ → 激活 → 行并行 W₂：每个 MLP 层 2 次通信

Attention 应用

QKV 投影用列并行，输出投影用行并行，每个 Attn 层 2 次通信

限制

TP 度 ≤ attention head 数；通信在节点内（需 NVLink）

TP 在节点内 NVLink 上几乎无瓶颈，每个 Transformer 层内 2 次 AllReduce，效率极高。

Pipeline Parallelism：流水线调度

类比
汽车装配流水线（4 工站）：底盘→车身→内饰→涂装。 每个工站只负责固定工序（对应 Transformer 层的子集）。 关键问题：换批次时工站空闲（气泡），多少辆车同时在线才能减少等待？
1F1B 调度示意（p=4, m=4 micro-batches）
GPU₁: [F1][F2][F3][F4]_____[B4][B3][B2][B1] ← 开头有气泡
GPU₂: ____[F1][F2][F3][F4][B4][B3][B2][B1]
GPU₃: ________[F1][F2][F3][F4][B4][B3][B2][B1]
GPU₄: ____________[F1][F2][F3][F4][B4][B3][B2][B1]
F=前向, B=反向, _=气泡（空闲）
  • 按层切分：每 GPU 负责 L/p 层
  • 一个 batch 分成 m 个 micro-batch
  • 1F1B：一前向一反向，降峰值显存
  • 跨节点通信：仅传激活值（小）
代价：气泡
  • 开始和结束阶段 GPU 空闲
  • m 越大，气泡占比越小
  • 实践推荐 m ≥ 4p
讲2 · 模型并行

气泡率公式与优化

气泡率 = (p − 1) / (m + p − 1)
p = 流水线阶段数（Pipeline Stages）  |  m = Micro-batch 数量
p（流水级） m=4 m=8 m=16 m=32 推荐 m
p = 2 20% 11% 6% 3% m ≥ 8
p = 4 43% 27% 16% 9% m ≥ 16
p = 8 64% 47% 32% 18% m ≥ 32
p = 16 79% 66% 50% 32% m ≥ 64
例题
p=4, m=8 时：气泡率 = (4-1)/(8+4-1) = 3/11 ≈ 27.3% → 约四分之一的算力在气泡中浪费。 改为 m=32：气泡率 = 3/35 ≈ 8.6%，代价是峰值显存随 m 增大。
气泡率是 PP 的核心 trade-off：m 越大气泡越小，但峰值显存越大。Megatron 用交错调度进一步减小气泡率至约 1/p 倍。

3D 并行选型矩阵

原则
把高带宽通信（TP）放节点内，低频通信（PP）放跨节点，DP 放最外层扩规模。
并行维度 通信类型 推荐位置 度数限制 典型值
TP（Tensor） AllReduce（每层） 节点内 NVLink ≤ attention heads 2, 4, 8
PP（Pipeline） P2P 激活传递 跨节点 IB ≤ 总层数 4, 8, 16
DP（Data） AllReduce（每步） 最外层，任意 无限制 8, 64, 512+
典型配置：65B 模型，64 卡

TP=8（8卡一节点），PP=4（4节点），DP=2（2路数据并行）
总 GPU = TP×PP×DP = 8×4×2 = 64

选型决策树

模型放得下单卡 → 只用 DP
放不下单卡但放得下节点 → DP + TP
放不下节点 → DP + TP + PP

3D 并行是训练超大规模模型（GPT-3/LLaMA-65B）的工业标准，关键是匹配硬件拓扑优化通信效率。

混合精度训练：草稿用粗笔

类比
写论文：草稿阶段用粗笔（BF16），快速推演，省纸； 定稿阶段用细笔（FP32），精确存档，保留所有细节。 两套笔同时存在，但关键时刻用细笔确认结果。
数据类型位宽用途优势限制
BF16 16 bit 前向/反向计算 速度 2x，显存 ÷2，动态范围大 精度略低
FP32 32 bit 梯度累加/主权重 高精度，避免下溢 显存多 2x
FP16 16 bit 老卡替代 BF16 速度快 需 Loss Scaling 防溢出
混合精度显存构成（每参数字节数）
FP16/BF16 权重 2B + FP32 主权重 4B + FP32 梯度 4B + Adam 动量×2 8B = 18B / 参数
vs 纯 FP32：4B 权重 + 4B 梯度 + 8B Adam = 16B / 参数 ← 差异不大，但计算快了 2x
BF16 是 A100 以上 GPU 的首选精度：训练稳定（动态范围与 FP32 相同），Tensor Core 加速约 2 倍，无需 Loss Scaling。

梯度检查点：以时间换空间

类比
登山不记录每一步的 GPS，只在关键路口（Transformer Block 边界）留标记。 下山（反向传播）时，发现需要某段的信息，就从最近的标记重新走一遍那段路。 代价是多走了约 1/3 的路，好处是大幅减少了随身携带的记录设备。
不用检查点（默认）
  • 保存所有层的激活值
  • 激活显存 ∝ 层数 × batch × seq_len
  • Llama-7B, bs=4, seq=2048：约 16GB 激活值
  • 反向传播直接读取，速度快
开启检查点
  • 只保存 Block 边界激活值
  • 激活显存降低 60-70%
  • 同样场景：约 4-6GB 激活值
  • 多约 33% 前向计算量（重算）
# PyTorch 使用方式 from torch.utils.checkpoint import checkpoint # 方式1：手动标记检查点 output = checkpoint(transformer_block, x) # 方式2：Hugging Face 一行开启（所有 Transformer Block） model.gradient_checkpointing_enable()
梯度检查点是训练大模型的标配：约 33% 速度换约 60% 显存，几乎所有 LLM 训练框架默认开启。
讲3 · 内存优化

ZeRO vs 梯度检查点：两种省内存策略

ZeRO 分片

  • 目标：参数、梯度、优化器状态的冗余
  • 手段：跨 GPU 分片存储，用时通信获取
  • 效果：最多节省 (N-1)/N × 总参数显存
  • 代价：额外 AllGather/Reduce-Scatter 通信
  • 适用：模型本身（参数量）导致的显存瓶颈

梯度检查点

  • 目标：前向激活值的中间存储
  • 手段：丢弃中间激活，反向时重新计算
  • 效果：激活值显存从 O(N) 降至 O(√N) 或 O(1)
  • 代价：约 33% 额外计算（重算前向）
  • 适用：批量大/序列长导致的激活显存瓶颈
组合使用效果（Llama-7B，8卡，bs=8，seq=2048）
FP32 DDP（基准）>200GB / 卡
无法训练
BF16 + ZeRO-2~45GB / 卡
勉强可行
BF16 + ZeRO-2 + 梯度检查点~22GB / 卡
充裕
两种技术解决不同瓶颈，组合使用：ZeRO 压缩模型本身的显存，梯度检查点压缩激活值显存。

Loss Spike：训练不稳定诊断

症状
训练曲线突然出现 Loss 上升 2-10x，可能随后自行恢复，也可能发散至 NaN。 千卡训练中每次 Spike = 潜在的数小时计算浪费。
原因诊断方式处理方法
坏数据 检查对应 batch 的 token，找异常序列 数据清洗，过滤极端长度/重复序列
LR 过高 对比历史 LR 曲线，Spike 前是否有 LR warmup 异常 降低峰值 LR，增加 warmup 步数
梯度爆炸 监控 gradient norm（应 < 1.0） clip_grad_norm_(params, max_norm=1.0)
数值溢出 检查是否出现 NaN/Inf，BF16 下特殊算子 混合精度关键操作用 FP32；检查 LayerNorm

必要时回滚 Ckpt
生产训练必须实时监控梯度范数和 Loss 曲线，并配置自动告警；Loss Spike 早发现比晚发现节省数倍算力。

Megatron-LM vs DeepSpeed 选型

Megatron-LM（NVIDIA）

  • TP + PP 工程实现最成熟
  • GPT / LLaMA / Falcon 官方支持
  • FlashAttention 深度集成
  • 性能调优文档丰富
  • 配置复杂，学习曲线陡峭
  • 需要修改模型代码适配
  • 适用：超大模型（>10B），NVIDIA 集群

DeepSpeed（Microsoft）

  • ZeRO-1/2/3 实现完整
  • HuggingFace Trainer 原生集成
  • 配置简单（JSON 文件驱动）
  • Offload 到 CPU/NVMe 支持
  • TP/PP 能力弱于 Megatron
  • 大规模 TP 性能有差距
  • 适用：中等规模（1-10B），快速迭代
选型建议
快速原型 (<7B)

HuggingFace Trainer + DeepSpeed ZeRO-2，json 一行配置

生产训练 (7-70B)

Megatron-DeepSpeed 组合，TP=8 + ZeRO-2

超大规模 (>70B)

Megatron-LM 完整 3D 并行，专用集群调优

模块二：4 个核心结论

① 并行策略：匹配硬件拓扑

TP 放节点内（NVLink 高带宽）→ PP 放跨节点（低频通信）→ DP 放最外层（规模无限）。 3D 并行是训练 7B+ 模型的工业标准。

② 内存优化：组合拳

混合精度（BF16）是起点，梯度检查点解决激活值，ZeRO-3 解决参数/优化器。 三者叠加可将可训练规模提升 10-20 倍。

③ 通信是瓶颈，也是可优化项

Ring-AllReduce 消除集中瓶颈；通信计算 Overlap 隐藏延迟； 降低 TP 度减少节点内通信。优化通信是千卡集群效率的关键。

④ 工程可靠性与算法同等重要

Checkpoint 策略、Loss Spike 监控、弹性恢复是生产级训练的必备能力。 每次千卡故障 = 数小时算力损失。

掌握这四点，就掌握了从单卡到千卡集群的核心设计哲学。
