💡 直觉类比

为什么需要 KV Cache？

📝 没有 KV Cache 的世界 生成第 100 个 Token 时，需要重新计算前 99 个 Token 的注意力——
相当于做完 99 道题之后，把草稿全撕掉，再从头重算一遍。

有了 KV Cache：把每个 Token 的 Key 和 Value 向量保存起来，
下次直接复用，不重新计算。这是空间换时间的经典策略。
O(n²)
无Cache时计算复杂度
O(n)
有Cache时计算复杂度

讲 2 · PagedAttention 核心设计

虚拟页 → 物理块映射

1
KV Cache 分块 — 每个物理块存固定数量（如16个）Token 的KV，按需分配
2
虚拟→物理映射表 — 每个请求维护一个映射表，逻辑连续但物理可以不连续
3
动态分配 — 生成一个Token分配一个槽位，不再预留最大长度
4
Copy-on-Write — Beam Search时多个候选路径共享KV块，写时才复制
📊 实测效果（vLLM论文数据） 吞吐量提升 2-4x，GPU内存浪费从 60% 降到 <4%

讲 3 · 哪些场景有公共前缀？

System Prompt 占大头

🤖 System Prompt 每次对话都有相同的系统指令（几百到几千Token）→ 可以缓存
📚 RAG检索结果 同一知识库片段在多次查询中重复出现 → 可以缓存
💬 多轮对话历史 对话前N轮对第N+1轮来说是公共前缀 → 可以缓存
🔬 Few-shot示例 所有请求共享相同的示例 → 可以缓存
讲 3 · SGLang 的 Radix Attention

前缀树自动管理所有缓存

🌳 Radix Tree 的工作方式 把所有历史请求的前缀组织成一棵树
新请求到来 → 在树中找最长公共前缀 → 直接复用对应的 KV Cache

例：两个请求都以「你是一个专业的医学助手...（800 token）」开头
→ 第二次请求直接复用，节省 800 token 的 Prefill 计算

💡 核心洞察

注意力矩阵的稀疏性

🔍 研究发现 在注意力计算中，通常只有 20-30% 的 Token 贡献了 80% 的注意力权重。
大量 Token 的注意力权重接近于零——它们的 KV 向量对最终结果影响极小。

核心问题：能不能把这些"不重要"的 Token 的 KV 删掉？
方案保留策略压缩比质量损失
H2O注意力分数高的Token2-4x小
SnapKVPrompt关键词位置2-3x小
StreamingLLM最近Token + Sink Token4-8x中（长文本）
KV量化(INT8)全部保留，降低精度2x极小

带宽差了 1000 倍

层级设备带宽容量延迟

讲 5 · 生产级案例
