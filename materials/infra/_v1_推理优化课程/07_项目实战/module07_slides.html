动手操作：从启动到Profile

启动 vLLM 服务

python -m vllm.entrypoints.openai.api_server \ --model Qwen/Qwen2.5-7B-Instruct \ --gpu-memory-utilization 0.85 \ --max-num-seqs 256 \ --served-model-name qwen2.5-7b \ --port 8000 # 验证服务就绪 curl http://localhost:8000/health

运行基准测试

for concur in 1 8 32; do python benchmark_serving.py \ --backend vllm \ --model qwen2.5-7b \ --request-rate $concur \ --num-prompts 500 \ --input-len 512 --output-len 256 \ --save-result \ --result-filename results_c${concur}.json done

Profile 分析

nsys profile \ --trace=cuda,nvtx \ --output=qwen_profile \ python benchmark_serving.py \ --num-prompts 50 \ --request-rate 8
⚠ 常见问题：Profile 文件过大 → 加 --duration 30 限制时长

第2讲 · 实战二

生产推理服务搭建

任务目标

基于实战一的优化假设，搭建具备生产特征的推理服务：Prefix Caching 降 TTFT、量化提升吞吐、PD 分离验证延迟优化——每个方案都要有前后对比数据。

实验 A：Prefix Caching

  • 场景：系统提示词复用
  • 预期：TTFT 降低 40-60%
  • 对照：相同 workload，关/开 cache
  • 指标：prefix hit rate + TTFT

实验 B：量化对比

  • FP16 vs W4A16 (AWQ)
  • 指标：吞吐量 / P99延迟 / 精度损失
  • 工具：AutoAWQ 量化
  • 数据：填标准对比表格

实验 C：PD 分离

  • Prefill实例 + Decode实例分离
  • 测量 TTFT / TBT 分别改善
  • 验证高并发下效果
  • 计算 GPU 利用率变化

第2讲 · 实战二

PD 分离：精细化资源调度

核心原理

Prefill（计算密集）和 Decode（内存带宽密集）的资源需求截然不同——把它们分到不同实例，各自针对性优化，整体效率提升 20-40%。

## SGLang PD 分离部署示例 # Prefill 实例（大 batch） python -m sglang.launch_server \ --model Qwen2.5-7B-Instruct \ --role prefill \ --port 30001 \ --chunked-prefill-size 512 # Decode 实例（低延迟） python -m sglang.launch_server \ --model Qwen2.5-7B-Instruct \ --role decode \ --port 30002 # 路由层 python router.py \ --prefill http://localhost:30001 \ --decode http://localhost:30002
指标合并部署PD分离改善
TTFT P50450ms180ms-60%
TBT P5035ms28ms-20%
GPU利用率72%88%+22%
GPU数量12×2 成本
⚠ PD分离不是银弹：低并发场景 ROI 可能为负，需要根据负载特征决策
第3讲 · 实战三

项目路演与答辩

路演核心原则

用数据讲故事，而不是用故事蒙数据。 每一个结论背后都要有数字支撑，每一张对比表都要公平可复现。

问题定义（2min）

  • 我们优化的是什么系统？
  • 初始基准数据是多少？
  • 与目标的差距有多大？
  • 为什么这个问题值得解决？

根因分析（4min）

  • Profile 截图/数据
  • Top-3 瓶颈排序
  • 排除了哪些错误假设？
  • 最终锁定哪个根因？

方案实施（5min）

  • 选择了哪些优化方案？
  • 为什么选这个而非其他？
  • 实施过程中遇到什么挑战？
  • 如何解决的？

效果量化（3min）

  • 优化前后完整对比表
  • 多次测量结果（统计显著性）
  • 成本收益分析（ROI）
  • 局限性与未来工作

模块总结

AI Infra 优化方法论

1

定义问题

建立基准，量化现状，明确目标 SLA，计算当前与目标的差距

2

精准诊断

Profile 工具定位瓶颈（不要靠猜！），区分 Compute Bound vs Memory Bound

3

ROI 优先级排序

每个优化假设都估算收益/成本，优先做高 ROI 的事，避免过早优化

4

受控实验

一次改一个变量，多次测量，公平对比——这是工程师和调参侠的核心区别

5

效果量化与复盘

不只看平均值，看 P99；不只看延迟，看成本；记录失败的实验同样宝贵

模块总结

工程师思维 vs 调参侠思维

调参侠

  • 凭感觉选优化方案
  • 只跑一次看结果
  • 一次改多个参数
  • 只报告成功的实验
  • "感觉快了很多"
  • 优化完就结束
  • 不考虑成本
VS

AI Infra 工程师

  • Profile 数据驱动方案选择
  • 多次测量取统计显著结论
  • 控制变量，一次一个改动
  • 记录所有实验（含失败）
  • "TTFT P99 从 450ms → 180ms"
  • 建立回归检测防退化
  • 优化前必算 ROI
结束语

AI Infra 工程师的核心能力——不是会用工具，而是知道什么时候用什么工具，以及为什么。
