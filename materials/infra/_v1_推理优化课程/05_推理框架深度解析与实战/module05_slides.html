💡 直觉类比

vLLM 就像一台精密工业机器

⚙️ 机器的各个零件 LLMEngine（控制中心）：接收所有请求，协调各模块工作
Scheduler（调度大脑）：决定哪些请求现在跑，哪些等待，哪些换出到CPU
Worker（执行手臂）：真正在GPU上运行模型的代码
KV Cache Manager（内存管家）：用 PagedAttention 精细管理每一块GPU内存

每个零件各司其职，任何一个零件出问题，整台机器就卡住了。

讲 1 · Scheduler 核心逻辑

三种队列，动态流转

W
Waiting 队列 — 刚进来的请求，等待分配KV Cache物理块，FCFS调度
R
Running 队列 — 正在GPU上执行的请求，Decode阶段逐Token生成
S
Swapped 队列 — GPU内存不足时，KV Cache被换出到CPU，等待换回
📌 抢占（Preemption）触发条件 GPU内存即将耗尽 → Scheduler将低优先级请求的KV Cache换出（Swap）到CPU内存
换出代价：PCIe带宽 ≈ 32 GB/s，换出32GB约需1秒 → 尽量避免
讲 1 · PagedAttention 实现细节

Block Table：虚拟到物理的映射

📐 核心数据结构 每个请求维护一个 Block Table（逻辑块号 → 物理块号的映射表）
物理块固定大小（默认16个Token的KV Cache）
Beam Search时多个候选共享相同前缀的物理块（Copy-on-Write）
✅ 解决的问题 内存碎片：从60%浪费降到<4%
按需分配，不预留最大长度
⚠️ 代价 Block Table查表有额外开销

讲 1 · 性能调优关键参数

四个最影响性能的参数

# 关键参数速查 vllm serve meta-llama/Llama-3-8B \ --gpu-memory-utilization 0.92 # GPU内存使用率上限（默认0.9） --max-num-seqs 256 # 最大并发序列数 --max-num-batched-tokens 8192 # 单次Forward最多token数 --enable-chunked-prefill # 开启Chunked Prefill # --enforce-eager # 禁用CUDA Graph（调试用）
💡 CUDA Graph 的作用 把固定形状的计算图预先录制成 CUDA Graph，消除每次 Python 开销 → Decode 阶段加速 10-20%
代价：首次"预热"需要额外时间，且形状固定（Batch Size/SeqLen变化会重新录制）

💡 直觉类比

为什么 SGLang 在某些场景更快？

🧠 三个核心升级 1. RadixAttention（超级记忆）：把所有历史请求的前缀组织成前缀树， 新请求来了自动找最长匹配——相当于大脑里装了一个完美索引。

2. FlashInfer（更快的肌肉）：用专门为LLM推理设计的GPU Kernel， 比通用实现快10-20%，尤其在多序列混合场景。

3. Overlap Scheduler（双手并用）：CPU调度下一批的同时，GPU执行当前批—— 完全消除CPU等待时间。
讲 2 · RadixAttention 核心原理

前缀树自动管理所有 KV Cache

🌳 Radix Tree 工作方式 所有历史请求的 Token 序列 → 组织成一棵 Radix Tree
新请求到来 → 从根节点开始匹配，找到最长公共前缀
→ 直接复用对应的 KV Cache，跳过 Prefill 计算

例：100个请求都有相同的 2000 token System Prompt
vLLM Prefix Cache：哈希匹配，需预先建索引
SGLang RadixAttention：自动，无感知，命中率更高

讲 2 · SGLang 两大差异化特性

结构化输出加速 + FlashInfer

📋 Structured Output 加速 在采样阶段直接 mask 非法 Token
（而不是采样后再验证）
JSON/正则约束下速度提升 5-10x
⚡ FlashInfer 集成 统一的 GPU Attention Kernel 库
支持 Ragged Batch（不等长序列）
Decode 阶段比 vLLM 快 10-20%
🔧 Overlap Scheduler 原理 传统：GPU 跑完一批 → CPU 调度下一批 → GPU 再跑（串行）
SGLang Overlap：CPU 调度 Batch N+1 与 GPU 执行 Batch N 完全并行
→ CPU 调度开销从关键路径上消除 → 整体吞吐提升 5-15%

讲 2 · 生产部署关键实践

从实验到生产的必经之路

1
容器化部署 — Docker/K8s，镜像固定版本，避免依赖地狱（vllm:latest-cuda12.4）
2
健康检查 — /health 和 /metrics 端点，GPU利用率/队列深度/P99延迟实时监控
3
预热策略 — 启动后发送若干预热请求，CUDA Graph 提前录制，避免首批请求延迟尖刺
4
滚动升级 — 蓝绿部署或金丝雀发布，新版本上线前跑 Benchmark 对比，确认无回归
