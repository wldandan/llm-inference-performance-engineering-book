benchmark_serving 实战

vLLM 内置基准脚本

python benchmarks/benchmark_serving.py \ --backend vllm \ --model Qwen/Qwen2.5-7B-Instruct \ --dataset-name sharegpt \ --dataset-path ShareGPT_V3_unfiltered_cleaned_split.json \ --num-prompts 1000 \ # 总请求数 --request-rate 10 \ # 并发请求率 (req/s) --max-concurrency 32 \ # 最大并发 --percentile-metrics p50,p99 # 输出百分位

关键参数

  • --request-rate: 压力梯度测试
  • --input-len / --output-len: 固定长度
  • --seed: 可复现随机
  • --ignore-eos: 强制满输出

输出解读

  • Throughput: X tokens/s
  • TTFT P50/P99: Xms
  • TPOT (= TBT) P50/P99
  • ITL: Inter-token Latency

测试矩阵

  • 并发数: 1/4/8/16/32
  • 输入长度: 128/512/2048
  • 输出长度: 128/256/512
  • 各组合各跑3次取均值
第1讲 · 性能基准测试

三大核心指标深度解析

指标全称计算方式影响因素优化方向
TTFT Time To First Token 请求发出 → 收到第一个 Token Prefill 计算量、KV Cache 命中、队列等待 Chunked Prefill、Prefix Caching
TBT Time Between Tokens 相邻 Token 生成间隔 Decode batch size、显存带宽 批处理优化、量化降显存压力
QPS Queries Per Second 单位时间完成请求数 Prefill/Decode 调度、连续批处理 PagedAttention、调度算法
E2E Lat 端到端延迟 TTFT + TBT × output_len 全链路 综合优化
SLA 设计参考

交互式对话：TTFT < 200ms，TBT < 30ms ｜ 批处理任务：QPS 优先，延迟可放宽 ｜ 代码补全：TTFT < 100ms（用户感知敏感）

容器化部署实践

Dockerfile 关键设计

FROM nvcr.io/nvidia/cuda:12.4.0-runtime-ubuntu22.04 RUN pip install vllm==0.6.0 \ --extra-index-url \ https://download.pytorch.org/whl/cu124 EXPOSE 8000 ENTRYPOINT ["python", "-m", "vllm.entrypoints.openai.api_server"]

K8s GPU 资源配置

resources: limits: nvidia.com/gpu: "1" memory: "32Gi" requests: nvidia.com/gpu: "1" memory: "28Gi" env: - name: CUDA_VISIBLE_DEVICES value: "0" - name: VLLM_GPU_MEMORY_UTILIZATION value: "0.90"
  • 镜像选择：优先用 NVIDIA 官方基础镜像，避免 CUDA 版本不匹配
  • HPA 配置：基于自定义指标（GPU 利用率/请求队列长度）自动扩缩容
  • Node Affinity：绑定 GPU 节点标签，避免 Pod 调度到 CPU 节点

GPU OOM 排查全流程

类比

OOM 就像 ICU 突然停电——不能等它发生才应对，要提前有预案、有早期预警、有快速恢复流程。

1

现象识别

kubectl logs 出现 CUDA out of memory / RuntimeError；Pod 反复 CrashLoopBackOff

2

快速诊断

kubectl describe pod → 查看 OOM Killed 事件；nvidia-smi dmon → 实时显存趋势；检查 --gpu-memory-utilization 参数

3

根因分析

KV Cache 预分配过大？请求 max_tokens 未限制？显存碎片？批大小设置不合理？

4

修复与预防

降低 gpu_memory_utilization（0.95→0.85）；限制 max_num_seqs；启用显存泄漏检测；配置 OOM Score Adjustment

模块总结

生产部署 10 条检查项

部署前

  • 完整 benchmark 测试（TTFT/TBT/QPS）
  • Profile 瓶颈定位，确认无低垂优化
  • OOM 压测（极端输入长度/并发）
  • 健康检查端点 /health 配置
  • 资源 limit/request 精确设定

运行中

  • DCGM + Prometheus + Grafana 监控栈就绪
  • OOM / 高延迟 AlertManager 规则配置
  • 滚动升级策略（maxUnavailable: 0）
  • 成本仪表盘（GPU 利用率 / Token 产量）
  • On-Call 响应手册与 Runbook
核心原则

没有监控的生产部署等于盲飞。可观测性不是锦上添花，是工程成熟度的核心标志。
