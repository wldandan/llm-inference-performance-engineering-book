# Chapter 29 Demo：上线检查与评审

`release_check.py` 做 29.2 那九项清单和 29.1 那五处接缝。三个子命令，全部离线：

```text
check    九项清单加五处接缝，退出码可直接接进发布流程
packet   同一份结果渲染成 29.6 那份评审材料
window   29.4 那四档观察窗口：各看什么、为什么
```

输入是一份把所有材料汇在一起的 JSON。仓库里三份样例，都是**合成设定**：

```text
release-docs-pass.json    材料齐备，五处接缝一致
release-docs-seam.json    九项全绿，一处接缝对不上（29.8 案例一）
release-docs-gaps.json    接缝都对，缺的正好是最容易跳过的第五和第八项
```

29.1 说评审的价值不在重审每一份材料，而在交叉检查那些接缝，这个子命令就是那句话的可执行版本。**接缝不一致是阻断项，和清单缺项同级。**

## 2. 接缝对不上要能换算成一个数

`context_length_consequence()` 把“12000 对 16000”换算成“并发少多少、卡要加几张”，依据是第 16 章那张表里并发上限反比于平均总长度：KV 预算固定，每条请求占的 KV 和它的总长度成正比。

```text
(12000 + 220) ÷ (16000 + 220) = 0.753
8 ÷ 0.753 = 10.6 → 11 张
```

**不做这一步的话，“接缝”只是一句口号。** 报出 11 张，评审现场就知道这不是一个格式问题。

这个换算只在显存先满时成立，所以它读容量模型里的 `binding_constraint`：

```text
memory       直接换算卡数，8 张要 11 张（本样例，system prompt 长、并发受 KV 限制）
throughput   不换算卡数。显存多出来的卡仍不是约束，变的是 Prefill 占时，
             要求用第 26 章的模型按新的输入长度重算
没写         照显存先满换算，同时提示先把这一项补上
```

第 26 章的主例就是吞吐先满：输入从 2600 加到 3400，显存一侧 5.3 → 6.8 张，吞吐一侧 31.7 → 36.3 张，42 张变 48 张。

## 2.1 实例数那处接缝是两个不等式

容量模型给峰值卡数和下限卡数（第 26 章 Demo 的 `gpus_floor`），扩缩容配一个区间。核对的是：

```text
max_instances ≥ 峰值卡数
min_instances ≥ 下限卡数
```

样例里峰值 8、下限 3，扩缩容区间 3 到 24，一致。要求最小实例数等于峰值卡数等于说波谷永远缩不下来，所以脚本不这样比。不一致时 `note` 会点名是哪一边：`最大实例数 6 低于峰值卡数 8`。四个数缺一个，状态是“无法核对”。

## 3. 监控就绪不是一个是非题

```bash
python3 code/ch29/release_check.py check \
  --docs content/ch29/evidence/release-docs-gaps.json
```

```text
  [缺项] 监控就绪    缺 ['itl_distribution']。29.8 案例三就是缺了 itl_distribution，
                     出问题后加指标、发版、等数据花了两天
  [缺项] 回滚预案明确且演练过  没有演练量出来的耗时：演练的目标就是量出这个数；
                     没写回滚后的缓存恢复期，29.8 案例二就栽在这里
结论              不通过
                  清单缺项：monitoring、rollback
```

`check_monitoring()` 不接受一个 `true`，它对着 `REQUIRED_METRICS` 那十一项点名，缺哪一项说哪一项。十一项分两组：`RESULT_METRICS` 是用户看得到的结果（P95 TTFT、P95 ITL、ITL 分布、错误率、拒绝率、SLO 达成率），`CAUSE_METRICS` 是调度器那一侧的原因（槽位占用率、排队长度、抢占计数、KV 使用率、Prefix Cache 命中率）。拒绝率单列，因为 SLO 的口径常常不含被拒绝的请求，只看达成率时多拒绝一些反而好看。29.8 案例三里那个“监控就绪”填的是“是”，而真正需要的 ITL 分布指标根本不存在。

`check_rollback()` 同样不接受“有预案”这个说法。它要四样东西：触发条件、**演练量出来的耗时**、不可回滚项、回滚后的缓存恢复期。29.3 说没演练过的预案在真正需要时才会发现不对，而演练的产出就是一个数；29.8 案例二栽的是第四样，回滚后旧实例重启、缓存清空，二十分钟里比新版本还慢。

这份样例缺的正好是 29.2 点名的第五项和第八项，`skipped_among_the_easy_ones` 把它们单独列出来。

## 4. 无法核对不等于通过

一处接缝的两边只要有一个没提供，状态是“无法核对”而不是“一致”，整份评审降级为**有条件通过**。把缺数据读成没问题，是这类检查最常见的坏掉方式。

`traffic_policy` 那一项还有一条额外规则：五项配置齐全但准入配了没开启，照样算缺项。**准入是突发流量唯一的防线**，这是第 21 章和 27.8 共同的结论。

## 5. packet 把缺项显式标出来

```bash
python3 code/ch29/release_check.py packet \
  --docs content/ch29/evidence/release-docs-gaps.json --output review-packet.md
```

按 29.6 那几块组织：九项清单、五处接缝、观察窗口、回滚、责任人。缺的地方写 `**未演练**`、`**未记录**`，不留空、也不渲染成一个 `None`。字段存在而值是空的，比字段不存在更容易被读成没问题。

## 6. window

29.4 那四档，`24h` 那一档的说明里点了一句别的三档都没有的话：**它是唯一能验证容量核算的窗口**，因为只有它跨越了一个完整的日内波峰。测试核对这句话只出现在这一档上。

## 7. 测试

```bash
python3 -m unittest discover -s code/ch29 -p 'test_*.py'
```

62 项。最重要的一组是 `TestSeamSample`：九项全绿、结论不通过、唯一原因是 `context_length`，而且它和通过样例除 `runtime` 和 `gate` 外逐字相同。其余钉住的：九项的顺序与第五第八项的位置、十一项必需指标（结果在前，命中率在原因那一组）、五项治理配置、四档观察窗口、`12220 ÷ 16220 = 0.753` 与 `8 → 11 张`、吞吐先满时不换算卡数、实例数那两个不等式。

用在自己的发布流程里时，先把五处接缝的两边改成直接从真实的配置文件和容量模型输出里读，免得汇总 JSON 时抄错；再演练一次回滚，把量出来的耗时填进去。
