# Chapter 26 Demo：容量与成本模型

`capacity_cost.py` 把 26.2 到 26.6 那条链变成可以改一个数就重算一遍的东西。三个子命令，全部离线：

```text
size      从日请求量一路推到卡数和月成本，每一步都把中间量打出来
whatif    改一个输入，看卡数和成本怎么动，并把没有影响的场景单独列出来
margin    26.3 那两张余量表：每档卡数的负载率、挂一张之后、突发消化时间，
          以及排队的两种算法（单副本上界和 Erlang C）
```

## 1. size 会把“搬数字”的条件一起搬过来

```bash
python3 code/ch26/capacity_cost.py size
```

```text
峰值调用 QPS      133.3333
峰值 token 速率   输入 346667，输出 29333 token/s
峰值在途          560 条（Little's Law）
                  单卡并发 149 条是在总长度 2300 token 下测的，本次负载 2820 token，折算为 122 条
                  Prefill 占时在输入输出比 1.5 时是 10%，本次 11.82，按 占时/(1−占时) 与比值成正比
                  折到 46.7%；单卡输出吞吐 1560 → 924 token/s
按吞吐            27.3 张
按显存            4.6 张
每卡在途          吞吐允许 21 条，显存允许 122 条（单卡 S ≈ 205 ms）
卡数              36 张  throughput 先满（27.3 对 4.6）。刚好够是 28 张，加 30% 余量后 36 张
下限卡数          4 张  波谷是日均的 30%，刚好够 2.7 张，加同样的余量、且不少于 2 张，下限 4 张。…
单位成本          每百万 token 1.3298 元（有用产出口径）
平均负载率        25.3%，实际单位成本是满载口径的 3.955 倍
```

**这里有两步折算，跳过任何一步，配出来的就是另一个负载的答案。**

第一步是并发。第 16 章那张容量表给出的 149 条是在平均总长度 2300 token（prompt 2000 + 输出 300）下算的，本例是 2600 + 220 = 2820。`scale_concurrency()` 做的就是这件事，测试钉住了 `149 × 2300 ÷ 2820 ≈ 122`。29.8 案例一整个就是在讲这一步被跳过之后会发生什么。

第二步是吞吐。1560 是第 19 章那次批量扫描量的，那份负载输入输出比约 1.5，Prefill 只占单卡时间的 10%（合成设定）；本例输入输出比 11.8，Prefill 占到约 47%。折算用的是比值形式：一条请求占卡的时间是 `输入 ÷ Prefill 速率 + 输出 ÷ Decode 速率`，所以与输入输出比成正比的是 `占时 ÷ (1 − 占时)`。直接按比例放大占时会算出 79%，输入再长一点就超过 100%。`prefill_share_at()` 钉住了附录 B-4 那几个数：25% 在 6.67 量到，换到 11.82 是 37.1%，8.18 是 29.0%，40 是 66.7%。

加 `--ignore-prefill` 就去掉第二步，得到只看两个静态约束的 16.2 张。正文 26.3 先算这个数，再说明它为什么不能用。

“每卡在途”那一行把两个约束放到同一把尺子上：吞吐那一侧按 Little's Law 换成在途条数（单卡请求速率 × 平均请求时长），和显存允许的条数直接比。

“下限卡数”是第 27 章的最小实例数和第 29 章那处接缝要的数。`--trough-to-mean` 是谷均比（波谷 QPS ÷ 日均 QPS，默认 0.3）；两个约束都和 QPS 成正比，所以波谷要的卡数就是峰值那个数乘以 谷均比 ÷ 峰均比，再加同样的余量，至少 2 张。

哪个约束先满决定了上下文变长时该怎么算。本例是吞吐先满：把输入从 2600 加到 3400，显存一侧从 4.6 张变成 5.9 张，仍然不是约束；吞吐一侧因为 Prefill 占时升到 53%，从 27.3 张变成 31.2 张，36 张变 41 张。第 29 章那个“8 张要 11 张”的换算只在显存先满时成立。

## 2. 输入长度这个杠杆，只有算了 Prefill 占时才通

```bash
python3 code/ch26/capacity_cost.py whatif \
  --scenario traffic=3x --scenario input_tokens=1800 --scenario peak_to_mean=2.0
```

```text
基线              36 张，月成本 432000
  traffic=3x              107 张（+71）  月成本 +197.2%  约束在 throughput
  input_tokens=1800        31 张（-5）  月成本 -13.9%  约束在 throughput
  peak_to_mean=2.0         24 张（-12）  月成本 -33.3%  约束在 throughput
```

同一条命令加上 `--ignore-prefill`，`input_tokens=1800` 那一行变成 `+0.0%` 并被单列进 `no_effect`：只有两个静态约束时，卡数由输出 token 速率定，输入长度对它没有任何影响。**报出 `+0.0%` 而不是编一个好看的降幅**，是这个子命令在那种情况下的全部价值。

`traffic=3x` 是三倍减去取整误差：维持同样的负载率，卡数和流量成正比。

`--peak-to-mean` 是峰均比，峰值 QPS ÷ 全天平均 QPS。它不是第 22 章的峰谷比。把 22 章那份负载的峰谷比 11.25 当峰均比代进来，按吞吐要 60.7 张，是正确值的 3.7 倍，测试里专门有一项钉着这件事。

## 3. margin 把“加 30% 到 50%”拆成四件事

```bash
python3 code/ch26/capacity_cost.py margin --minimum-cards 27.3 --options 31,36,39,41
```

```text
   31 张   ρ = 0.881   单副本上界 7.38   Erlang C 0.1054  加 14% 余量
   36 张   ρ = 0.758   单副本上界 3.14   Erlang C 0.0088  加 32% 余量
   39 张   ρ = 0.700   单副本上界 2.33   Erlang C 0.002   加 43% 余量
   41 张   ρ = 0.666   单副本上界 1.99   Erlang C 0.0007  加 50% 余量
```

每一行的 `reading` 里还有挂一张卡之后的负载率和一分钟三倍突发的消化时间（13.8 / 5.3 / 3.7 / 3.0 分钟）。余量由四件事各要一份：单卡故障和滚动升级各一张、流量预测误差、突发。前三项连乘约加 25%，突发决定还要不要往上加。

排队报两列，因为哪一列更接近你的部署取决于派发方式，脚本看不到：请求被前缀亲和钉在副本上时接近单副本上界，按负载派发时接近 Erlang C。两列都以单卡服务时间 S 为单位。`erlang_c()` 在 16 张当量、18 张卡时给出平均排队 0.266 个 S、53% 的请求要排队，和附录 B-1 那张表一致。

它们都只给量级，用来定档位，不要用来承诺毫秒数。

## 4. costs 的分母是有用的实际产出

`costs()` 默认不报满载口径的单位成本，要看得加 `--show-saturated`，而且会附一行警告。默认口径的分母是有用的实际产出：`--useful-share` 是成功、达标、没被用户放弃的那部分占实际产出的比例，默认 1。单位成本永远和平均负载率一起报，并给出它是满载口径的几倍：

```text
实际单位成本 = 满载单位成本 ÷ 平均负载率 ÷ 有用比例
```

本例满载口径每百万 token 约 0.34 元，实际口径约 1.33 元，3.96 倍；同一份负载走 API 的混合价约 0.89 元。`--useful-share 0.9` 时实际口径约 1.48 元。

56 项。钉住正文数字的那一组：`160万 ÷ 86400 ≈ 18.5`、`18.5 × 3 × 2.4 ≈ 133`、`130 × 2300 ÷ 2820 ≈ 106`、`133 × 4.2 ≈ 559`；静态 18.8 张、补上 Prefill 占时 31.7 张、42 张；Prefill 占时 10% → 46.7%、单卡 1560 → 924；每卡在途 30 → 18 条；余量四档的负载率与消化时间、单副本上界与 Erlang C；平均负载率 25.2%、3.97 倍、每百万 token 0.39 / 1.55 元；峰均比 3 → 2 降 33.3%、输入 2600 → 1800 降 14.3%；峰谷比错代成峰均比时的 3.75 倍；下限卡数 5 张；上下文 2600 → 3400 时显存一侧 5.3 → 6.8、吞吐一侧 31.7 → 36.3。
