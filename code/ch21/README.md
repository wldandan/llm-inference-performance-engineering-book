# Chapter 21 Demo：过载演练

`overload_drill.py` 做两件事：把服务压过容量看它以什么形状垮，以及把 21.5 那个重试放大器走一遍。

四个子命令，后两个之外的两个需要真实服务：

```text
run           阶梯加压，每档记录六个字段
analyze       判 goodput 曲线的形状：健康 / 退化 / 危险 / 可疑 / 未到容量
retry-storm   21.5 那个放大器，可以手填失败率，也可以从演练曲线上读
cancel-check  比较断开前后两份调度器快照，验证 21.4 那条链路
```

## 1. 先看形状

仓库里有一对合成演练，同一份负载、同一个容量，只差有没有准入：

```bash
python3 code/ch21/overload_drill.py analyze \
  --report content/ch21/evidence/overload-drill-no-admission.json
```

```text
goodput 峰值      11.5（offered 12.0 QPS）
末档 goodput      2.1（峰值的 18.3%）
峰值后拒绝        0.0 QPS
形状              危险
```

换成 `overload-drill-with-admission.json`，同样的 36 QPS 末档：

```text
末档 goodput      11.1（峰值的 97.4%）
末档拒绝          24.7 QPS
形状              健康
```

这一对就是 21.1 那个 A 和 B。**两份报告的 offered_qps、容量、SLO 逐项相同**，测试会核对这一点，否则对比不成立。

## 2. 五种形状，其中两种是关于演练本身的

```text
健康        末档 goodput ≥ 峰值的 90%，且峰值之后有拒绝
退化        掉到峰值的 50% 到 90%：准入生效了但不够早
危险        掉到峰值的 50% 以下：准入没有生效，全员失败
可疑        goodput 平稳而一条都没拒 → 瓶颈可能在压测客户端，不在服务端
未到容量    goodput 一路涨到最后一档且全程没有拒绝 → 这次加压没超过容量
```

**最后两种是这个脚本最该存在的理由。** 一条根本没压到容量的曲线被判成“健康”，是唯一一种会让人挨伤的错答案，所以这一条判在最前面。

## 3. retry-storm 的两种模式

手填失败率，复现案例一那张表：

```bash
python3 code/ch21/overload_drill.py retry-storm \
  --failure-rates 0.04,0.15,0.40,0.73 --retries 3
```

```text
轮次   单次失败率 p    放大系数    上界 1+p·r    下一轮负载
 0        4.0%        1.04        1.12          1.04 倍
 1       15.0%        1.18        1.45          1.18 倍
 2       40.0%        1.62        2.2           1.62 倍
 3       73.0%        2.65        3.19          2.65 倍
用户侧失败        28.4%
可用性            71.6%
```

放大系数按各次独立失败的精确式 `1 + p + p² + … + p^r` 算，旁边那列是速记的上界 `1 + p·r`，对应每次重试都失败。

71.6% 和案例里那个 71% 落在同一个位置，而它是从表里最后那个 73% 算出来的，不是另外量的。

从演练曲线上读，这是案例一那道讨论题的答案：

```bash
python3 code/ch21/overload_drill.py retry-storm \
  --report content/ch21/evidence/overload-drill-no-admission.json \
  --initial-p 0.04 --retries 3
```

这份演练的曲线比案例走得慢（第 1 轮 7.4% 对 15%），但它不会停在第 3 轮，第 17 轮走到 94.2% 的不动点，可用性 21.4%。**差别不在算法，在于案例只观察到第 3 轮就已经在处理故障了。** 换成加了准入的那份报告跑同一个回路，失败率收在约 43%，可用性约 97%：被拒的请求同样算失败、同样会被重试，但准入让被接受的那部分保持健康，回路的终点就挪开了。

**曲线超出实测范围时钳住，不外推。** 真实的失败率曲线比任何一条穿过它的直线都更陡，外推出来的数字会读着让人安心，而这正是最不该让人安心的地方。

## 4. goodput 的定义和第 5 章一致

`summarize_step` 只把“成功且 TTFT 满足 SLO”的请求算进 goodput。**快速失败不算，慢速成功也不算。** 这两条各有一项测试钉着，因为把 429 算成 goodput 会让危险的曲线看起来是健康的。

`p95_ttft` 只统计被接受的请求。被拒的请求几毫秒就返回，混进分布会把 P95 拉低一大截。

## 5. 三条重试纪律里的第一条做成了检查

`classify_retry_policy` 判一份重试配置重试了哪些错误：

```text
可以重试    connection_failed、503、带 Retry-After 的 429
不可重试    timeout、不带 Retry-After 的 429
```

超时刻意不在可重试之列：你不知道服务端是不是还在处理，而对 LLM 请求来说重试意味着整段生成付两遍钱。

## 6. 测试

```bash
python3 -m unittest discover -s code/ch21 -p 'test_*.py'
```

57 项。钉住正文数字的那一组：r = 2 时精确放大在 2% / 50% / 90% 上是 1.02 / 1.75 / 2.71，上界 `1 + p × r` 是 1.04 / 2.00 / 2.80，且上界永远不小于精确值；`1/(1−p)` 在 90% 上是 10；案例一那四轮的放大系数是 1.04 / 1.18 / 1.62 / 2.65；`0.73⁴` 对应的可用性是 71.6%。

两份演练报告都是**合成设定，不是真机演练**，`synthetic` 字段和 `_note` 都写明了。

在自己的服务上做一次真机演练：跑完 `run` 三档以上加压，确认 goodput 曲线是平稳形态，用 `retry-storm --report` 从自己的曲线上读出那条回路，并用 `cancel-check` 量出取消的生效时间。`cancel-check` 的两份快照可以直接用第 20 章的 `collect` 取。
