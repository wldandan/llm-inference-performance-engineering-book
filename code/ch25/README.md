# Chapter 25 Demo：全链路实验

`e2e_experiment.py` 做 25.3、25.6、25.7 各自要求的那一件事。四个子命令，全部离线：

```text
budget    编排层按步数、模型服务按调用次数拆预算，在预算不可能达成时直接报错
run       检查一份全链路实验报告：十维记分卡、预算对照、跨层影响、五项边界
guard     跑 25.7 那五条断言，退出码可直接接进 CI
ceiling   算出命中率断言的天花板，用来核对门槛设得对不对
```

## 1. budget 会拒绝不可能的目标

```bash
python3 code/ch25/e2e_experiment.py budget --slo 8000 --steps-p95 10 \
  --model-calls-p95 7 --service-time-ms 103 --rho 0.69
```

```text
总预算            8000 ms
  orchestration      500 ms   步数 P95 = 10，每步编排开销 50 ms
  retrieval         1200 ms   含重排
  model_serving     5000 ms   含排队，按 7 次模型调用计，每次 714 ms
  tools             1000 ms   代码执行设超时
  未分配余量         300 ms   余量是整条链路共用的一份
每次模型调用      714.286 ms（实测纯计算 480.0 ms，留给排队 234.286 ms）
负载率上限        0.6946（S = 103.0 ms，按 20.6 反推）
负载率 0.69 时    每次排队约 229.3 ms
这份预算下最多    10 次调用（只算纯计算）
验收              这张表是一条 P95 那类任务的时间怎么分；验收只看整条链路的
                  P95 任务完成时间，不拿各层自己的 P95 相加（第 5 章）
```

编排层按步数、模型服务按调用次数拆，因为 25.2 那 34 步里只有约 7 次是模型调用。传现状负载率 0.9，也就是 25.3 里被推翻的那一版：

```text
REJECTED: 每次调用 714 ms，扣掉纯计算 480 ms，留给排队的只有 234 ms；负载率
0.9 时按 20.6 每次排队约 927 ms（S = 103.0 ms）。要么把负载率守在 0.69 以下
（准入、容量、减少调用），要么这个 SLO 定错了。这个矛盾必须在动手之前解决
```

**报错而不是返回一份看起来合理的分配，是这个子命令的全部价值。** 25.3 说这个矛盾必须在动手之前解决，而一个总能返回结果的函数正是让它在优化到一半才被发现的那个东西。

`0.69` 不是拍的：排队预算 q = 714 − 480 = 234 ms，`ρ/(1−ρ) ≤ q/S` 即 `ρ ≤ q/(S + q) = 234/337`。S = 103 ms 是从 25.2 反推的：负载率 0.9 时平均排队 9 个 S，每次调用排队约 930 ms。纯计算一侧另有一条硬线：`5000 ÷ 480 = 10.4`，哪怕排队为零也最多放 10 次调用，不给 `--model-calls-p95` 时按每步一次调用算，15 步会因为每次只有 333 ms 被拒。

## 2. ceiling 把 25.7 那个 55% 的依据算出来

```bash
python3 code/ch25/e2e_experiment.py ceiling --calls 7 --route-hit 0.9 --threshold 0.55
```

```text
7 次调用的追加式上下文里可缓存占比约 71.4%，前缀亲和后的路由命中 0.9，
天花板 64.3%，门槛 55.0% 留 9.3 个点的余量
```

可缓存占比那 71% 是算出来的，不是量出来的：`1 − 2/调用次数`。推导在 25.7 里：每次调用里全新的只是上一次之后新增的那一段，各次的全新部分加起来正好等于最后一次调用的输入，而按 24.3 那个梯形式子累计输入约是 `调用次数 × 末次输入 / 2`。**由此也能看出调用越多可缓存占比越高**，4 次是 50%，40 次是 95%。

门槛贴着或超过天花板时它会说“这条断言必然长期红着”并以退出码 1 返回。不做前缀亲和、三实例轮询时，按第 22 章的路由项，7 次调用的会话前缀路由命中约 0.6，缓存吃紧时往 1/3 掉，天花板在 43% 到 24% 之间，55% 的门槛够不着，这个检查会当场说出来。

## 3. guard 要求每条断言写出依据

```bash
python3 code/ch25/e2e_experiment.py guard \
  --config content/ch25/evidence/guard-rules-sample.json
```

五条断言里少任何一条就拒，某条没写 `basis` 也拒：

```text
REJECTED: 断言 load_skew 没有写 basis：25.7 要求每条断言后面都写清阈值是
从哪里来的，否则半年后没人敢改它，也没人敢相信它
```

测试里有一组专门核对 25.3 那个数字改动的后果：门槛定在第一版的 15 步时，实测 14 步会被判为合格，而 14 步时编排层要 700 ms，超出调整后预算给的 500 ms；换成 10，同一个实测值就被拦住了。**这条门禁原来会放过它本该拦住的那次回退。**

## 4. run 的三条硬性检查，加一条没法用检查表达的规则

```text
layer_breakdown 必须标注采集时的负载水平，空闲状态下采集的分解直接拒
cross_layer 不可为空，跨层实验必须记录对其他层的影响
boundary 五项齐全，比第 14 章多一项 chain_structure
```

还有一条：**质量、任务成功率、抢占计数是否决项，不是投票项。** 报告写着通过而这三项里有一项恶化，检查器拒绝。仓库里那份 `e2e-experiment-three-at-once.json` 就是这种情形：

```text
记分卡            10 维，2 维改善
否决项            ['task_success_rate', 'preemption_count']
                  2 个维度改善，但这两项恶化了。记分卡不是投票
```

它对应 25.9 案例二本身（三项一起改，端到端 21 秒涨到 24 秒），而 `e2e-experiment-admission.json` 对应那个案例修正之后的那一轮（单独开准入并同步关掉编排层盲目重试，降到 16 秒）。**两份报告的采集条件（`collected_under_load`、`load_note`）和 `boundary` 逐字相同**，测试核对这一点，否则对比不成立；`layer_breakdown` 里的占比两份不同，因为分解正是被改动的对象。两份都还没走完 25.4 那六项改动，所以四层都还在超支——它们是过程中的两轮，不是终态。

`layer_breakdown` 的各层占比之和必须等于 1（容差 2%），各层实测之和要和端到端 P95 对得上（容差一成），每层的占比还要和它自己的实测对得上（容差 3 个百分点）。对不上时报错说的是“要么有一层漏了，要么某一段的时间被算了两遍”，后者在全链路追踪里比前者常见。

四种结论仍然是第 14 章那四种，`run` 直接 import `code/ch14/prefill_experiment.py` 的 `VERDICTS`，和第 19 章一样。

## 5. 测试

```bash
python3 -m unittest discover -s code/ch25 -p 'test_*.py'
```

62 项。钉住正文数字的那一组：调整后的预算 `500 + 1200 + 5000 + 1000 + 300 = 8000`、编排层 `10 × 50 = 500`、7 次调用每次约 714 ms 其中约 234 ms 给排队、S = 103 ms 时负载率上限约 0.69、现状 0.9 时每次排队约 927 ms 被拒、7 × 927 ms 约等于 25.2 那 31%、`5000 ÷ 480 = 10.4` 所以最多 10 次调用、`1 − 2/7 ≈ 71%`、`0.71 × 0.9 ≈ 64%`、门槛 55% 留约 9 个点；案例一约 7% 与“吞吐跟着涨时约 36%”的对照。

三份样例都是**合成设定，不是真机实验**。

在自己的链路上做一次综合实验，这是 Part 5 的交付：按 25.4 的顺序做完六项改动，每改一项跑一次 `run`，产出十维齐全的报告，并把 `guard` 接进部署流程。
