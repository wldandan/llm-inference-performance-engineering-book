# Chapter 19 Demo：Decode 实验记分卡

`decode_experiment.py` 复用第 14 章那份检查器的纪律（四种结论、可识别线、预期必须事前写下），再加上 Decode 侧才有的三块：五维记分卡、批量扫描的 Goodput 曲线、与已启用项的相互作用检查。

采数据需要真实 vLLM 服务。检查器本身不需要，可以直接拿仓库里那份合成样例跑一遍。

## 1. 运行

```bash
python3 code/ch19/decode_experiment.py \
  --report content/ch19/evidence/decode-experiment-sample.json
```

## 2. 三条硬性检查

```text
1  latency、throughput、capacity 三项不可为空，缺一项拒绝出报告
2  changed 里动了精度 → quality 必须有值、有底线、有底线的写入时间、有评测集
3  changed 里开了投机解码 → 必须提供两个批量档位的接受率
```

第二条是这一章最重要的一道闸。**动了精度却没有质量数据的报告，不该被接受**，哪怕 TPOT 数字很漂亮。

`latency` 那一项要三个数：`tpot_mean_ms`、`itl_p95_ms`、`itl_max_ms`。第三个最常被漏掉，而它是唯一看得出抢占的那个。最大 ITL 超过平均 TPOT 十倍时，脚本会追加一条“先去查抢占计数，不要当成噪声”。

## 3. 两处 Decode 侧才有的设计

**指标方向必须写清楚。** 第 14 章只判 TTFT，越小越好。这一章同一份报告里 TPOT 越小越好、并发越大越好，所以 `results.direction` 是显式的。方向写错会把 213 → 419 这样的改善读成劣化。

**`passed` 和 `kept` 是两件事。** 一轮实验可以结论有效而这项改动仍然不留下：第 3 轮那样，收益真实，但不值得付出草稿模型那 2.1 万 token 的容量。两个字段分开，后面几轮才算得对自己叠加在什么之上。判失败却写着保留，检查器会拒。

## 4. 检查器拒绝什么

- 记分卡缺 latency / throughput / capacity 任一项；
- `latency` 缺三个数里的任何一个；`capacity` 缺抢占计数；
- 动了精度而 `quality` 为空、没写底线、没写底线的写入时间、没写评测集；
- 开了投机解码而 `acceptance` 为空，或只给了一个批量档位；
- `changed` 出现两项或以上；
- 报告写下的结论和它自己的数据算出来的不一致（结论要从数据里出来，不是写上去的）；
- 报告写 `passed: true` 而质量已越界；
- 报告写 `kept: true` 而这一轮判失败；
- 有 `results` 却没有 `verdict`；既没有 `results` 也没有 `sweep`；
- 标了“在波动内不可分辨”却又在别处写着“小幅有效”“略有改善”；
- 叠加在已启用项之上却没有 `interaction`，或 `remeasured_all_dimensions` 不为 true，或 `stacked_on` 没列全；
- `sweep.design` 不是 `closed_loop_fixed_concurrency` 或 `fixed_cap_sweep_rate`：用一个固定的开环到达率去扫批量上限，装不下的档位会一直排队；
- 扫描的档位里没有一档的达标率达到 95%（可行集是空的）。

扫描的峰值按 19.3 的两步规则选：先用 SLO 的整体要求（达标率 ≥ 95%）和质量底线筛出可行档位，再在其中取 Goodput 最大。对照轮的结论按第 14 章那两步判：先比改善和可识别线（t × √(2/n) × CV），再比改善减预期和同一条线，中心值用均值。

## 5. 五轮各演示一种情形

`decode-experiment-sample.json` 是**合成样例，不是真机结果**，`synthetic` 字段和 `_note` 都写明了。

```text
第 0 轮  批量扫描              闭环固定并发，按 SLO 筛出可行档位，只出 Goodput 曲线
第 1 轮  KV Cache INT8         符合预期，并发 213 → 419（改善 96.7%，预期 96%）
第 2 轮  权重 INT8             四个维度全部改善，质量越界，判失败并回滚
第 3 轮  投机解码              低于预期，暴露离线 3.1 与线上 2.1 的差；成立但不留
第 4 轮  CUDA Graph 最大捕获批量   主指标在波动内不可分辨，收益在容量一列
```

**第 2 轮是核心。** TPOT 降 40.3% 正好符合预期，吞吐涨、并发涨、显存降，五个维度里四个都在改善，而结构化输出那一维掉了 3.9 个百分点，越过 1 个百分点的底线。检查器判失败：**四个维度改善抵不过一个越界，记分卡不是投票。**

**第 4 轮是另一头。** 它把最大捕获批量从 512 降到 64，启动日志里的图捕获显存从 2.4 GiB 降到 0.9 GiB（合成设定），省下的 1.5 GiB 被 KV 池接走，并发上限 419 → 429。主指标测不出来是一个合法且诚实的结论，而这一轮仍然保留：收益不大，但没有代价。每一轮的并发乘平均长度再乘每 token KV 字节，都核过装得进那一轮的 KV 预算。结论写在 `capacity` 而不是 `latency`，这正是五维记分卡存在的理由：收益出现在哪一列，就写在哪一列，不往主指标上凑。

第 0 轮那条曲线里，可行档位是批量 4 到 32，Goodput 峰值在 32（1560 达标 token/s），TPS 峰值在 128。后者名义上高 109%，但有 80% 的请求不达标，Goodput 反而低 57%。这是 19.7 案例三那组数字。不加约束时 Goodput 最大的是批量 64（1807），它的达标率只有 74%，不在可行集里，这正是“先筛再选”这个顺序要挡住的。

TPS 那一列不是手填的：`sweep_from_model` 按第 15.3 节那条搬运模型生成，`check_sweep_floor` 再逐档校验，自己的实测扫描也该先过这道体检。批量 B 时每步至少要搬一遍权重，TPS 超过 `B ÷ 单步下限` 的档位不可能是量出来的。

## 6. 测试

```bash
python3 -m unittest discover -s code/ch19 -p 'test_*.py'
```

72 项测试，大部分是拒绝测试。另有一组针对样例本身：四种结论都出现过、只有第 2 轮失败、只有第 3 轮成立但不留、五轮的 workload 与 protocol 逐字相同、每轮的 magnitude 每一项都有 `basis`、每轮都有 `null_criterion`、每轮的 `boundary` 四项齐全且 model 那一项带上了每 token KV 的具体字节数。

样例是合成的。在真实服务上跑完批量扫描和五轮之后，用真实报告替换它，检查器的规则不变。
