# Chapter 27 Demo：弹性伸缩仿真

`autoscale_sim.py` 把 27.4 的回路滞后和 27.5 的时间尺度错配变成可以跑的东西。四个子命令，全部离线：

```text
lag       把回路滞后拆成三段，指出哪一段最长，并给出“值得响应”的门槛
simulate  在一条流量轨迹上跑一种策略，把未满足需求按突发和趋势分开算
compare   四种策略同轨迹对比，包括不扩不缩只做准入
cache     22.4 那条前缀迁移式子：缩容会让多少前缀要重建
```

## 1. lag：滞后是三段之和，而最长的那一段决定你能做什么

```bash
python3 code/ch27/autoscale_sim.py lag
```

```text
  observation      30 到    90 秒
  decision         30 到   120 秒
  cold_start      180 到   600 秒
解读              回路滞后 4 到 13.5 分钟。经验上取两倍，也就是持续 27 分钟以上的变化
                  才值得交给 Autoscaling；更短的突发，无论指标选得多好、阈值调得多准，都追不上。
```

`27.0` 是 `13.5 × 2`，两倍是经验取法：滞后 13.5 分钟的回路要等变化持续到它的两倍以上，扩出来的容量才还用得上。**冷启动是默认配置下最长的那一段**，所以 `loop_lag()` 会点名它，并提示预热实例池是唯一能把它压到秒级的办法。把冷启动压到 10 秒后最长的那一段换成决策与冷却，整个滞后降到 150 秒以内。

## 2. compare：四种策略，同一条轨迹

```bash
python3 code/ch27/autoscale_sim.py compare \
  --traffic content/ch27/evidence/traffic-trace-sample.csv
```

```text
轨迹              高峰是中位的 3.928 倍，持续 90 秒
策略                       未满足        被拒    抖动        成本  结论
reactive            107175.0       0.0     0      49.1  趋势跟得上，突发跟不上
scheduled           106695.0       0.0     0      49.7  趋势跟得上，突发跟不上
warm-pool           106467.0       0.0     0      50.3  趋势跟得上，突发跟不上
admission-only           0.0  133440.0     0      44.0  可用
静态档位          admission-only 按需求 P95 ÷ 目标负载率 0.7 配 11 个实例
```

**这张表是 27.5 那段话的量。** 那次突发只持续 90 秒，比 420 秒的回路滞后还短，所以三种靠扩缩容的策略都在那一段上漏了需求；而只做准入的那一列未满足为零，成本还低一成。

`unmet` 一开始是一个总数，看不出问题出在哪里。现在它拆成 `unmet_in_surge` 和 `unmet_in_trend`，样例轨迹上前者占 99% 以上，所以结论写的是“趋势跟得上，突发跟不上”而不是笼统的“尺度错配”。**弹性不是没用，是突发那一段不该交给它。**

`admission-only` 配的实例数不是 `min_instances`，而是 `ceil(P95 需求 ÷ (单实例容量 × 0.7))`，也就是 27.5 说的“按预留余量配”，而且按目标负载率 0.7 配。按负载率 1 配只要 8 个，P95 时负载率 0.955，成本 32 看着更省；可模拟器不建模延迟，负载率贴着 1 在这里没有代价，在真实服务上那是第 20 章曲线最陡的地方。`--target-load` 可以改这个数。

输出最后那行“注意”是给读表的人的：未满足和被拒不是同一种损失。被拒的请求立刻拿到 429，可以退避或降级；未满足的请求堆在队列里慢慢超时，还拖慢同批的其他请求。按 Goodput 比，不要把两列加起来比。

## 3. simulate 会拒绝对称阈值

```bash
python3 code/ch27/autoscale_sim.py simulate \
  --traffic content/ch27/evidence/traffic-trace-sample.csv \
  --scale-down-threshold 0.7
```

```text
REJECTED: 阈值要满足 0 < 缩容 0.7 < 扩容 0.7 < 1：27.6 说两个方向的风险不对称，
用同一个阈值的系统会持续抖动
```

27.6 讲的就是这条。**报错而不是跑出一条抖动曲线**，是因为抖动的成因在配置里，不在轨迹里。

## 4. cache：缩容的代价能算出来

```bash
python3 code/ch27/autoscale_sim.py cache --before 12 --after 8
python3 code/ch27/autoscale_sim.py cache --before 12 --after 8 --modulo
python3 code/ch27/autoscale_sim.py cache --before 12 --after 4
```

```text
解读              12 → 8，必须重建 33% 的前缀，预计回暖 40 分钟。一致性哈希要重建 33%，取模哈希要重建 67%
解读              12 → 8，必须重建 67% 的前缀，预计回暖 80 分钟。一致性哈希要重建 33%，取模哈希要重建 67%
解读              12 → 4，必须重建 67% 的前缀，预计回暖 80 分钟。这一档取模哈希和一致性哈希一样
                  （12 和 4 成倍数），换哪种哈希都救不回来，要改的是缩容幅度
```

两个式子都来自 22.4。一致性哈希要迁移的键约占 `|N − M| ÷ max(N, M)`；取模哈希保住的是 `gcd(N, M) ÷ max(N, M)`，因为 `hash % N` 和 `hash % M` 相同要求余数小于两者中较小的那个，每个最小公倍数周期里恰好有 `min(N, M)` 个这样的键。所以 12 → 11 取模只保住 1/12，而 12 → 4 碰巧和一致性哈希一样保住三分之一。**一致性哈希能把缩容的代价降下来，但降不到零**；缩容幅度大到成倍数时，换什么哈希都一样。

27.9 案例二那三个数（12 → 8 取模八十分钟、一致性哈希四十分钟、缩到 4 时两种都是八十分钟）由测试钉住，取模的保留比例还和暴力枚举对过一遍。

## 5. 样例轨迹

`content/ch27/evidence/traffic-trace-sample.csv`，4 小时、30 秒一步。它同时带着两类变化：一条 450 → 1150 的日内波峰，和 t=9000 处一次持续 90 秒的 3 倍突发。**两类都要有，否则 27.5 那张表没法验证**：只有趋势的轨迹会让弹性看起来无懈可击，只有突发的轨迹会让它看起来一无是处。

轨迹是**合成设定**，`.README.md` 里写了生成参数。
