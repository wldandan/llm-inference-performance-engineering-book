# Chapter 24 Demo：Agent 任务档案

`agent_profile.py` 报的每一个数都是任务级的，一个都不是调用级的。这是 24.1 那句话的直接后果：单次调用的指标全部达标，任务仍然可能要几分钟。

三个子命令，都是离线的：

```text
profile    24.7 那张字段表
tail       长尾任务的步骤序列与浪费模式
step-slo   24.2 那张表和它的反推
```

## 1. profile

```bash
python3 code/ch24/agent_profile.py profile \
  --traces content/ch24/evidence/agent-traces-sample.jsonl
```

```text
任务数            10
                  只有 10 个任务，P95 落在最大值上，它反映的是那一个任务而不是一个分布。
步数              P50 8  P90 18  P95 40  P99 40  max 40  均值 11.9
模型调用次数      均值 11.9  P50 8  P95 40
LLM 占比          67.2%
工具占比          14.8%
  run_code        9.7%
  search          3.2%
  read_file       1.9%
未归属占比        18.0%
累计输入          精确 1757200，梯形估 1762700.0
放弃率            10.0%，平均在第 9.0 步
步数超限率        10.0%
```

两处刻意的设计：

**未归属时间单独成列，不摊进 LLM 和工具。** 编排层开销、串行等待、追踪没覆盖到的部分都落在这里。让三项占比凑成 1 会正好盖掉这个缺口，而 25.2 那张表里编排层那一栏量的就是这个缺口（两条链路不同，样例那 18% 是照 25.2 设的）。

**步数和模型调用次数分两项报。** 第 26 章代进容量链的是后者的均值：纯工具步不打到模型服务上（24.1、25.5）。这份合成样例里每一步都有模型调用，所以两项相等，真实链路上往往差好几倍。

**样本少于二十个时输出一句提醒。** 十个任务的 P95 就是最大值，它反映的是那一个任务，不是一个分位数。与其让读者以为自己看到了分位数，不如把这句话说出来。

## 2. step-slo 把 24.2 那张表变成可执行的

```bash
python3 code/ch24/agent_profile.py step-slo \
  --step-pass-rate 0.95 --steps 15 --task-target 0.95
```

```text
  N = 5    0.95^5 ≈ 77%
  N = 8    0.95^8 ≈ 66%
  N = 15   0.95^15 ≈ 46%
  N = 35   0.95^35 ≈ 17%
反推              要让 15 步任务的任务级达标率做到 95.0%，单步需要 99.66%。
砍一半步数        7 步时任务级达标率 69.8%
```

最后那一行是“先减步数”那条结论的量：把单步从 95% 抬到 99.66% 很难，把步数从 15 砍到 7 就能把任务级达标率从 46% 抬到 70%。

**带重试的 Agent 会被直接拒绝：**

```text
REJECTED: 这个 Agent 开了重试，不能用 p 的 N 次方来估任务级达标率：
带重试的 Agent 可以多花两三步换一次成功，任务整体仍然达标。按 24.6 的做法，
达标要定成“任务在时限内完成”的比例，用 profile 的 duration 分布和目标时限算，
不是按步累乘
```

24.2 自己就说了这条估算有两处会偏，其中带重试那一处足以让乘法模型失效，所以这里把它做成硬拒绝而不是一句提示。

## 3. tail 是这一章最有用的工具

```bash
python3 code/ch24/agent_profile.py tail \
  --traces content/ch24/evidence/agent-traces-sample.jsonl \
  --percentile 0.7
```

它按判据降序输出长尾任务的工具序列，并找三种浪费模式：

```text
repeated_tool    同一个工具被连续调用 ≥ 4 次 → 工具粒度太细
oscillation      在两个工具之间来回 ≥ 4 步 → 错误信息不够清楚
same_resource    ≥ 4 次调用指向同一份资源 → 同一份长文档被反复解析
```

门槛设在 4 是刻意的：连续两三次调同一个工具是正常的。`same_resource` 不要求连续，因为隔着几步读同一份长文档一样要为它的返回内容重复付费。

最后一行的解读才是重点：

```text
长尾里有 2 种模式出现在两个以上的任务里（['same_resource', 'repeated_tool']）：
修掉一个模式能同时改善很多任务，这是从长尾下手的全部理由。
```

一种模式都没重复出现时，它会说这些任务大概确实复杂，该看的是 24.5 那条能不能拆成并行子任务。

**样本小的时候把 `--percentile` 调低。** 十个任务用 0.95 只会挑出一个，看不出模式是否共享。

## 4. 梯形式子在两处都有用

`cumulative_tokens` 同时报三个数：逐步累加的精确值、24.3 那个 `步数 × (首步 + 末步) / 2` 的梯形估算，以及“首步乘以步数”这个错法。

```text
t-001   12 步，2000 → 28000    精确 174500   梯形 180000   偏高 3.15%
t-002    8 步，3000 → 20000    精确  92000   梯形  92000   偏差 0
```

第一行是 24.3 那个例子，第二行是 24.8 案例二那笔账。第三列那个错法在 t-002 上给的是 24000，而真实是 92000，正好 3.83 倍；案例二里加上步数估少了那一项，一共差 6.1 倍。

## 5. 一处拒绝

一步没有 `tools` 字段就拒，理由是 24.4 那句话：没有按工具拆开的 Span，工具等待这块时间在监控里是不存在的，你只会看到“任务很慢”。**没调工具的那一步写空列表**，这和“没记”是两件事，脚本区分得开。
