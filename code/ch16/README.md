# Chapter 16 Demo：KV Cache 容量计算器

`kv_capacity.py` 是 16.6 那张九步容量表的代码版，外加三件表本身说不出来的事。

只依赖 Python 标准库，不需要 GPU。

## 1. 运行

```bash
python3 code/ch16/kv_capacity.py \
  --config code/ch15/model-7b-generic.json \
  --weight-memory 14 \
  --avg-context 2300 --p99-context 9200 \
  --block-size 16 \
  --mix 0.97:2300,0.03:32000 \
  --preempt-context 8000 --recompute-ms 1288
```

模型形状默认读 Part 4 共享的那份配置，`--layers`、`--kv-heads` 这些可以逐项覆盖。

## 2. 九步表

```text
1. 可用预算    80 GiB × 0.9 = 72 GiB
2. 减去权重    -14 GiB
3. 减去开销    -6 GiB（经验值，必须实测）
4. KV 预算     52 GiB
5. 每 token    128 KiB
6. 总 token    425984
7. 平均总长    2300
8. 理论并发    185 条
9. 打折        130~148 条
```

第 1 步那个 `--utilization` 默认按 vLLM 的 0.9 取：引擎只拿到整张卡的九成，按 80 GiB 整张卡起算会把 KV 预算高估 8 GiB，到第 8 步就是多出近三十条并发。自己的服务按启动参数的实际取值传。

第 3 步那个 `--overhead` 每次运行都会带一条警告：它是经验值，猜出来的数字会让后面全错。实测方法不是看空载时的 nvidia-smi：vLLM 一类引擎启动时已按 `gpu_memory_utilization` 留出 KV 池，空载也显示七十多 GiB。要读启动日志里的权重显存与 KV 池容量，用 `gpu_memory_utilization × 显存总量 − 权重 − KV 池` 反推（16.6 第 3 步）。

## 3. 三件表说不出来的事

**安全并发在两个数之间。** `concurrency_avg` 和 `concurrency_p99` 一起给出是刻意的：平均长度给 185，P99 长度给 46，真实的安全并发在这两个数之间，具体位置取决于长度分布的形状和你能接受多少抢占。

**块大小不是免费的。** `blocks` 那一组把 16.4 那笔内部碎片的账算出来：平均浪费半个块，乘并发才是总账。128 条并发、块大小 16 时浪费约 1024 个 token 的空间（128 MiB），块大小 128 时是 8192 个（1 GiB）。浪费超过预算的 2% 会给警告，因为它直接换走一部分并发上限。

**并发上限由最坏情况的混合决定，不是由平均长度决定。** `--mix` 接一个长度分布：97% 的请求 2300 token、3% 的请求 32000 token，平均 3191，按平均算是 133 条；而全是长请求时只有 13 条。16.9 案例三那个“并发掉到十几条”就是后一个数。给了 `--mix`，报告会同时给这两个数，并提醒容量表第 7 步用平均值等于默认了混合比例稳定。

## 4. 抢占那一段，被代码改过一次

`preemption_cost` 算重算与换出的代价。写这个函数时发现正文初稿是错的。

初稿写的是“分界点随长度移动，短序列上重算更划算”。摊到每个 token 上算一遍就知道不成立：重算是 `2 × 参数量 ÷ 有效算力`，7B 上约 0.14 ms；换出往返是 `2 × 每token字节数 ÷ PCIe 带宽`，约 0.016 ms。两者都与长度成正比，比值约八点五倍，**跟长度无关**，而 Prefill 的平方项只会让重算更贵。

所以这个函数不判哪个“划算”。它报告哪个在墙钟上更快，并说明墙钟算不出来的两笔代价：重算要占满整卡算力跑一段 Prefill，那一秒多里同卡正在 Decode 的请求都跟着停，这笔代价摊给了所有人；换出走 PCIe，带宽相对显存带宽很小，对其他请求影响有限，它的代价是主机内存（批量 32 条就是 31 GiB）和引擎复杂度。**判据不是哪个更快，是愿不愿意让一次抢占打断所有人。**

## 5. 实测对照

给了 `--measured-concurrency`，报告会按 16.8 那两个用法给解读：远低于建议区间就怀疑 `--overhead` 估小了或有别的显存占用；显著高于理论上限就说明真实平均长度比你以为的短，回去核对负载画像。

## 6. 测试

```bash
python3 -m unittest discover -s code/ch16 -p 'test_*.py'
```

63 项测试。16.2 的 131072 字节与 512 MiB、16.4 的两档块大小浪费、16.5 的 1000 MiB 与 65 / 131 ms、16.6 的 72 GiB 预算 / 52 GiB / 425984 / 185 / 46 / 130~148、16.7 那张四行表的每一行、16.9 案例三的 3191 与 133 与 13，全部由代码算出来。其中 `TestSection165Preemption` 那一组的类注释记录了上面那次正文被改的经过。

这张表算出的并发是待校准的估计。用在自己的服务上时，按它去压测，记录实际的抢占计数和显存占用，反过来校准 `--overhead`。
