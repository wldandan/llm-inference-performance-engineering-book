# Chapter 22 Demo：架构决策与路由评估

`serving_choice.py` 两个子命令，对应这一章的两半：

```text
decide      22.2 那四条判据，按 22.2 的优先级排。离线
route-eval  22.4 那个取舍，命中率与不均衡度两个反向指标。路由项那张表离线
```

## 1. decide 的判据顺序就是算法

```bash
python3 code/ch22/serving_choice.py decide \
  --workload content/ch22/evidence/workload-knowledge-base.json \
  --peak-qps 45 --trough-qps 4 \
  --data-residency required \
  --slo-ttft 1500 \
  --api-price 0.002 --gpu-monthly 12000 \
  --capacity-per-gpu 12 \
  --team-capacity yes
```

```text
硬约束            ['数据不能出域']
峰谷比            11.25
峰值需要          4 张卡，平均负载率 29.2%
API 月成本        101606.4
自建月成本        48000.0
平衡点            平均 6.6138 QPS，即平均负载率 13.8%
建议形态          自托管
  - 硬约束成立（数据不能出域），按 22.2 的第一条直接走自托管，成本不参与这个决定
```

**成本算了但不参与决定**，这是刻意的。22.2 的第一条说三条硬约束任何一条成立就直接走自托管，不用再算成本；数字仍然报出来，因为预算要报，但输出里写明它没有进入这个决定。

把 `--data-residency` 和 `--slo-ttft` 都去掉，同一组数会给出相反的答案（只去掉 `--data-residency`、留着 `--slo-ttft 1500` 时，第三条判据会把它推回专用部署）：

```text
建议形态          共享 API
  - 峰谷比 11.25，过了 5.0 这条线：自建要按峰值配 4 张卡和一支团队，22.1 那三项
    不进月成本的投入（工程、可用性、模型迭代）在这种只在峰值时段用满的形状下最不划算。
    这条线是经验界，已经在养别的自建服务的团队可以用 --api-peak-trough 调高
  - 按卡钱算自托管更便宜（API 101606 vs 自建 48000）：平均负载率过 13.8% 自建就和
    API 打平，这份负载是 29.2%。但 22.1 说过成本通常不是自建的真正优势，所以它排在判据之后
```

那条 1500 ms 也是经验界：22.2 第三条只说“SLO 卡得紧的场景需要独占资源”，脚本把“卡得紧”落在这个数上。

**自建便宜一半，仍然不推荐自建。** 七成的闲置已经算在那 48000 里了，卡钱这一侧自建确实赢；推荐 API 靠的是峰谷比那条判据背后的三项不进月成本的投入。那条线 5 是本书的经验界，`--api-peak-trough 20` 时同一组数推荐专用部署。

`breakeven_utilization` 是平衡点 QPS 除以按峰值配好的总容量：平均负载率到这里，按卡钱算两边打平。它和第 26 章那个分解式是同一件事的两面：自建的单位成本随平均负载率反比变化。

## 2. `--team-capacity` 是一道闸

结论是自托管或专用部署而没填这一项时，脚本拒绝出结论：

```text
REJECTED: 结论是自托管，但没有填 --team-capacity：22.2 把“团队能不能养”
列为第四条判据并说它最常被低估，没有这一项的结论不能出
```

填 `no` 时分两种情形，这个区分是这道闸真正的价值：

```text
无硬约束 + 养不起   → 退回共享 API
有硬约束 + 养不起   → 仍然是自托管，但输出里写明这是一个必须先解决的前置条件
```

## 3. route-eval 把 22.4 那个取舍变成两个数

```bash
python3 code/ch22/serving_choice.py route-eval \
  --report content/ch22/evidence/route-eval-sample.json
```

那份样例复现 22.8 案例二：多轮对话服务，长前缀是每段对话自己的历史（`prefix_scope` 是 `session`），可缓存占比 0.92，四个实例，三种策略。

```text
会话级前缀被轮询打散时的路由项（缓存装得下时；装不下更低）
  1 个实例  k=2 50.0%  k=10 90.0%  k=100 99.0%
  4 个实例  k=2 12.5%  k=10 62.3%  k=100 96.0%
  8 个实例  k=2 6.2%  k=10 41.0%  k=100 92.0%
```

```text
  round-robin                 命中率 29.6%  不均衡度 0.0018  P95 1250
  prefix-hash                 命中率 88.8%  不均衡度 0.9416  P95 980   最差实例 1420
  prefix-hash-with-overflow   命中率 79.9%  不均衡度 0.2041  P95 680   最差实例 740
```

**中间那一行是 22.4 说的热点。** 它命中率最高，却在 P95 上输给带溢出的那一版，而且最差实例 1420 ms，聚合值掩盖了 440 ms。所以脚本除了报“命中率最高”和“最均衡”，还报一个“实际可用形态”：在不均衡度还感觉不到（≤ 0.3）的策略里取命中率最高的那个。这一栏选出来的正是 22.4 说的第三种形态。

## 4. 三处刻意的拒绝

```text
缺 worst_instance 或任一实例字段   拒（22.5：聚合指标会掩盖单实例问题）
单实例命中率 > 可缓存占比          拒（13.3：那是天花板，超过说明量错了）
加权命中率 > 声明的溢出天花板      拒（溢出比例是配置不是实测，最容易对不上）
                                   溢出天花板 = 可缓存占比 × (1 − 溢出比例 × (1 − 1/N))
```

第三条比第二条更容易踩到。溢出比例是你在路由里设的阈值，实际溢出多少是跑出来的，两者不一致时命中率会莫名其妙地超过天花板。轮询不设 `1/N` 这条线：全体共享的前缀轮询下照样命中，`1/N` 只是会话级前缀在复用少、缓存又装不下时的情形，不能拿来拒绝报告。

**命中率按请求数加权，不是各实例简单平均。** 轻载实例的高命中率和满载实例的低命中率等权，会让打散的策略看起来比实际好。

## 5. 测试

```bash
python3 -m unittest discover -s code/ch22 -p 'test_*.py'
```

63 项。钉住正文数字的那一组：路由项在 N = 4 时 k = 2 / 10 / 100 必须是 12.5% / 62% / 96%，且和第 13 章的同名函数逐值相等；不均衡度在 `[25,25,25,25]` 上是 0、在 `[100,0,0,0]` 上是 2.0（样本标准差）；N = 4、平均负载率 0.7、不均衡度 0.3 时最热实例最坏约 1.0；滚动升级时 85% 在 4 个和 12 个实例下分别变成 113% 和约 93%；取模哈希 12 → 11 只保住 8%；案例二的轮询命中率约 29.6%、带溢出回到约 79.9% 且 P95 降到 680 ms；平衡点是平均 6.6138 QPS，即平均负载率 13.8%。

两份样例都是**合成设定，不是真机数据**。

在自己的服务上做一次多实例评估：起三个实例，跑三种路由策略，量出缓存命中率和负载不均衡度的取舍曲线，替换这份样例，并核对溢出比例那一项声明的值和实际跑出来的是否一致。
