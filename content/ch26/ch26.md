# 第 26 章 容量、显存与成本模型：这套系统该配多少，花多少钱

## 学习目标

读完这一章，你应该能回答三个问题：

1. 给定业务量，需要多少张卡？
2. 一次调用到底花了多少钱，一个用户一个月花多少钱？
3. 成本降不下来时，该动哪个数字？

跟着做完，你会得到一份容量与成本模型：从业务指标推到卡数和月度账单，并能回答“流量涨三倍要加多少钱”。

## 26.1 一个答不上来的问题

前五篇都在让系统更快。现在换一个人来问：

```text
"明年用户量翻五倍，预算要报多少？"
```

这个问题答不上来，前面所有的优化都很难被认可。因为它不是技术问题的延伸，而是另一条推理链：从业务指标推到资源，再推到钱。

**而这条链的每一环，前面几章其实都已经建好了：**

```text
业务指标  →  请求速率        第 6 章的 workload 描述
请求速率  →  token 速率      第 12 章和第 24 章的上下文账
token 速率 → 卡数            第 16 章的容量表 + 第 19 章的 Goodput
卡数      →  月度成本        第 22 章的成本对比
```

这一章要做的是把这四段接起来，并且让它能回答假设性问题。

## 26.2 从业务指标推到 token 速率

第一段是把产品口径翻译成技术口径。

产品方通常给的是这类数字：日活、月活、人均使用次数。要转成请求速率，中间有几处容易出错。

```text
日活 50 万
人均每天对话 3.2 轮
  → 日请求量 160 万
  → 平均 QPS = 160万 / 86400 ≈ 18.5
```

**但平均 QPS 不能用来做容量规划。** 三个原因：

**一、流量不均匀。** 日内波峰通常是平均值的 2 到 4 倍。容量按峰值配，账单也按峰值配置出。**峰谷比是这一步最重要的输入**，它直接决定了自建方案里有多少卡在波谷期闲着。

**二、一次“对话”不等于一次请求。** RAG 链路一次对话可能包含改写、检索、生成三次模型调用；Agent 任务一次可能是几十次。第 24 章那条纪律在这里生效：**按任务算账，不按调用算账。**

**三、真正决定资源的是 token 速率，不是请求速率。** 一个 8000 token 的请求和一个 300 token 的请求对系统的压力差几十倍。

所以要推到 token 速率：

```text
峰值 QPS = 18.5 × 3（峰谷比）× 2.4（每轮对话的模型调用数） ≈ 133
峰值输入 token/s = 133 × 平均输入长度 2600 ≈ 346000
峰值输出 token/s = 133 × 平均输出长度 220 ≈ 29000
```

**输入和输出要分开算**，因为它们消耗的是不同资源：输入吃 Prefill 的算力，输出吃 Decode 的带宽和时间。计价上也通常不同价。

## 26.3 从 token 速率推到卡数

第二段用第 16 章和第 19 章的结果。

单卡能承载多少，取决于两个约束，取更紧的那个：

```text
显存约束   单卡并发上限 = KV 预算 ÷ 每条请求的平均 KV 占用    （第 16 章）
吞吐约束   单卡 token 吞吐 = 批量 × 每 token 时间的倒数        （第 19 章的 Goodput 峰值）
```

**两个约束哪个更紧，取决于负载形状。**

```text
长输入短输出（RAG、文档问答）   通常显存先满
短输入长输出（创作、代码生成）   通常吞吐先满
```

以第 16 章那个例子继续：单卡安全并发 150 条，Goodput 峰值对应的输出吞吐是每秒 1400 token。

```text
按输出吞吐   29000 ÷ 1400 ≈ 21 张
按并发       峰值在途请求数 = QPS × 平均请求时长 = 133 × 4.2 ≈ 559
             559 ÷ 150 ≈ 4 张
```

取更紧的：21 张。

**这里用到了 Little's Law**，第 6 章讲过：

> **Little's Law**：稳定系统中，平均在途请求数 = 到达速率 × 平均停留时间。它把“每秒多少请求”和“同时有多少请求”联系起来，是从 QPS 推并发的唯一正确方式。

注意平均请求时长要用实测值，且要用高峰期的实测值。高峰期排队更久，时长更长，在途数更多，这是一个会自我放大的量。

**最后要加余量。** 21 张是刚好够的数字，实际配置要考虑：

```text
滚动升级期间的容量下降    第 22 章那条，逐个替换时剩下的要扛全部流量
单实例故障的冗余         至少能挂一台
流量预测的误差           业务估算通常偏乐观
```

常见的做法是在计算值上加 30% 到 50%。**这个余量不是浪费，它是前面几章那些“不要跑在饱和区”结论的落地。** 第 20 章说过，90% 利用率下多 5% 流量延迟就可能翻倍。

## 26.4 单位成本：三种口径

第三段是钱。而“一次调用多少钱”这个问题有三种算法，用错了会差很多。

**口径一：按 token 计价（用 API 时）**

```text
单次成本 = 输入 token × 输入单价 + 输出 token × 输出单价
```

直接、准确，且和用量严格成正比。这是用 API 时唯一需要的口径。

**口径二：按卡时摊销（自建时）**

```text
单卡月成本 = 硬件摊销 + 电费 + 机房 + 运维分摊
单位 token 成本 = 单卡月成本 × 卡数 ÷ 月度总 token 数
```

**这个口径有一个陷阱：分母用的是实际用量，而分子按峰值配置。** 峰谷比越大，实际的单位成本越高于“满载时的单位成本”。

```text
满载单位成本      按卡 24 小时跑满算，看起来很便宜
实际单位成本      按实际用量算，峰谷比 3 时约是前者的 2 到 3 倍
```

**报告里要给出的是后者。** 用满载成本去和 API 报价比，是自建成本被低估的最常见原因。

**口径三：按业务单位计价**

```text
每用户每月成本 = 月度总成本 ÷ 月活用户数
每任务成本     = 月度总成本 ÷ 月度任务数
```

**这是唯一能和业务对话的口径。** “每 token 0.8 分”对产品方没有意义，“每个活跃用户每月 2.4 元”才有。

而且它能直接回答一个关键问题：**这个成本和产品的单用户收入相比是多少。** 比例失衡时，该做的可能不是继续优化性能，而是改产品形态。

## 26.5 成本模型要能做假设分析

一份只能算出当前成本的模型，用处有限。真正有用的是能回答假设。

把前面三段串起来，就得到一个可以调参数的模型：

```text
输入：日活、人均次数、峰谷比、每次的调用数、输入输出长度
中间：峰值 QPS、token 速率、单卡容量、卡数
输出：月度成本、单位成本、每用户成本
```

**几个最值得试的假设：**

**“流量涨三倍”。** 卡数不是线性涨三倍。如果当前跑在低利用率，可能只需要加一倍；如果已经接近饱和，可能要三倍还多，因为要维持同样的延迟余量。

**“上下文砍一半”。** 这个改动会同时影响三处：Prefill 算力降、KV 占用降、并发上限升。第 12 章和第 16 章那两笔账在这里合并，收益通常比直觉大。

**“换成量化版本”。** 第 17 章那两笔账：权重量化改善延迟从而改善吞吐，KV 量化改善并发。但要把质量评测的结论一起带进来。

**“峰谷比从 3 降到 1.5”。** 通过把批量任务调度到波谷期，能显著提高卡的利用率。这不是技术优化，是排班，但对自建成本的影响可能比任何技术优化都大。

**最后这一条常被忽略。** 峰谷比是成本模型里杠杆最大的一个参数，而它通常不在性能工程师的视野里。

## 26.6 哪个数字最值得动

成本降不下来时，按杠杆大小排序：

| 可动的数字 | 杠杆 | 代价 | 归属 |
|---|---|---|---|
| 峰谷比 | 很大 | 需要业务配合调度 | 产品 + 运维 |
| 平均输入长度 | 很大 | 可能损失质量 | 算法 + 性能 |
| 每次任务的调用数 | 很大 | 需要改编排逻辑 | 应用开发 |
| 模型档位（大换小） | 很大 | 质量下降 | 算法 |
| 量化 | 中 | 质量下降 | 性能 |
| 批量与调度参数 | 中 | 延迟抖动 | 性能 |
| 推理引擎优化 | 小到中 | 工程投入 | 性能 |

**杠杆最大的四项都不在性能工程的职责范围内。** 这不是在推卸责任，而是说明一件事：**成本模型的价值在于让这些讨论能基于同一组数字发生。**

没有这份模型，讨论会停留在“能不能再优化一点”；有了它，可以说“把平均上下文从 2600 降到 1800，月成本降 31%，需要算法侧确认质量影响”。

**这一章的真正产出不是一个数字，是一份能让不同角色对话的模型。**

## 26.7 Demo：容量与成本模型

本章 Demo 位于 `code/ch26/capacity_cost.py`，不需要 GPU。

```bash
python3 code/ch26/capacity_cost.py \
  --dau 500000 --sessions-per-user 3.2 \
  --peak-ratio 3.0 --calls-per-session 2.4 \
  --input-tokens 2600 --output-tokens 220 \
  --request-duration 4.2 \
  --gpu-concurrency 150 --gpu-output-tps 1400 \
  --gpu-monthly 12000 --headroom 0.4 \
  --api-input-price 0.0008 --api-output-price 0.002
```

输出：

```text
peak_qps            峰值请求速率
token_rate          峰值输入与输出 token 速率
inflight            按 Little's Law 算出的峰值在途请求数
gpus_by_memory      按显存约束需要的卡数
gpus_by_throughput  按吞吐约束需要的卡数
gpus_required       取更紧者，含余量
selfhost_monthly    自建月成本
api_monthly         API 月成本
cost_per_token      实际单位 token 成本（非满载口径）
cost_per_user       每活跃用户月成本
utilization         按实际用量算的平均利用率
```

假设分析模式：

```bash
python3 code/ch26/capacity_cost.py whatif \
  --base base-model.json \
  --scenario "traffic=3x" \
  --scenario "input_tokens=1800" \
  --scenario "peak_ratio=1.5"
```

每个场景输出卡数、月成本和单位成本的变化，以及相对基线的百分比。

**两条口径上的硬性约束：**

`cost_per_token` 用实际用量做分母，不提供满载口径的数字。想看满载成本要显式加 `--show-saturated`，且输出会带一行警告说明它不能用于和 API 报价对比。`utilization` 必须一同输出，因为它是解释单位成本高低的唯一依据。

**本章的模型尚未用真机数据校准。** GX10 恢复后要做的是：用实测的单卡并发和 Goodput 替换 `--gpu-concurrency` 和 `--gpu-output-tps`，重跑一遍并对比估算偏差。

## 26.8 课堂案例与常见误区

### 案例一：按平均 QPS 报预算，上线当天挂了

团队按日均 QPS 18.5 算出需要 3 张卡，配了 4 张留余量。

上线首日晚高峰，实际 QPS 到了 61，服务直接过载。峰谷比是 3.3，而预算里完全没有体现。

更麻烦的是采购周期要三周，这期间只能靠降级维持。

讨论：峰谷比该从哪里拿？产品方能提供这个数字吗？

### 案例二：自建比 API 便宜，算错在哪

一份对比报告写着：自建单位成本每百万 token 3.2 元，API 是 9 元，自建省 64%。

复核发现自建那个数字是按卡 24 小时满载算的。实际平均利用率只有 27%，真实单位成本是每百万 token 11.9 元，比 API 还贵。

**分子按峰值配置出，分母按实际用量进。** 这两个口径混用，是自建成本被低估的标准做法。

讨论：什么情况下满载成本这个口径才是有意义的？

### 案例三：优化了一年，成本没降

性能团队一年里做了量化、调参、换框架，单次调用的 GPU 时间降了 45%。但月度账单几乎没变。

分析发现同期业务侧发生了两件事：为提升效果把 RAG 的 Top-K 从 5 加到 12，以及新增了一个 Agent 工作流，每个任务平均 11 次调用。

**性能优化的收益被业务侧的用量增长吃掉了**，而这两边从来没有在同一组数字上讨论过。

后来建了成本模型并在季度评审上过，业务侧的每一次改动都要报一次成本影响。

讨论：这个机制怎么落地才不会变成流程负担？

### 两个不写在模型里的误区

误区一：成本优化就是性能优化。

26.6 那张表里杠杆最大的四项都不是性能手段。性能优化能降低单位成本，但用量、上下文长度、调用次数、模型档位这几项的影响通常更大，而它们属于产品和算法。

误区二：算出一个精确的数字就够了。

精确的当前成本用处有限，因为决策总是关于未来的：流量涨了怎么办、改了模型怎么办、砍了上下文能省多少。模型的价值在于能做假设分析，能算准当前值只是它的副产品。

## 本章总结

回到开头的三个问题。

**需要多少张卡？** 分三段推：业务指标推到 token 速率（要乘峰谷比、要按任务算调用数、要把输入输出分开）；token 速率推到单卡容量（显存和吞吐两个约束取更紧的，用 Little's Law 从 QPS 推在途数）；最后加 30% 到 50% 的余量，覆盖滚动升级、故障冗余和预测误差。余量不是浪费，是“不要跑在饱和区”这条结论的落地。哪个约束更紧取决于负载形状：长输入短输出通常显存先满，短输入长输出通常吞吐先满。

**一次调用花多少钱？** 三种口径。按 token 计价适用于 API；按卡时摊销适用于自建，但必须用实际用量做分母，用满载口径去和 API 比是自建成本被低估的最常见原因；按业务单位计价是唯一能和产品对话的口径，而且它能直接回答成本与单用户收入的比例是否失衡。

**该动哪个数字？** 按杠杆排序：峰谷比、平均输入长度、每任务调用数、模型档位，然后才是量化、调参、引擎优化。前四项都不在性能工程的职责内，所以这一章真正的产出不是一个数字，而是一份能让产品、算法、性能三方基于同一组数字讨论的模型。没有它，讨论会停在“能不能再优化一点”。

下一章处理卡数确定之后的事：这些实例怎么组织、怎么扩缩容，以及弹性为什么救不了突发流量。

### 本章 Checklist

- [ ] 知道业务的峰谷比，且这个数字有实测依据。
- [ ] 能从日活推到峰值 token 速率，中间每一步的乘数都能解释。
- [ ] 知道当前负载是显存先满还是吞吐先满。
- [ ] 用 Little's Law 算过峰值在途请求数，用的是高峰期的实测时长。
- [ ] 卡数里包含了滚动升级、故障冗余和预测误差三项余量。
- [ ] 单位 token 成本用实际用量做分母，不是满载口径。
- [ ] 知道每活跃用户每月的成本，以及它和单用户收入的比例。
- [ ] 成本模型能做假设分析，至少跑过流量、上下文、峰谷比三个场景。

## 课后练习

1. 从产品方拿到日活和人均使用次数，推到峰值 QPS，写清每一步的乘数和依据。
2. 统计一次业务操作平均触发多少次模型调用，和产品方的直觉估计对比。
3. 分别算出按显存和按吞吐需要的卡数，说明当前哪个约束更紧。
4. 用 Little's Law 算峰值在途数，用高峰期和低峰期两组时长各算一次，对比差异。
5. 算出实际单位 token 成本和满载单位成本，说明两者差几倍。
6. 算出每活跃用户每月成本，和产品的单用户收入对比。
7. 跑三个假设场景：流量三倍、上下文减半、峰谷比降到 1.5，对比各自的成本变化。
8. 按 26.6 那张表给你的业务排一次杠杆顺序，标出每一项的责任方。
