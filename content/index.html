课程方法论

先系统，后技术；先分析，后优化

不按 FlashAttention、PagedAttention、Speculative Decoding 这样的技术清单组织，也不按 TTFT、TPOT 这样的单一指标组织，而是以"推理系统"本身为主线——建立一套可迁移的思维方式，面对任何模型、框架和硬件都能用。

理解系统→ 理解瓶颈→ 定位瓶颈→ 优化方案→ 验证收益
01

先系统，后技术

先建立推理系统和请求生命周期的整体认知，再进入具体技术专题，技术点不会和系统位置脱节。

02

先分析，后优化

不从"有哪些优化技术"出发，而从"当前系统的瓶颈是什么"出发——完成 Benchmark、Profiling 和根因分析后，才选择优化方案。

03

指标必谈 Trade-off

TTFT、TPOT、TPS、显存、成本并非相互独立，不把某项技术简单归到单一指标，而是分析它对多个指标的共同影响。

04

优化必须验证

每项优化都要通过可重复 Benchmark 验证，不能仅凭原理或单次运行结果判断收益。

先睹为快

一次请求，到底经历了什么

在拆开每一个技术点之前，先用一个真实场景把整条链路走一遍。

场景：一个基于 vLLM 部署的 Llama-3.1-8B-Instruct 聊天服务，用户输入 "帮我写一段快速排序的 Python 代码，并解释一下时间复杂度。"
  1. 01请求到达服务入口，如果系统正忙，会先排一小会儿队 —— 这就是 Queue。
  2. 02系统把这句话整段"读"一遍，这个阶段叫 Prefill，读完后用户看到第一个字冒出来。
  3. 03模型进入逐字生成，叫 Decode——为避免重复计算前文，中间结果被缓存为 KV Cache，显存不够时会成为重要瓶颈。
  4. 04文字一个接一个蹦出来，而不是等全部写完再显示——这叫流式输出。
  5. 05代码和解释生成完毕，模型输出停止信号，请求结束。
但这只是一个用户 —— 需求继续往上走
  1. 06同一时间，成百上千个像这样的用户一起在问问题呢？——请求要排队、要打包成批次处理，GPU 要一直保持忙碌、不能让谁被落下，这是 Serving 优化要回答的问题。
  2. 07这个服务要在生产环境里长期扛住这样的流量，还要压低每一次回答的成本呢？——要决定用多少张卡、怎么分摊负载、什么时候该加机器，这是 Scalability 优化要回答的问题。
"等多久看到第一个字""字与字蹦出来快不快""这台机器同时能服务多少用户""一千个并发要花多少钱"——这些问题背后，分别对应具体的性能指标和具体的软硬件瓶颈。整门课，就是把从单个请求到生产集群的每一层需求拆开，讲清楚原理、讲清楚怎么测、讲清楚怎么优化。

适合谁学

面向想把系统真正跑快的人

  • 独立完成一次完整的 LLM 推理性能优化：从 Benchmark、Profiling 到根因定位、方案选择和收益验证
  • 看懂从 GPU 硬件、KV Cache 到推理引擎、Serving 编排的完整链路，而不是只会调框架参数
  • 面对新模型、新框架、新硬件，也能用同一套分析方法找到瓶颈，而不是死记一份优化清单
  • 理解 Prefill-Decode 分离、MoE 专家并行等 2026 年生产级架构背后的系统原理
  • 产出一份优化前后的对比报告，讲清楚收益、代价和适用边界

先修要求

  • Python 与 Linux 基础操作
  • 理解 Transformer 的基本结构（Attention、自回归生成）
  • 具备基础的软件工程能力
