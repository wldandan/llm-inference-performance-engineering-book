# 第 2 章 真实请求生命周期：请求在系统里如何流动

## 学习目标

读完这一章，你应该能回答三个问题：

1. 一条请求在服务端经历了什么？需要记录哪些事件，各阶段的起止点在哪里，取消和失败又会走上哪条路？
2. 客户端观测与服务端观测为什么不能直接混算？
3. 拿到一份只覆盖部分阶段的报告，怎样判断哪些结论仍然成立、哪些必须放弃？

跟着做完，你会得到一张标出各阶段起止事件的请求时间线，以及一份给每个字段标明证据等级的生命周期报告。

## 2.1 首包等待偏大，时间花在了哪一段

第 1 章的流式调用让“多久看到第一个字”成了一个能测的量。现在假设这个量偏大，用户抱怨要等很久才看到回应。你该去改什么？

请求可能在队列里等了太久，可能模型处理这段 prompt 本身就慢，也可能首 token 早已生成、时间全耗在了返回路上。三种原因对应三种完全不同的修法，而客户端记录的那几个时刻无法区分它们：它们都发生在请求发出与首个分片到达之间，被压缩成了同一段时间。

要拆开这段时间，得知道请求在服务端内部经历了什么。本章先用一套与框架无关的事件和时间点描述这段经历，再在一条带数字的时间线上把它拆开，最后从真实 vLLM 请求上采集证据，并为每个结论标明证据来自哪里。

![推理请求生命周期与关键时间点](figures/fig02-01_request_lifecycle_timeline.svg)

图2-1：推理请求生命周期与关键时间点。

动手之前，先说清楚“请求”指的是哪一层。业务侧说“一次请求”，推理引擎听到的可能完全不是一回事。

> **Agent**（智能体）：由模型自己决定下一步做什么的程序。它把一个任务拆成若干步，每一步可能调用模型、也可能调用外部工具，拿到结果再决定下一步。
> 对性能工程的意义只有一条：用户眼里的“一次任务”，在模型服务这一侧是好几次请求，而且次数事先不知道。第 24 章专门算这笔账。

以 Agent 为例，用户只提交了一次“帮我比较三家供应商”的任务。Agent 可能先调用一次 LLM 制订计划，随后并行调用三个工具，再调用一次 LLM 汇总结果。业务系统看到一个 Task，模型服务看到两次或更多 LLM Call；如果中间发生重试，同一个 Call 还可能对应多条 Inference Request。

```text
Business Task
  -> LLM Call 1
       -> Inference Request 1
  -> Tool Calls
  -> LLM Call 2
       -> Inference Request 2
       -> Retry Request 3
```

本章研究的对象是最内层的 Inference Request。它有独立的请求 ID、输入 token、生成参数、队列状态、输出 token 和终态。第 24 章再把多条请求拼回 Agent 的端到端任务。

![业务任务、LLM 调用与推理请求](figures/fig02-02_task_call_request.svg)

图2-2：业务任务、LLM 调用与推理请求是三个不同层级。

模型为什么要分成两种方式处理输入和输出，放在第 3 章；这些事件由哪个组件记录，放在第 4 章；TTFT、TPOT 和分位数的正式定义，放在第 5 章。抢占、Chunked Prefill、远程 KV 传输和 Prefill/Decode 分离会让请求路径变得不连续，本章只讲没有这些情况的主路径。

## 2.2 用归一化状态描述生命周期

不同框架给状态起的名字并不一致。本书先使用一套归一化事件，避免把概念绑死在某个版本的内部类上：

```text
request_received
  -> queued
  -> scheduled
  -> first_token
  -> token ...
  -> last_token
  -> finished
```

这条主路径表达的是：服务收到请求；请求完成入口处理并进入等待队列；调度器给它分配执行机会；模型产出首 token；后续 token 持续产生；最后一个 token 生成；响应发送完毕，请求结束。

从 `scheduled` 到 `last_token`，模型做的是两种不同的工作。拿到请求后，模型先一次读完整段 prompt，这段计算叫 Prefill；读完之后，再一个接一个地写出输出 token，这段叫 Decode。本章只需要知道它们在时间线上的先后和边界。

`cancelled` 和 `failed` 是旁路终态。它们可以发生在排队、Prefill 或 Decode 期间。实际系统还可能出现 waiting for grammar、waiting for remote KV、preempted 等更细状态。例如 vLLM 当前的 RequestStatus 明确区分 WAITING、RUNNING、PREEMPTED 以及若干特殊等待状态；这些都可以映射回本章的归一化模型，而不必照搬名称。[vLLM RequestStatus](https://docs.vllm.ai/en/stable/api/vllm/v1/request/)

这里有四个容易混用的概念：

| 概念 | 表达什么 | 例子 |
|---|---|---|
| Event | 某件事发生的瞬间 | `queued`、`first_token` |
| State | 请求在一段时间内所处的状态 | WAITING、RUNNING、FINISHED |
| Phase | 两个边界事件之间的逻辑区间 | Queue、Prefill、Decode |
| Duration | 在确定时钟和边界后计算出的时间 | `t2 - t1` |

Event 是点，Phase 是区间，State 描述区间内的处境，Duration 才是数字。先把前三者定义清楚，再计算时间；否则，同一个“Prefill 30 ms”可能分别指模型计算、首次调度到首 token，或者客户端等待首包，三者不是同一件事。

## 2.3 给生命周期建立时间坐标

状态说清楚后，再给每个关键事件记一个时间戳。一次流式请求上值得记录的事件，按发生顺序是：

| 事件 | 记录方 | 时间点 | 说明 |
|---|---|---|---|
| `request_sent` | 客户端 | | 客户端发出请求 |
| `request_received` | 服务端 | `t0` | 服务端接收到请求 |
| `queued` | 服务端 | `t1` | 请求进入引擎等待队列 |
| `scheduled` | 服务端 | `t2` | 请求首次获得执行机会 |
| `first_token` | 服务端 | `t3` | 引擎生成第一个输出 token |
| `first_chunk_sent` | 服务端 | | 服务端第一次把流式数据写出 |
| `first_chunk_received` | 客户端 | | 客户端读到第一个内容分片 |
| `last_token` | 服务端 | `t4` | 引擎生成最后一个输出 token |
| `finished` | 服务端 | `t5` | 响应发送和收尾工作结束 |
| `stream_done` | 客户端 | | 客户端收到 `[DONE]` |

服务端的六个时间点可以得到一组阶段时间：

```text
Admission                = t1 - t0
Queue                    = t2 - t1
Scheduled-to-First-Token = t3 - t2
Decode                   = t4 - t3
Response Tail            = t5 - t4
End-to-End               = t5 - t0
```

`t3 - t2` 这一段常被直接称作 Prefill，但它除了 prompt 计算，还包含取 logits、采样和组装输出对象。除非引擎明确告诉你埋点位置，否则应使用 `Scheduled-to-First-Token` 这个按边界命名的写法。它只声明“从首次调度到首 token 生成”，不声称这段时间全都花在 Prefill 上。

表里没有编号的四个事件不参与上面的减法。`first_chunk_sent` 在服务端，但多数引擎并不记录它；另外三个在客户端，和服务端时间点不在同一个时钟域。这组相减有一个前提：参与计算的时间点来自同一个时钟域，或者已经经过可靠的时钟对齐。客户端的 `request_sent` 使用客户端时钟，服务端的 `first_token` 使用服务端时钟，不能把两个原始时间戳直接相减。即使两台机器都启用了 NTP，也应把跨机差值视为近似值，并保留同步误差。

> **NTP**（Network Time Protocol）：网络时间协议，让多台机器的系统时钟保持一致。
> 它能把偏差压到毫秒级，但不消除偏差，所以跨机时间戳相减始终只是近似值。

单进程测量持续时间时，优先使用单调时钟。它只关心经过了多久，不受系统时间回拨影响。需要把多个进程、多个服务拼成 Trace 时，再同时保留墙钟时间、Trace ID、Span 关系和时钟同步信息。这样既能排序单个进程内的事件，也能解释跨服务路径，而不是制造一个看起来精确、实际边界不成立的数字。

这张表是生命周期的概念模型，不代表 OpenAI-compatible API 会返回全部时间戳。某些引擎把 tokenization 算进 arrival 到 scheduled，某些系统把首 token 的采样放在 Prefill 尾部，还有些监控只能看到客户端分片。第 5 章会把这件事写成一份十个字段的指标合同，其中直接对应本节的是三项：Boundary（这个数由谁记录）、Window（起止是哪两个事件）、Clock（用哪种时钟、跨机怎么对齐）。

![Queue 与首次调度的边界](figures/fig02-04_queue_schedule_boundary.svg)

图2-4：只有明确 queued 和 scheduled 两个时间点，Queue 才有可复核的边界。

## 2.4 Request Received 与 Queue：计算开始前发生了什么

`request_received` 表示服务边界已经接到请求，但请求还不一定进入引擎队列。协议解析、鉴权、参数校验、tokenization、路由和准入控制都可能发生在这一段。它们是否计入 Admission，取决于观测点放在哪里。

`queued` 表示请求已经进入某个等待执行的队列。排队不是“系统什么都没做”，而是在等待一组条件满足：有可用执行预算、有足够的 KV Cache 空间、调度策略允许、请求没有超时或被取消。

> **KV Cache**：模型为已经处理过的每个 token 保存的中间结果，生成后面的 token 时直接复用，不必重算。
> 它随请求的 token 数增长并占用显存，所以一条请求能不能开始执行，要看还有没有地方放它的 KV Cache。它从哪里来，第 3 章讲。

`scheduled` 是第一次真正获得引擎执行机会。这里要强调“第一次”：请求后面仍可能经历很多轮调度，甚至被抢占后重新排队。生命周期里的 Queue 通常关注首次排队到首次调度；要研究重复等待，需要额外事件，不能靠一个 queue 时间猜出来。

第 4 章会区分 Gateway、Router、Admission Queue 和 Engine Scheduler。当前只需记住，`request_received -> queued -> scheduled` 发生在模型产出 token 之前，其中任何一段变长，用户都会觉得首包变慢。

## 2.5 Scheduled、Prefill 与 First Token

请求第一次被调度后，模型要先处理输入上下文，也就是 Prefill：一次读完整段 prompt，并把后面生成要复用的中间结果存进 KV Cache。

Prefill 的结束边界容易说错。完成最后一个 prompt token 的计算，还不等于第一个输出 token 已经产生：服务端还要取 logits、执行采样，才选出这个 token。本章把 `first_token` 定义为服务端在这里生成首 token，它与客户端看到第一段正文之间还隔着一段路，2.7 再展开。

```text
scheduled
  -> prompt compute
  -> KV Cache created
  -> logits
  -> sampling
  -> first_token generated
```

如果启用了 Prefix Cache 或 Chunked Prefill，这条路径会出现缓存命中或多轮 Prefill，但请求仍要经过“输入尚未处理完”到“首 token 已生成”的状态变化。Prefill 的工作机制与优化放在第 11～14 章。

![Prefill 与首 token 的边界](figures/fig02-05_prefill_first_token.svg)

图2-5：Prefill 连接首次调度与服务端首 token，客户端首个分片还要经过返回链路。

## 2.6 Decode 是一串引擎步，不是一段黑盒时间

首 token 之后，请求进入 Decode。每一步写出一个新 token，这个循环一直持续到 EOS、stop condition、长度上限、取消或错误出现为止。

```text
first_token
  -> decode step 1 -> token 2
  -> decode step 2 -> token 3
  -> ...
  -> last_token
```

引擎并不是一条请求从头算到尾再换下一条。它按轮推进，每一轮叫一次 engine iteration，一轮里可以同时推进多条请求。于是一条请求会跨越许多 iteration，一个 iteration 又同时属于多条请求。这形成两条正交的时间线：

| 时间线 | 回答的问题 | 单位 |
|---|---|---|
| 请求时间线 | 这条请求经历了什么 | 一条请求的 t0 到 t5 |
| 引擎时间线 | 这一轮 GPU 推进了哪些请求 | 一次 engine iteration |

两条线不能互相换算。同一个 Decode step 在请求时间线上是“我的第 7 个 token”，在引擎时间线上是“这一轮同时推进的 12 条请求之一”。看请求时间线，你只知道自己等了多久；看引擎时间线，才知道这段时间 GPU 在为谁工作。

这个区分后面会反复用到：GPU 利用率高而单条请求慢，通常就是两条线给出了不同的答案，引擎一直在忙，只是没怎么轮到你。第 20 章分析调度和 Batch 效率时，两条线都要摆出来。

Decode 也不一定连续。显存紧张时，引擎可能先暂停某条请求、让出它占的资源，稍后再恢复，这叫抢占。请求会从 RUNNING 进入 PREEMPTED，之后重新等待调度。此时 `first_token -> last_token` 仍然是用户经历的 Decode 区间，但其中包含了暂停。要解释暂停原因，必须再看 Scheduler 和 KV Cache 事件。

## 2.7 Streaming：token、输出对象和网络分片不是一一对应

第 1 章那次调用，客户端数到 254 个分片，服务端说写了 256 个 token。两者不能互相换算。模型产出 token 后，服务端还要解码文本、组装协议对象、写入网络，这几步都可能改变分片与 token 的对应关系。服务端可能攒够几个 token 才发一个分片，网络栈可能把多次写入合并，投机解码还可能一次接受多个 token。分片数是网络行为的结果，token 数是模型行为的结果。

所以 2.3 的表在首 token 之后放了三个紧挨着的事件：`first_token`（引擎产出首 token）、`first_chunk_sent`（服务端写出首个分片）、`first_chunk_received`（客户端读到首个分片）。第 1 章能观测到的只有最后一个。

这三个事件之间的两段路，客户端都量不出来。首 token 生成到首个分片写出这一段全在服务端内部，多数引擎不记录 `first_chunk_sent`；分片写出到客户端读到这一段跨了两个时钟域，两个原始时间戳不能直接相减。所以客户端手上只有一个数：从请求发出到收到第一个分片。

**这个数不能当成服务端 TTFT。** 它把排队、Prefill、采样、解码成文本、组装协议对象、写入网络和网络传输全都包在里面，而这些段各占多少，客户端拆不开。但它本身是一个合法的量，第 5 章会给 TTFT 这一族量各自划定作用域，那时它有一个正式名字：客户端口径的 TTFT。在那之前，本章一律写它的全称“客户端首个内容分片等待”，不用缩写。

反过来的误用同样常见：拿客户端这个数减去服务端报的首 token 等待，把差值叫“网络耗时”。差值里还含着解码、组装和写出，2.9 会用一张表说明为什么它只能叫“服务端首 token 之外的部分”。

## 2.8 Finished、Cancelled、Failed 都必须收口

正常结束只是终态之一：

- `finished`：生成满足 EOS、stop condition 或长度上限，响应正常完成。
- `cancelled`：客户端断开、业务主动取消或超时策略终止请求。
- `failed`：参数、模型执行、Worker、网络或其他环节发生错误。

三条路径都必须进入资源清理。服务需要停止后续计算，释放或复用 KV Cache block，清理调度状态，关闭流式响应，并写入 finish reason、错误和 usage。否则一次已取消的请求仍可能继续消耗 GPU；状态泄漏积累后，服务看起来像是“越跑并发越低”。

不要把清理等同于立即释放所有缓存。Prefix Cache、会话缓存或远程 KV 可能按策略保留。生命周期要求的是请求所有权结束后，资源进入明确的新所有者或可回收状态，而不是留成无法解释的占用。

## 2.9 一条请求的时间线，能拆到哪一步

前面几节定义的是事件和公式。现在拿一份事件记录，把服务端这一侧真的算一遍，同时看清哪一段算不出来。`code/ch02/sample-events.jsonl` 里有三条请求的服务端事件，时间戳是为演示公式构造的合成数据，不是 GPU 实测：

```text
req-ok      request_received 0  queued 2    scheduled 12   first_token 42   last_token 92   finished 97
req-cancel  request_received 120  queued 122  scheduled 140  cancelled 148
req-failed  request_received 200  queued 202  scheduled 205  first_token 230  failed 250
```

用离线分析器把它们换算成阶段时长：

```bash
python3 code/ch02/lifecycle_trace.py \
  --input code/ch02/sample-events.jsonl
```

输出整理成表（单位 ms）：

| 请求 | 终态 | Admission | Queue | Scheduled-to-First-Token | Decode | Response Tail | End-to-End |
|---|---|---:|---:|---:|---:|---:|---:|
| req-ok | finished | 2 | 10 | 30 | 50 | 5 | 97 |
| req-cancel | cancelled | 2 | 18 | `null` | `null` | `null` | 28 |
| req-failed | failed | 2 | 3 | 25 | `null` | `null` | 50 |

先看正常请求。服务端从收到请求到生成首 token 用了 42 ms，拆开是入口 2 ms、排队 10 ms、首次调度到首 token 30 ms。这段等待里最大的一块在模型那一侧，而不在队列里。

再看另外两条。`req-cancel` 在 140 ms 被调度，148 ms 就被取消了，还没有生成首 token，所以 Scheduled-to-First-Token 算不出来，后面的 Decode 和 Response Tail 更无从谈起。`req-failed` 生成了首 token，但在 Decode 途中失败，没有 `last_token`，Decode 同样算不出来。

这些格子写的是 `null`，不是 `0`。`0 ms` 表示两个都观测到了的边界恰好重合；`null` 表示缺了一个边界，这段时间根本无法计算。把 `req-cancel` 的 Decode 写成 0，读者会以为它“Decode 瞬间完成”，而事实是它从来没有进入 Decode。

回到本章开头的三种怀疑，现在可以逐个对上时间线：

| 开头怀疑的原因 | 看哪一段 | req-ok 的结果 |
|---|---|---|
| 请求在进入引擎前或队列里等了太久 | Admission 与 Queue（`t1 - t0`、`t2 - t1`） | 2 ms 与 10 ms |
| 模型处理这段 prompt 慢 | Scheduled-to-First-Token（`t3 - t2`） | 30 ms |
| 首 token 早已生成，时间耗在返回路上 | `first_token` 到 `first_chunk_sent`，再到 `first_chunk_received` | 样例没有这两个事件，不可得 |

第三行最值得注意。要判断返回路径，至少需要服务端写出首个分片的时刻，以及一个能和服务端对齐的客户端时钟。缺了它们，客户端首包等待减去服务端 42 ms 得到的差值，只能叫“服务端首 token 之外的部分”，不能直接命名为网络耗时。

## 2.10 Demo：为真实 vLLM 请求生成证据报告

合成时间线让你看清了公式，但它不是任何真实服务的记录。本章主 Demo 位于 `code/ch02/capture_lifecycle.py`，它要求真实 vLLM 服务运行在 GPU 上，完成一条流式请求，同时采集三类来源的证据：客户端事件、vLLM 返回的请求级指标、请求前后 `/metrics` 的差值。

> **Prometheus**：一种按时间抓取指标的监控系统。vLLM 在 `/metrics` 接口上以 Prometheus 格式暴露计数器和直方图，例如累计处理了多少请求、各段耗时落在哪些区间。
> 这些数字是整个服务的累计值，不带请求 ID，所以只能用前后两次读数的差，看这段时间里服务整体发生了什么。

不同来源的数字，能支撑的结论不一样。为了避免“有数字就算证据”，本书把报告字段分成四级。这张表是本篇那条观测边界的执行形式：等级写的就是这个字段由谁记录、因此能管到哪里。

| 证据等级 | 典型字段 | 可以回答的问题 | 不能越过的边界 |
|---|---|---|---|
| 客户端直接观测 | 请求发出、响应头、首个内容分片、`[DONE]` | 用户侧何时看到数据，流是否正常结束 | 不能单独拆出 Queue 或 Prefill |
| 请求级服务端直接观测 | request ID、Queue、首次调度到首 token、Generation | 当前请求的服务端阶段时长 | 受所用 vLLM 版本的指标定义约束 |
| 服务端聚合直接观测 | `/metrics` 前后快照及差值 | 统计窗口内服务发生了什么变化 | 并发时不能归属于单条请求 |
| 推导、推断或不可得 | 客户端时长差、缺失阶段边界 | 明确哪些结论经过计算，哪些仍未知 | 未知不能填成 `0`，推断不能改写成实测 |

“直接观测”也不等于“可以回答所有问题”。客户端直接观测到首个分片，只能闭合客户端首包窗口；Prometheus 直接观测到某个直方图计数增加，只能证明统计窗口内发生了变化。证据是否足够，取决于它的作用域是否与问题一致。

先用请求级指标启动服务：

```bash
vllm serve /home/admin/models/Qwen2.5-0.5B-Instruct \
  --served-model-name Qwen/Qwen2.5-0.5B-Instruct \
  --enable-per-request-metrics \
  --host 0.0.0.0 \
  --port 8000
```

再运行采集脚本：

```bash
python3 code/ch02/capture_lifecycle.py \
  --base-url http://127.0.0.1:8000/v1 \
  --model Qwen/Qwen2.5-0.5B-Instruct \
  --model-revision local-snapshot \
  --server-command "vllm serve ... --enable-per-request-metrics" \
  --require-server-metrics \
  --require-complete-evidence \
  --output content/ch02/evidence/gx10-real-lifecycle-report.json
```

请求级指标里有一个名字容易误导的字段：`time_to_first_token_ms`。按课程所用 vLLM 版本的请求级指标说明，它从调度开始算到首个输出 token，所以报告把它存进 `scheduled_to_first_token`，而不是第 5 章那个从用户发出请求算起的 TTFT。换了 vLLM 版本，要先核对这个字段的起点再用。vLLM 暴露的服务端指标边界也可能随版本以及抢占行为变化，本 Demo 固定无抢占主路径，并记录实际 vLLM 版本；遇到抢占时只报告“当前 Demo 不支持归因”，不强行套用一次 `scheduled` 的公式。[vLLM Per-Request Metrics](https://docs.vllm.ai/en/latest/features/per_request_metrics/)

拿到报告后，按下面的顺序阅读：

1. 先确认 request ID、模型、模型 revision、vLLM 版本和启动命令，避免分析错服务或错版本；
2. 检查客户端是否收到正文、usage 和 `[DONE]`，确认请求是否正常收口；
3. 只在同一时钟域内排序事件和计算持续时间；
4. 把请求级服务端指标映射到 Queue、Scheduled-to-First-Token 和 Generation，不擅自改名；
5. 把 Prometheus 差值保留为聚合旁证，并记录采集窗口内是否存在其他流量；
6. 对每个阶段写出证据等级，缺失边界标为 `unavailable`。

Queue、首次调度到首 token 和 Generation 三个请求级时长都有效，并且 request ID、usage 与环境元数据齐全时，`acceptance.status` 才会是 `complete`。一份合格报告不是要求所有阶段都有数字，而是要求每个结论都能追溯到来源。真实接口没有暴露 `request_received` 或 `first_token` 的精确时间戳时，报告应坦白缺失。

完整命令、字段说明和边界见 [Demo README](../../code/ch02/README.md)。

### 本章预期看到什么

本章目前还没有保存通过完整验收的 GX10 真机报告，因此正文不提供示例数值。真机执行后，`acceptance.status` 应为 `complete`，`phase_evidence` 对每个阶段标明证据等级，Prometheus 差值被标成聚合证据，而不是只输出一列毫秒数。如果状态是 `incomplete`，先看缺失字段，不要从已有数字继续推演完整生命周期。客户端路径成功、服务端字段缺失，说明“调用成功”和“证据完整”是两种不同的验收结果。

## 2.11 课堂案例与常见误区

### 案例一：第 1 章那份报告能回答什么

完整生命周期报告还没生成，手头已有的真实数据是[第 1.8 节那份 GX10 客户端流式报告](../ch01/evidence/gx10-streaming-client-report.json)：NVIDIA GB10 上对 `Qwen/Qwen2.5-0.5B-Instruct` 的一次流式请求，首个内容分片 29.64 ms，254 个分片，usage 报告 30 个输入 token、256 个输出 token，总时长 2345.26 ms。

把它放进 2.10 的四级证据表，逐项判断：

| 报告里的内容 | 证据等级 | 能回答 | 不能回答 |
|---|---|---|---|
| 首个内容分片 29.64 ms、`[DONE]` 2345.26 ms | 客户端直接观测 | 用户侧何时看到首段正文，流是否正常结束 | Queue、Prefill、Decode 各占多久 |
| `prompt_tokens=30`、`output_tokens=256` | 客户端直接观测（usage 由服务端填写） | 这次请求读了多少、写了多少 | 这些 token 在服务端各花了多长时间 |
| `stream_chunks=254` | 客户端直接观测 | 客户端收到多少个非空内容分片 | 254 个分片对应多少次模型执行 |
| 请求级 Queue、首次调度到首 token | 不可得 | 无 | 29.64 ms 里有多少是排队，有多少是模型计算 |

结论是：这份报告属于第一级证据，能回答客户端问题，回答不了本章开头那三种怀疑中的任何一种。它也缺少 `vllm_version`，可以证明链路和客户端观测，不能作为可复现的记录。

讨论：如果只允许在第 1 章的脚本上补一个服务端来源的字段，补哪一个最能缩小 29.64 ms 的归因范围？补上之后，哪一段仍然不可得？

### 案例二：服务端两段都没变，用户却说首包变慢了

一个团队在 vLLM 前面加了一层带鉴权和审计的网关。上线后，客户端记录的首包等待明显变长。值班工程师拉出 vLLM 请求级指标，Queue 和首次调度到首 token 与上线前几乎一样，于是回复“推理服务没有变化”。

这句回复只对了一半。请求级指标覆盖的是 vLLM 收到请求之后、到生成首 token 为止的几段。新网关里的鉴权和审计发生在 vLLM 的 `request_received` 之前，首 token 之后的写出和转发也要经过这层网关，两者都在这组指标的边界之外。服务端指标没变，说明变慢的部分不在它们量得到的范围内，不说明整条链路没有变化。

讨论：要把新增的时间定位到网关里，最先应该补记哪两个事件？在补上之前，报告里这段差值应该怎样命名？

### 两个不会出现在时间线上的误区

误区一：请求级 Queue 很短，说明服务没有排队问题。

这个 Queue 只量引擎等待队列里、从首次入队到首次调度的那一段。请求在网关限流、外置准入队列里等的时间发生在它之前，被抢占后重新等待的时间发生在它之后，都不会算进来。Queue 短只能说明“进了引擎之后很快被调度”，要判断整体有没有排队，还得看引擎之外的队列有没有自己的事件。

误区二：非流式请求没有首 token，不需要看 Scheduled-to-First-Token。

非流式请求在服务端同样先 Prefill 再 Decode，同样有 `first_token` 这个时刻，只是服务端把整段结果攒到最后才发，客户端看不到它。服务端的阶段划分对两种请求完全一样，差别只在返回路径：非流式请求没有 `first_chunk_sent`，Response Tail 里装的是整段响应的发送。

## 本章总结

回到开头的三个问题。

**一条请求在服务端经历了什么？** 六个关键时间点：接收、入队、首次调度、首 token、末 token 和结束。它们把 Admission、Queue、Scheduled-to-First-Token、Decode、Response Tail 和 End-to-End 分开，也让取消和失败各有位置。在合成样例里，正常请求 42 ms 的服务端首 token 等待拆成 2、10、30 ms 三段，开头怀疑的“排队”和“模型处理 prompt”由此各有了数字。三类终态都必须走到资源清理，否则一次已取消的请求仍会占着 GPU。阶段的名字由两个边界事件决定，不由你以为那段时间在做什么决定。

**客户端观测与服务端观测为什么不能直接混算？** 因为它们量的不是同一段东西，也不在同一个时钟域。首 token 已生成，不代表首个分片已经到达用户，中间还隔着解码、组装和网络；想判断返回路径，需要服务端写出分片的事件和对齐的时钟，缺了它们，差值不能叫网络耗时。同一段时间放在请求时间线和引擎时间线上，答案同样不一样：前者告诉你自己等了多久，后者告诉你这段时间 GPU 在为谁工作。

**一份只覆盖部分阶段的报告，哪些结论仍然成立？** 先看它属于哪一级证据。客户端直接观测只能闭合客户端窗口，请求级指标才能归属到这条请求，聚合差值在有并发时谁也不属于。第 1 章那份真实报告属于第一级，回答得了用户何时看到正文，回答不了排队和计算各占多久。真实系统很少把所有时间点暴露出来，所以这些时间点给出的是问题的结构，不是答案。缺失的阶段就写 `unavailable` 或 `null`，它和 `0 ms` 是两回事：前者表示没有证据，后者表示两个已观测的边界重合。

下一章进入 Transformer 生成机制，解释 Prefill 为什么一次处理整段输入、Decode 为什么逐 token 推进，以及 KV Cache 如何连接两个阶段。第 4 章再回答 Gateway、Scheduler、Worker 和 Runtime 分别负责什么。
