# 实验环境与版本

正文里凡是说“默认”“当前版本”“较新的版本”，指的都是下面这张表里的版本。换一个版本，那些说法要按第二节的清单重新核对一遍，不要照搬。

## 一、本书的实测环境

真机记录有两份，同一句 prompt、同一个模型，机器和 vLLM 版本都不同。

| 项 | 第一台 | 第二台 |
|---|---|---|
| 记录 | `content/ch01/evidence/gx10-streaming-client-report.json` | `content/ch01/evidence/rtx3080ti-streaming-client-report.json` |
| 主机名 | `gx10` | `autodl-container-s268v0c3ns-6954074f` |
| GPU | NVIDIA GB10 | NVIDIA GeForce RTX 3080 Ti |
| 驱动 | 580.159.03 | 595.71.05 |
| Python | 3.12.3 | 3.12.3 |
| vLLM | 报告里是空的 | 0.10.2 |
| 模型 | Qwen/Qwen2.5-0.5B-Instruct | Qwen/Qwen2.5-0.5B-Instruct |
| 正文用它讲什么 | 第 0、1、2、5 章和附录 A 的全部时间数字 | 1.9 的分片计数、3.2 的 prompt_tokens 构成 |

**两份不能混着比。** 第一台那次是暖机之后的调用，首个内容分片 29.64 ms；第二台那次是服务起来后的第一条请求，454.28 ms 里有很大一部分是冷启动，不是 Prefill 慢（第 7 章讲为什么 Warmup 不能省）。所以时间一律以第一台为准，第二台只用来说明两件和时间无关的事。

**同一句话，两台报的 prompt_tokens 不一样**，第一台 30，第二台 40。差额来自 Chat Template：第二台那一版在请求没带 system 消息时会补一句默认系统提示，第一台那一版没有。3.2 拿这件事说明 prompt_tokens 跟着模板走，不是模型的固有属性。

第一台那份报告的 `vllm_version` 是空的，1.11 节拿它当“报告缺字段”的反面例子，所以保留原样不补写。采集脚本后来补上了这一项，第二台那份就有。

其余章节的数字分两类：合成设定（正文和 evidence 里都标了 `synthetic`），以及按 Part 3 开篇那张参考模型与参考卡表算出来的。两类都不依赖上面这张表的版本。

## 二、版本相关的说法

下面每一条都随 vLLM 版本变化，本书按上表第二台那个 0.10.2 核的。升版本时照这张单子逐条重核，核完把日期写在后面。

| 说法 | 在哪一节 | 核的办法 |
|---|---|---|
| `gpu_memory_utilization` 默认 0.9，引擎一次性划走这块显存 | 1.1、16.6 第 1 步 | 看 `vllm serve --help`，或读启动日志里报的 KV 池容量 |
| 抢占默认挑最晚进来的那条，且只由显存不足触发 | 16.5、20.2 | 读调度器日志里的抢占记录；开了优先级调度时结论不同 |
| 抢占的处理方式是重算还是换出 | 16.5 | 看启动参数与启动日志；V1 之后只有重算 |
| Chunked Prefill 是否默认开启 | 13.5、14.4 第 4 轮、20.3 | 看 `--enable-chunked-prefill` 的默认值；默认开着时，对照轮要先显式关掉 |
| 请求级指标 `time_to_first_token_ms` 的口径 | 2.7、5.8 | 读该版本的指标文档，确认它是否含排队 |
| `/metrics` 上各指标的名字 | 2.10、8.2、20.8 | 直接抓一次 `/metrics` 比对 |
| 响应头是否回带 `X-Request-Id` | 8.3、8.7 | 需要 `--enable-request-id-headers`，默认关闭 |
| 在线服务下输出是否逐 token 可复现 | 14.4 的护栏 | 读该版本关于可复现性的说明；默认不保证 |

**判断方法**：一条说法如果删掉版本前提之后还成立，它就不该进这张表；要靠“这一版是这样”才成立的，一定要进来。
