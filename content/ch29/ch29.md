# 第 29 章 Performance Review 与上线检查：上不上，谁来拍板

## 学习目标

读完这一章，你应该能回答三个问题：

1. 一次上线评审要看哪些材料，缺哪一份就不该放行？
2. 出问题时怎么回滚，以及哪些东西回滚不掉？
3. 性能工作怎么从一次次救火变成持续运转的机制？

跟着做完，你会得到一份上线检查清单和一套评审模板，以及一份回滚预案。

## 29.1 最后一道关口

前面二十八章的产出到这里汇总：

```text
第 7 章    可复现的 Baseline
第 10 章   根因报告
第 19 章   Decode 优化报告
第 25 章   端到端优化报告与防回退断言
第 26 章   容量与成本模型
第 27 章   扩缩容配置
第 28 章   门禁结果
```

**评审要做的不是重新审一遍这些内容，而是检查它们是否齐全、是否互相一致、以及有没有人对结果负责。**

一个反复出现的失败模式是：每一份材料单看都没问题，合起来却对不上。容量模型按平均上下文 2600 算，而新版本的 prompt 模板加长到了 3400；门禁在批量 32 下通过，而生产配置是 64。

**评审的价值就在这些接缝处。**

## 29.2 上线检查清单

一次上线要过九项。每一项都指向前面某一章。

**一、SLO 定义清楚且可测。**

```text
指标、分位、阈值、统计窗口、适用范围
```

第 4 章讲过口径的重要性。**“TTFT 要快”不是 SLO，“P95 TTFT < 1500 ms，按 5 分钟窗口统计，不含被拒绝的请求”才是。**

**二、Baseline 在当前配置下重跑过。** 不是三个月前那份。第 28 章讲过环境指纹，评审时要核对指纹是否与生产一致。

**三、容量核算过，且和实际配置一致。** 第 26 章那个模型，输入参数要用最新的实际值。**特别要核对上下文长度**，它是最容易和模型里的假设脱节的一项。

**四、门禁通过，或有记录在案的豁免。** 第 28 章那套。豁免要有原因和审批人。

**五、监控就绪。** 上线后要看的每一个指标，现在就要能看到。

```text
必须有   Running 占比、排队时间、P95 ITL、抢占计数、拒绝率
容易漏   Prefix Cache 命中率、各实例的负载分布、取消生效率
```

**上线后才发现某个指标没采集，是最常见的准备不足。**

**六、流量治理配置齐全。** 第 21 章那五项：准入、超时、取消、重试、背压。**尤其要确认准入是开启的**，它是突发流量唯一的防线。

**七、冷启动时间已知。** 第 27 章那个数字。它决定了出问题时恢复要多久，也决定了扩容能不能指望上。

**八、回滚预案明确且演练过。** 下一节展开。

**九、有人对结果负责。** 不是“团队负责”，是具体的人，且这个人有权在指标异常时执行回滚。

**九项里最容易被跳过的是第五和第八项**，因为它们在上线前看起来不产生价值。而它们恰恰是出问题时唯一有用的两项。

## 29.3 回滚：哪些回得去，哪些回不去

回滚预案不能只写“切回旧版本”。要先分清哪些东西能回滚。

**能回滚的：**

```text
服务版本        重新部署旧镜像
配置参数        改回旧值
路由权重        切回旧实例组
模型版本        加载旧权重
```

**回不去或很难回去的：**

```text
数据写入        新版本已经写进数据库或向量库的内容
缓存状态        回滚后旧版本的 Prefix Cache 是冷的，性能会暂时更差
索引重建        知识库如果被重新切分和向量化，切回要很久
下游依赖        如果新版本触发了外部系统的状态变化
用户可见的输出  已经发给用户的回答收不回来
```

**第二项是 LLM 场景特有的，也最容易被忽略。** 回滚之后旧版本的实例缓存是空的，TTFT 会比回滚前更差一段时间。**如果回滚的原因就是性能问题，回滚瞬间可能看起来更糟**，这会让人怀疑回滚决定本身。

预案里要写清这一点，并给出预期的恢复时间。

**回滚要演练。** 没演练过的预案在真正需要时会发现：权限不对、旧镜像已被清理、配置文件找不到、执行的人不在。**演练的目标是量出从决定到生效需要多久**，这个数字要写进预案。

**回滚的触发条件要事先定好**，不能临场判断：

```text
自动回滚   错误率 > X%，持续 Y 分钟
           P95 延迟 > SLO 的 1.5 倍，持续 Y 分钟
人工决策   质量指标异常
           成本异常上升
```

**把自动回滚的条件定死，是为了避免在压力下犹豫。**

## 29.4 上线后的观察窗口

上线不是终点。要明确一段观察期，以及这期间看什么。

```text
前 10 分钟   错误率、P95 延迟、Running 占比
             看的是有没有立刻崩

前 2 小时    缓存命中率的恢复曲线、抢占计数、显存占用
             看的是稳态下的资源状况

前 24 小时   跨越一个完整的日内波峰，看峰值表现
             这是唯一能验证容量核算的窗口

前 7 天      成本、质量指标、长尾任务
             这些需要足够样本才看得出来
```

**24 小时那一档最重要**，因为容量核算的所有假设只有在真实波峰下才能被验证。很多问题在低峰期完全不显现。

**观察期内不要叠加其他变更。** 这是第 14 章那条“一次只改一项”在生产场景下的版本。上线当天又改了别的配置，出问题时无从判断是谁的原因。

## 29.5 让性能工作持续运转

最后一个问题：怎么让这些不退化成一次性的项目。

**四件需要固定下来的事：**

**一、定期重跑 Baseline。** 不是等出问题才跑。月度或跟随重要变更。第 28 章那套门禁已经覆盖了变更触发的部分，定期重跑覆盖的是环境自然漂移。

**二、成本与容量的定期复核。** 第 26 章那份模型的输入参数会变：上下文长度、调用次数、峰谷比。季度复核一次，并把差异归因。

**三、变更要报性能影响。** 第 26 章案例三那个机制：业务侧改 Top-K、加一个 Agent 步骤，都要报一次成本和延迟影响。**关键是这个评估要基于同一份模型**，否则会变成各说各话。

**四、事故要产出可自动化的检查。** 每次性能事故的复盘，产出不应该只是一份文档，而应该包含至少一条能加进第 28 章那套断言的检查。**没有转化成断言的教训，下次还会重犯。**

**四件事的共同点是它们都需要一个固定的节奏**，而不是靠个人记得。评审机制的作用就是提供这个节奏。

## 29.6 评审模板

一份可用的评审材料包含六块：

```text
1. 变更说明     改了什么，为什么改，影响范围
2. 性能证据     Baseline 对比、门禁结果、关键指标变化
3. 容量核算     卡数、余量、和成本模型的一致性检查
4. 风险清单     已知风险、缓解措施、未覆盖的场景
5. 回滚预案     触发条件、执行步骤、预期耗时、不可回滚项
6. 责任与观察   负责人、观察窗口、各阶段看什么
```

**第四块里的“未覆盖的场景”是最有价值的一项**，也是最容易被省略的。第 14 章那条边界纪律在这里的形式是：这次验证了什么，以及没验证什么。

```text
已验证   批量 32、上下文 P95 3800、单区三实例
未验证   批量 64 的表现、跨区部署、上下文超过 8000 的请求
```

**写出未验证项不是暴露不足，是让风险变得可管理。** 上线后如果真在这些场景出问题，至少知道从哪里查。

## 29.7 Demo：上线检查与评审

本章 Demo 位于 `code/ch29/release_check.py`。

```bash
python3 code/ch29/release_check.py \
  --baseline baseline.json \
  --gate-result gate-result.json \
  --capacity-model capacity.json \
  --runtime-config prod-config.json \
  --monitoring-spec monitoring.json \
  --rollback-plan rollback.md \
  --output review-packet.md
```

它做两件事。

**第一，逐项检查九项清单**，缺项直接标红：

```text
slo             定义完整性检查
baseline        环境指纹与生产配置的一致性
capacity        模型输入参数与实际配置的一致性
gate            门禁结果与豁免记录
monitoring      必需指标的可用性探测
traffic_policy  五项治理配置的存在性
cold_start      冷启动时间是否已记录
rollback        预案是否包含触发条件、耗时和不可回滚项
owner           责任人是否指定
```

**第二，做一致性交叉检查**，这是它最有价值的部分：

```text
容量模型的上下文长度  vs  当前 prompt 模板的实际长度
门禁运行时的批量      vs  生产配置的批量
Baseline 的框架版本   vs  待发布镜像的框架版本
容量模型的实例数      vs  扩缩容配置的最小实例数
SLO 阈值              vs  门禁绝对阈值
```

**这五项就是 29.1 说的那些接缝。** 每一项不一致都对应着一个真实发生过的事故形态。

输出是一份 Markdown 评审材料，按 29.6 那六块组织，缺失项显式标出而不是留空。

**本章的检查尚未在真实发布流程中跑过。** GX10 恢复后要做的是：走一次完整的发布，用这个脚本生成评审材料，并演练一次回滚量出耗时。

## 29.8 课堂案例与常见误区

### 案例一：所有材料都通过，上线当晚过载

评审很顺利：Baseline 达标、门禁通过、容量核算说 8 张卡够用。

上线当晚波峰时过载。复盘发现容量模型用的平均上下文是 2600，而这次上线的新版本把 system prompt 从 800 加长到了 1600，平均上下文实际是 3400。按第 16 章那张表，并发上限降了约四分之一。

**每一份材料单看都没错，接缝处对不上。** 后来加了交叉检查，这类问题在评审时就能发现。

讨论：还有哪些接缝值得加进自动检查？

### 案例二：回滚之后更慢了

新版本上线后 P95 TTFT 上升，值班决定回滚。回滚完成后 TTFT 不降反升，比新版本还高 40%。

原因是回滚后旧版本实例全部重启，Prefix Cache 清空。团队以为回滚失败，又切回新版本，结果缓存又清一次，来回折腾了四十分钟。

如果预案里写清了“回滚后有约 20 分钟的缓存恢复期，期间 TTFT 会更高”，就不会有这次反复。

讨论：有什么办法能让回滚不清空缓存？

### 案例三：监控上线后才补

上线后发现 P95 ITL 抖动很大，但没有 ITL 的分布指标，只有 TPOT 平均值。加指标、发版、等数据，花了两天才定位到是批量配置的问题。

而这两天里用户一直在受影响。

**上线前十分钟能做完的事，出问题后要花两天。**

讨论：监控就绪该怎么验证，才不会流于形式？

### 两个不写在清单里的误区

误区一：评审是走流程。

评审真正的价值在交叉检查，而这件事没有任何一个单独的角色会做：性能工程师看性能证据、运维看容量、开发看变更说明，接缝处正好是所有人的盲区。案例一那个事故就发生在这里。

误区二：回滚是万能的兜底。

有相当一部分东西回滚不掉：已写入的数据、已发给用户的输出、被重建的索引。而且回滚本身有代价，缓存清空会让性能短期更差。把回滚当成“反正能退回去”的安全感，会让人在上线前少做检查。

## 本章总结

回到开头的三个问题。

**评审要看什么？** 九项：SLO 定义、当前配置下的 Baseline、和实际配置一致的容量核算、门禁结果或豁免、监控就绪、五项流量治理配置、已知的冷启动时间、演练过的回滚预案、明确的责任人。但评审的价值不在重审每一份材料，而在交叉检查那些接缝：容量模型的上下文长度对不对得上新的 prompt 模板、门禁跑的批量是不是生产批量、Baseline 的框架版本是不是待发布的版本。每一项不一致都对应一种真实的事故形态。

**回滚能回什么？** 服务版本、配置、路由、模型权重能回；已写入的数据、已发给用户的输出、被重建的索引回不去。还有一项 LLM 特有的：回滚后缓存是冷的，如果回滚的原因本身是性能问题，回滚瞬间会看起来更糟，预案里必须写明这一点和预期恢复时间。回滚要演练，目标是量出从决定到生效需要多久；触发条件要事先定死，避免在压力下犹豫。

**怎么持续运转？** 四件事要有固定节奏：定期重跑 Baseline 覆盖环境的自然漂移、季度复核容量与成本模型的输入参数、业务变更要基于同一份模型报性能影响、每次事故复盘要产出至少一条能加进自动断言的检查。最后这条最关键，没有转化成断言的教训下次还会重犯。

Part 6 到此结束。下一篇只有一章，把前二十九章的全部内容用在一个完整的项目上。

## 课后练习

1. 把你的 SLO 补全成含指标、分位、阈值、窗口和适用范围的完整定义。
2. 核对容量模型的上下文长度假设和当前 prompt 模板的实际长度，记录差异。
3. 列出上线后要看的所有指标，逐个验证现在就能查到。
4. 写一份回滚预案，包含触发条件、步骤、预期耗时和不可回滚项。
5. 演练一次回滚，量出从决定到生效的实际耗时。
6. 测量一次实例重启后 Prefix Cache 命中率的恢复曲线，写进预案。
7. 做一遍 29.7 那五项交叉检查，记录发现的不一致。
8. 找一次过去的性能事故，把它的教训写成一条可自动执行的断言。
