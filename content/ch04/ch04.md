# 第 4 章 LLM Serving 架构：谁负责请求链路的哪一段

## 学习目标

读完这一章，你应该能回答三个问题：

1. 一个请求从客户端到 GPU 要经过哪些逻辑组件？每个组件接收什么、决定什么、输出什么？
2. Router、Admission 和 Engine Scheduler 都在“调度”，为什么不能合并成一个？
3. 架构图上的框和真实的进程、Pod、设备是什么关系？怎样把一张图变成可检查的契约？

跟着做完，你会得到一张标出组件职责与第 2 章时间点的架构图，以及一份能被检查器验证的架构契约。

## 4.1 架构图不是方框清单，而是一组责任契约

只画 `Client -> LLM -> GPU`，足以说明系统大致在做什么，却不足以排障。用户看到超时，团队仍然不知道请求有没有通过鉴权、是否选中了正确实例、有没有进入引擎队列，还是已经下发到 GPU 后执行失败。

第 2 章描述了请求经历哪些状态，第 3 章解释了模型怎样生成 token。本章换一个视角，回答这些状态和计算由谁接收、决定、执行和观测。

单实例 vLLM 的最小逻辑请求路径可以写成：

```text
Client
  -> Gateway
  -> Engine Scheduler
  -> Worker
  -> Runtime
  -> Accelerator
```

当系统出现多副本选择、全局配额或分级队列时，再扩展为：

```text
Client -> Gateway -> Router -> Admission / Queue
       -> Engine Scheduler -> Worker -> Runtime -> Accelerator
```

![LLM 推理系统全局架构](figures/fig04-01_inference_system_architecture.svg)

图4-1：LLM 推理系统的请求路径、响应路径与主要逻辑组件。

返回路径通常更短：计算结果经 Runtime 和 Worker 回到负责协议输出的 Gateway，再流向 Client。Router 不必为每个 token 重新选择实例，Admission 也不会再次做准入决定。真实系统还可能经过 Output Processor、Detokenizer、消息总线或代理，其中 Detokenizer 负责把 token ID 转回文本。这些扩展仍要回答三个问题：接收什么，决定什么，输出什么。

本书把图中的框称为“逻辑组件”。逻辑组件不等于进程，也不等于 Pod。Gateway 与 Router 可以在同一个 API Server 进程里；Admission 与 Engine Scheduler 可以同处一个引擎进程；Worker 与 Runtime 也常在同一个 Worker 进程里。反过来，一个逻辑 Worker 也可能展开为跨多张 GPU 的 Worker Group。单实例服务里没有独立部署的 Router 或全局 Admission，也不代表这些能力完全不存在：它仍然要校验请求、决定何时执行，只是没有必要为它们单独起一个服务。

因此，读架构图时要同时看两层：

- 逻辑层回答责任归属。
- 部署层回答进程、节点、设备和故障边界。

> **变更频率与故障域（failure domain）**：变更频率是一个部分多久被改一次，故障域是它出问题时会波及多大范围。
> 这两件事跟着责任走，不跟着进程走。Gateway 的协议和鉴权逻辑可能一周改几次，挂掉主要影响还没进来的新请求；Worker 持有的权重和执行状态可能一个季度不动，挂掉会丢掉正在生成的全部请求。把它们塞进同一个进程不会改变这个差别，所以分析必须按责任分层。

先把逻辑责任画清楚，再讨论如何部署。否则一换框架或一拆进程，整张系统地图就失效了。

## 4.2 Client 与 Gateway：业务语义进入模型服务的边界

Client 可能是网页、后端服务、IDE 插件、Agent Orchestrator、评测脚本，也可能是另一个模型。它负责构造业务请求、生成或传递 Trace ID、处理超时与取消，并消费普通响应或流式响应。

Gateway 是服务端入口。常见职责包括：

- 终止 HTTP、gRPC 或内部 RPC 协议；
- 完成鉴权、租户识别、配额和基础限流；
- 校验模型名、生成参数、上下文大小和流式选项；
- 把外部协议转换成内部请求对象；
- 组装错误响应、usage 和流式分片；
- 记录入口时间、状态码、Trace ID 和客户端断开事件。

Gateway 不负责模型 forward，也不应决定每个 engine iteration 运行哪些 token。它拥有的是协议与租户边界。这里的失败通常表现为请求还没进入引擎：认证失败、参数非法、上下文超限、配额耗尽或连接已经断开。

单实例服务不一定发生目标选择，因此不需要虚构独立 Router。多副本场景中，路由有时直接写在 Gateway 进程里，但分析时仍应区分两种责任：协议处理回答“请求是否合法”，路由回答“合法请求去哪里”。

## 4.3 Router、Admission 与 Engine Scheduler：三种不同的流量决策

LLM Serving 里常把所有排队和选择都叫 scheduling。这个词太宽，一旦出问题，团队很容易同时去改负载均衡、并发上限和 batch 参数。多实例系统可以分成三层；单实例最小路径通常只显式保留 Engine Scheduler，Router 和全局 Admission 属于按需增加的角色。

| 逻辑组件 | 核心问题 | 主要输入 | 主要输出 |
|---|---|---|---|
| Router | 请求去哪个后端？ | 模型、版本、租户、实例健康、负载、缓存信息 | 目标 replica、worker group 或 engine |
| Admission / Queue | 请求现在能不能进去？ | 配额、优先级、延迟目标、队列长度、并发上限 | 接收、排队、拒绝或降级决定 |
| Engine Scheduler | 下一轮执行谁？ | 等待/运行请求、token 预算、KV Cache、Worker 状态 | iteration plan、batch metadata、抢占或等待决定 |

Router 做的是放置选择。最简单的实现是轮询；更复杂的实现会看实例负载、会话亲和性、模型版本或 Prefix Cache 重叠。它不应越过引擎边界，直接构造下一轮 token batch。

Admission 管的是全局流量预算。它可以把交互式请求和离线任务放进不同队列，也可以在过载时快速拒绝，避免所有请求进入引擎后一起超时。这里的 Queue 可能位于 Gateway、Router 后面或引擎入口，具体位置由实现决定，架构图必须标明。

Engine Scheduler 已经处于某个推理实例内部。它知道请求当前处于 Prefill 还是 Decode、还剩多少 token 预算、KV Cache 是否足够、哪些 Worker 能执行。它输出的是执行计划，不是业务响应。

“下一轮执行谁”听起来抽象，放到几条请求上就具体了。设想某一轮开始时，请求 B 和 C 已经在 Decode，请求 A 刚从队列里被选中。Engine Scheduler 可以把三者放进同一轮：A 这一轮要处理整段 prompt，B 和 C 各只处理一个新 token。这一轮结束，A 产出首 token，下一轮它也转入 Decode；如果这时新请求 D 到达，而 KV Cache 还放得下，D 又可以在下一轮加入。批次里的成员每一轮都可能变化，这就是第 2 章说的“一条请求跨越许多 iteration，一个 iteration 同时推进多条请求”。怎样排才高效，是第 20 章的主题。

三者可以部署在同一进程，但不能丢掉职责边界。Router 选错实例、Admission 允许过多流量、Engine Scheduler 形成低效 batch，会产生完全不同的证据和修复路径。

还有一个后果要现在就记住：**同一条请求可能在这三处各等一次。** 在 Router 前面等一次放置决策，在 Admission 队列里等一次准入，进了引擎再等一次被选进 batch。用户感到的“还没开口”是这三段加起来，而监控面板上常常只有最后一段有数字。三层都在同一进程里时，三段时间会被记在同一个字段上，看起来就只有一段。所以排障时要先问这个数字覆盖了三段里的哪几段，第 5 章给延迟分预算时会把它们分开列。

## 4.4 Worker、Runtime 与 Accelerator：计划如何变成模型计算

Engine Scheduler 产生执行计划后，Worker 才把计划变成一次实际模型执行。

Worker 是模型执行单元。它通常持有或管理模型权重、请求执行状态、KV Cache 句柄、并行通信上下文和 Model Runner。单卡部署中，一个 Worker 常绑定一张 GPU；多 GPU 部署中，多个 Worker 可以组成 Tensor Parallel 或 Pipeline Parallel Group。具体并行方式放在多 GPU 与 NCCL 附录中。

Runtime 位于 Worker 与硬件之间。它把模型操作转换成框架算子、编译后的 engine、CUDA、ROCm 或 Metal 调用、kernel 或 graph。PyTorch eager、CUDA Graph、TensorRT engine 和 ggml backend 都属于不同形态的 Runtime 路径。Runtime 决定“怎么执行”，但不理解租户为什么具有更高优先级。

Accelerator 是执行张量计算并承载设备内存的硬件。本书主要以 GPU 为例，但同样的逻辑边界可以映射到 CPU、NPU、TPU 或其他加速器。硬件会暴露计算、容量、带宽和通信约束，却不会理解 HTTP request ID 或业务对延迟的承诺。

| 组件 | 拥有的核心信息 | 产出 |
|---|---|---|
| Worker | 模型与请求执行状态 | Model Runner 调用、token 结果、状态更新 |
| Runtime | 算子、engine、kernel 与设备执行配置 | 硬件调用、logits、采样结果、运行时事件 |
| Accelerator | 张量、权重、KV Cache、工作区 | 计算结果、设备内存变化、硬件计数器 |

“GPU 利用率高”只说明硬件正在忙，不能证明 Router、Queue 或 Scheduler 的架构是健康的。同样，“Worker 正常”也不能排除 Runtime kernel 或设备内存问题。组件边界的意义，就是让一句模糊判断可以继续往下拆。

![Worker、Runtime 与 Accelerator 分层](figures/fig04-04_worker_runtime_accelerator.svg)

图4-4：Worker 持有模型执行状态，Runtime 组织执行路径，Accelerator 承担计算和设备内存压力。

## 4.5 三类状态：谁拥有，谁消费，谁负责回收

推理服务同时管理三类状态：

| 状态类型 | 典型内容 | 主要拥有者 | 主要消费者 | 谁负责回收 |
|---|---|---|---|---|
| 请求状态 | prompt、参数、Trace ID、生成进度、取消、终态 | Gateway / Engine | Router、Scheduler、Worker、Client | 引擎写入终态，Gateway 关闭响应并记录 finish reason |
| 执行状态 | batch metadata、模型配置、采样状态、通信上下文 | Scheduler / Worker / Runtime | Worker、Runtime、Output Processor | 这一轮结束即丢弃，由 Scheduler 与 Worker 各自清理 |
| 资源状态 | 队列槽位、KV block、设备内存、Worker 健康 | Admission / Scheduler / Worker | Router、Scheduler、控制面 | Scheduler 释放队列槽位，Worker 归还 KV block 与设备内存 |

第三列和第四列决定谁能做决定，最后一列决定请求结束后这些东西会不会留下来。“主要拥有者”不代表其他组件没有副本。例如 Gateway 记录外部 request ID，引擎内部可能再生成 request handle；Router 持有 Worker 负载快照，权威状态却可能来自 Worker 或遥测系统。真正重要的是说明哪份状态可以做决定，哪份状态只是缓存或观测副本。

取消传播最能暴露所有权问题。Client 断开连接后，Gateway 要识别取消；引擎要把请求从等待或运行集合中移除；Worker 要停止后续执行；KV Cache 要释放、复用或转交给明确策略。只在 HTTP 层返回“已取消”，GPU 上的请求却继续 Decode，说明架构契约没有闭合。

这也解释了为什么第 2 章的 `finished`、`cancelled`、`failed` 不能只由一个组件自说自话。终态需要跨组件传播，并最终完成状态与资源收口。

## 4.6 规模化以后，变的是部署，不变的是责任

最小服务可以把 Gateway、Scheduler、Worker 和 Runtime 放在一台机器上。流量上升后，系统通常沿着下面的方向演变：

1. API 与引擎分离，让入口的 CPU 工作和模型执行分别扩展。
2. 同一模型部署多个 Replica，由 Router 选择目标实例。
3. 多个模型或版本共享平台，由控制面负责发布、回滚、配额和容量。
4. Prefill 与 Decode 使用不同的 Worker 池，Router 还要协调 KV 状态放在哪里。

每一步都引入了新的流量。除了承载请求、token、取消和错误的请求流量，还有管理版本、实例和发布状态的控制命令，以及日志、指标和 Trace 这类遥测数据。三者不是同一种流量，画架构图时要用不同语义的连线区分开。

复杂度不会凭空消失。多副本提高容量，也引入负载偏斜和缓存局部性；多模型提高资源复用，也带来冷启动和隔离问题；平台化统一治理，也扩大控制面和故障域。每次拓扑变化之后，都要重新标出：入口在哪里、谁选实例、谁做准入、谁形成执行计划、状态由谁持有、结果从哪里返回。

![LLM Serving 部署形态](figures/fig04-06_deployment_patterns.svg)

市面上的系统也分布在不同层级上：有的负责服务平台层的发布与扩缩容，有的负责推理服务器层的协议入口和模型实例，有的是直接调度 KV Cache 和执行模型的 LLM 引擎。比较它们之前，先确认是不是在同一层上比较。容量与多副本在第 26、27 章展开，多 GPU 和 Prefill/Decode 分离留在附录。这一段对照的出处是七份官方架构文档，逐条列在 [Demo README](../../code/ch04/README.md) 里。

## 4.7 从架构图走向可观测边界

回到开头那个超时。架构图只有连线、没有观测点，排障时还是会退回猜测。要让它能用来排障，先把第 2 章的时间点放回组件上。

以第 1 章启动的那台单实例 vLLM 为例，一次流式请求依次经过：

1. vLLM 的 OpenAI-compatible API 接收 HTTP 连接，解析参数，套用 Chat Template 并完成 tokenize。它在这里扮演 Gateway，`request_received`（t0）应在这里记录。
2. 请求交给引擎，进入等待队列（t1）。单实例没有独立的 Router 和全局 Admission，排队发生在 Engine Scheduler 管理的队列里。
3. 某一轮，Engine Scheduler 把它选进执行计划（t2），Worker 让 Runtime 在 GPU 上跑完这一轮，其中包括这条请求的 Prefill。
4. 采样得到首个 token（t3），输出处理把它转回文本，再由 API 层写成 SSE 分片发出（`first_chunk_sent`）。
5. 之后每一轮 Decode 产出新 token，直到最后一个（t4）。API 层发出结束分片和 `[DONE]`，引擎释放这条请求的 KV Cache 和调度状态（t5）。

对应关系一建立，第 2 章那些毫秒数就有了归属。2.9 那条正常请求的服务端首 token 等待是 42 ms，拆成三段；现在每一段都能说出是哪个组件在花时间：

```text
t0 → t1   Admission                  2 ms    API 层：协议解析、Chat Template、tokenize
t1 → t2   Queue                     10 ms    Engine Scheduler 管理的等待队列
t2 → t3   Scheduled-to-First-Token  30 ms    Worker + Runtime，在 GPU 上跑完含 Prefill 的那一轮
          服务端首 token 等待        42 ms
```

这四个数就是第 2 章那张表里的数，这里只是把它们从事件对换成了组件。**换一遍之后，同一个 42 ms 指向的是三个不同的修法。** 2 ms 那一段偏长要去看入口进程的 CPU，10 ms 那一段偏长要去看准入和队列长度，30 ms 那一段偏长要去看 prompt 长度和这一轮的批次构成。三者的修法互不相干，而把它们合在一个“首 token 慢”里，三条路都试不出来。

这几个数来自第 2 章的合成样例，换一台机器数值完全不同；但拆成哪三段、每一段归谁，不随机器变化。

有了这张对应关系，“用户看到超时”就能换成一个具体问题：这条请求最后被记录到的是哪个事件，下一个事件应该由哪个组件产生。

| 现象 | 对应第 2 章的时间点 | 首先核对的边界 | 最小证据 |
|---|---|---|---|
| 请求立即失败 | 没有 t0，或刚过 t0 就结束 | Client -> Gateway | Trace ID、协议错误、鉴权与参数校验结果 |
| 请求已接收但长期未执行 | 有 t0、t1，迟迟没有 t2 | Router -> Admission -> Scheduler | 目标实例、准入决定、入队与首次调度事件 |
| 引擎有请求但设备空闲 | 有 t2，迟迟没有 t3 | Scheduler -> Worker -> Runtime | iteration plan、dispatch、kernel launch 事件 |
| 服务端早有首 token，客户端很久才看到首个分片 | 有 t3，`first_chunk_received` 很晚 | Worker -> 输出处理 -> Gateway -> Client | 首分片写出事件、网关与代理日志 |
| GPU 不忙，吞吐却上不去 | t0 到 t1、t3 到首分片写出偏长 | Gateway 与输出处理 | 入口进程 CPU 占用、tokenize 与 detokenize 耗时 |
| 客户端取消后仍在生成 | 客户端已断开，t4 仍在推进 | Client -> Gateway -> Engine -> Worker | 同一 Trace ID 下的取消传播和资源释放事件 |
| 某些副本持续无流量 | 这些副本上从未出现 t0 | Router -> Replica | 实例发现、健康状态、路由选择记录 |

倒数第三行最容易被忽略。模型计算在 GPU 上，但 HTTP 解析、tokenize、把 token 转回文本、组装分片都在 CPU 上完成。入口进程的 CPU 跑满时，GPU 会空着等活，这时去调 batch 参数不会有任何效果。

这些证据现在只用于确认“问题落在哪个组件或交接点”。第 5 章才正式定义 TTFT、TPOT、成功输出和请求速率与分位数；第 7、8、9 章再建立 Benchmark、请求级追踪和 Profiling 工具链。架构定位早于指标归因，但不能替代它。

## 4.8 Demo：检查一份 LLM Serving 架构契约

本章 Demo 位于 `code/ch04/`。它读取一份 JSON 架构说明，检查以下内容：

- Client 到 Accelerator 的请求路径是否完整；
- Accelerator 返回 Client 的响应路径是否完整；
- 所选架构 profile 要求的角色是否齐全；单实例不强制 Router 和 Admission；
- 组件 ID、连线类型和连线端点是否合法；
- 哪些逻辑组件部署在同一进程、服务或设备中；
- Router 与 Engine Scheduler 的职责是否保持分离。

从 Git 仓库根目录运行：


## 4.9 课堂案例与常见误区

### 案例一：还原课程中的真实 vLLM 单实例

课堂主案例直接使用第 1 章跑通、第 2 章继续观测的那个 vLLM 服务，不另造平台拓扑。先画出最小逻辑路径：

```text
客户端（第 1 章的同步与流式调用）
  -> vLLM OpenAI-compatible API
  -> Engine Scheduler
  -> Worker / Runtime
  -> NVIDIA GB10
  -> 同步响应或流式响应
```

再逐个角色写出它在课程里对应什么，以及这个对应有什么证据：

| 逻辑角色 | 课程实例中的对应物 | 当前证据 |
|---|---|---|
| Client | 第 1 章的同步与流式调用 | 第 1 章客户端流式报告记录了 base URL、模型和流式结果 |
| Gateway | vLLM OpenAI-compatible API | `/v1/models` 与 `/v1/chat/completions` 实际可访问 |
| Router | 不单独出现 | 当前只有一个目标实例，不需要跨副本选择 |
| 全局 Admission | 不单独出现 | 当前实验没有外置配额或分级队列 |
| Engine Scheduler | vLLM 实例内的调度职责 | 由 vLLM 架构说明与请求级 Queue 指标支持，具体实现随版本变化 |
| Worker / Runtime | vLLM 的模型执行路径 | 属于服务内部逻辑，现有客户端报告不直接暴露进程边界 |
| Accelerator | NVIDIA GB10 | 第 1.8 节的 GX10 客户端流式报告直接记录 |

这张表里，真机报告直接证明的只有 API 调用、模型名、GPU 和响应结果；Scheduler、Worker 与 Runtime 的映射来自 vLLM 的架构说明，现有报告没有证明这些角色是否分属不同进程。

讨论：

1. 哪些组件由真机报告直接证明，哪些来自架构说明？
2. 为什么不能根据逻辑架构图推断进程数量？
3. 第 2 章真实生命周期报告完成后，会为哪些组件边界增加证据？

### 案例二：Agent 重试造成的“重复请求”由谁识别

一个 Agent 调用模型超时后自动重试。Gateway 看见两次合法请求，引擎也分别分配了 request handle，于是同一段工作被执行了两遍，账单和 GPU 占用都翻倍。团队讨论要不要让 Engine Scheduler 发现“两个 prompt 一模一样”时直接合并。

这是把业务职责塞进了引擎。Engine Scheduler 只知道 token 和执行预算，它看不出两个相同的 prompt 是一次重试，还是两个用户恰好问了同一个问题。如果业务希望避免重复执行，幂等键应该由 Agent Client 生成，在 Gateway 或更靠前的业务层检查；同时，第一次调用超时后，客户端应该显式取消它，让 4.5 的取消传播把 GPU 上那次执行停下来。

讨论：重试、路由重选和引擎内部抢占都可能让同一段工作再执行一次，三者分别属于哪个组件边界？

### 案例三：企业知识助手要加哪些角色

一家企业的知识助手要支持部门权限、交互式请求与夜间批处理隔离，还要让两个模型版本灰度发布。有人提议把这些逻辑都写进 LLM 引擎的配置里。

按责任拆开看，部门权限属于 Gateway 的租户与鉴权边界，版本选择属于 Router，交互式与批处理的隔离属于 Admission 的分级队列。文档检索属于 RAG 应用链路，也不应塞进 LLM 引擎。模型服务部分可以在单实例路径前加上企业网关、模型路由和准入队列，而这些角色完全可以同处一个进程。

讨论：哪些角色放进同一个进程是合理的？哪一个一旦和引擎放在一起，就会让夜间批处理拖慢白天的交互请求？

### 两个不会画在架构图上的误区

误区一：控制面不在请求热路径，所以不会影响线上流量。

控制面下发的模型版本、实例数量和路由配置会直接改变数据面。一次错误的发布配置，可以让所有请求路由到一个还在加载模型的副本上。区别在于控制面通常不处理每个 token，而不是它与线上行为无关。

误区二：选了一个高性能 LLM Engine，就自动拥有完整生产平台。

Engine 解决的是模型调度与执行。生产系统还需要入口、租户、路由、发布、观测、容量和故障处理，这些不会因为引擎更快而自动出现。反过来，部署平台也不会替代引擎内部的 token 调度。

## 本章总结

回到开头的三个问题。

**一个请求要经过哪些逻辑组件？** 单实例的最小路径是 Client、Gateway、Engine Scheduler、Worker、Runtime、Accelerator。Gateway 拥有协议与租户边界，Engine Scheduler 决定下一轮执行谁，Worker 持有模型与请求执行状态，Runtime 把模型操作转成 kernel 或 graph，Accelerator 只管张量计算和设备内存。每个组件都要能回答同样三件事：接收什么，决定什么，输出什么。多副本选择或全局治理出现后，再增加 Router 和 Admission。把第 2 章的 t0 到 t5 放到这些组件上，开头那个“用户看到超时”就变成了可以查的问题：请求最后停在哪个事件，下一个事件该由谁产生。第 2 章那条 42 ms 的服务端首 token 等待也随之各归其主，2 ms 在入口、10 ms 在引擎队列、30 ms 在 GPU 上那一轮，三段的修法互不相干。

**三种“调度”为什么不能合并？** 因为它们用的状态、决策频率和资源预算都不同。Router 回答“请求去哪个后端”，Admission 回答“现在能不能进去”，Engine Scheduler 回答“下一轮执行谁”，而且每一轮的答案都可能变。三者可以挤在同一个进程里，但一旦出问题，Router 选错实例、Admission 放进太多流量、Scheduler 形成低效 batch，会留下完全不同的证据，也需要完全不同的修法。把它们统称“调度器”，排障时就会三处一起改。

**图上的框和真实进程是什么关系？** 没有固定关系。Gateway 与 Router 可以同处一个 API Server 进程，Worker 与 Runtime 常在同一个 Worker 进程里，而一个逻辑 Worker 也可能展开成跨多张 GPU 的 Worker Group。规模化之后，变的是部署，责任仍然要能逐项找到主人。所以读图要同时看两层：逻辑层回答责任归属，部署层回答进程、节点、设备和故障边界。要让一张图变成可检查的契约，就把组件和连线写成声明，交给 4.8 的检查器验证请求路径、响应路径和角色缺失。但它只验证声明是否自洽，不会替你发现真实进程。
