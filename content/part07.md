# Part 7 综合项目（Capstone）

## 本篇导读

前二十九章是分开讲的。这一篇只有一章，把它们用在同一件事上，要检验的是：**给你一条真实链路和一组 SLO，你能不能自己把顺序排出来、把证据建起来、把结论说清楚。**

## 本篇主线

```text
一个从零开始的服务
  -> 跑起来并说清楚          Ch0-Ch5
  -> 把负载和基准立住        Ch6-Ch7
  -> 让系统可观测            Ch8-Ch10
  -> Prefill 与上下文        Ch11-Ch14
  -> Decode 与显存           Ch15-Ch19
  -> 服务与链路              Ch20-Ch25
  -> 容量、门禁与评审        Ch26-Ch29
```

七个阶段沿着前六篇的顺序走，只把第 2 篇拆成“立基准”和“可观测”两段。每个阶段的产出、验收判据，以及为什么不能大幅打乱，见 30.2；交付物、报告契约和八条自查见 30.1、30.3、30.4，这里不重复。

## 本篇章节关系

| 章节 | 本章完成什么 | 明确不做什么 |
|---|---|---|
| Chapter 30 端到端性能工程项目 | 五项交付物、七个阶段、报告契约、八条自查 | 不引入任何新技术 |

## 本篇靠哪条道理

主线位置：整条主线走一遍，从运行到上线守护。和第 0 章的关系：本篇同时收束第 0 章的三条规律和 0.6 那条方法，而这条道理是第三条规律的终点。第 0 章说“只有有用的产出才算数”，并把性能定义成快、省、好三者之间的一个位置；这一篇要做的就是在一条真实链路上把那个位置挪一次，并说清每一步换走了什么。

前六篇各有一条自己的道理，这一篇只剩一条，而它是前面六条的公约数：**快、省、好三者互相拉扯，任何一次优化都是一笔交换，交换不会因为手法高明而消失。** 本书称之为折中不可消除。

判据只有一句：每一项改动都要写出它换走了什么。批量换走 ITL 的稳定，量化换走一部分质量，前缀亲和换走负载均衡，余量换走成本，准入换走一部分请求。写不出交换的改动只有两种可能，一是真的白拿，二是代价还没被测到。30.4 那八条自查里有五条查的就是第二种。

它在什么地方不成立：白拿确实存在，但都落在“本来就错了”这一类，比如 prompt 拼接顺序反了导致缓存全不命中、`max_model_len` 设成了实际长度的十倍。所以每次优化之前先找一遍这类错误，它们不需要付代价，也就不需要权衡。

## 学完本篇你应该能做到什么

- 独立排出一个性能工程项目的推进顺序，并说明每一步依赖前一步的什么；
- 为每个阶段定出可检验的验收判据，而不是“做完了”；
- 产出一份含九块内容的完整报告，包括边界与未验证项；
- 用八条自查发现自己报告里的可信度缺口；
- 判断一份别人的性能报告是否站得住，指出它缺了什么；
- 在报告里保留失败的和不可分辨的实验，并说清它们的价值；
- 把这套方法迁移到换了模型、换了硬件、换了框架的场景。

## 最后

具体的技术会换代，公式里的常数会变，框架的参数名会改。不会变的是两样：第 0 章那三条规律，写比读贵，批量摊薄搬运而满载拉长等待，只有有用的产出才算数，它们告诉你先怀疑哪里、该数什么；第 0.6 节那条方法，规律只给假设，结论要靠测量。第 30 章最后一段会把它们并在一起，收成四条纪律。
