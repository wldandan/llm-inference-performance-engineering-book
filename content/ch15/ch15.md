# 第 15 章 Decode 工作机制与性能模型：为什么一次只算一个 token 反而更亏

## 学习目标

读完这一章，你应该能回答三个问题：

1. 生成第 100 个 token 和第 1000 个 token，哪个更慢，为什么？
2. 为什么 Decode 阶段 GPU 利用率看起来很低，但也确实快不起来？
3. 同样的模型和硬件，TPOT 大概应该是多少？

跟着做完，你会得到一份 Decode 阶段的估算表：单步耗时的量级、批量对它的影响，以及这个模型在这台卡上的 TPOT 下限。

## 15.1 首包已经出来了，后面为什么还要等

第 11 章到第 14 章解决的是首个 token 之前的事。假设现在 TTFT 已经降到了可接受的范围，用户仍然会抱怨慢。

因为一个 500 token 的回答，首包只占开头那一小段。剩下的 499 个 token 是一个一个吐出来的，每个之间的间隔叠起来，才是用户真正等待的大头。

这段时间由 TPOT 决定，也就是第 5.3 节定义的那个量：首个 token 之后，平均每生成一个输出 token 花的时间。

所以问题变成：这个间隔由什么决定，以及它的下限在哪里。

要回答这个，得先看清 Decode 的一步到底做了什么。而它和 Prefill 的差别，比“一个处理整段、一个处理一个”要大得多。

## 15.2 一步 Decode 做的事

第 3 章讲过 Decode 的机制：拿上一步生成的 token，过一遍模型，得到 logits，采样出下一个 token。这一章关心的是，这一步的时间花在哪里。

拆开来是四件事：

```text
1. 读权重      把模型全部参数从显存读进计算单元
2. 读 KV       把这条请求已有的 KV Cache 读出来做 Attention
3. 算          GEMM 和 Attention 的实际计算
4. 采样 + 调度  从 logits 选 token，引擎准备下一步
```

关键在于**第 1 项和第 3 项的比例**，它和 Prefill 完全相反。

Prefill 一次处理几千个 token，权重读一遍，被几千个 token 共用，所以计算量大、搬运量相对小，是算力受限。

Decode 一次只处理一个 token，权重**还是要完整读一遍**。一个 0.5B 的模型用 FP16 存，权重就是 1 GB 左右，每生成一个 token 就要把这 1 GB 完整过一遍显存带宽。而这一个 token 的实际计算量，只有 Prefill 处理 8000 token 时的八千分之一。

**同样的搬运，八千分之一的计算。** 这里的八千是相对一次 8000 token 的 Prefill 而言，换个输入长度这个倍数就跟着变，但量级上的反差不变。这就是 Decode 变成带宽受限的原因。

这句话值得亲手算一次，因为后面三章的方向都由它决定。第 11 章给过算术强度的定义：一段计算里，运算量与数据搬运量的比值，单位是 FLOP/byte。现在把课程模型代进去。

Qwen2.5-0.5B 有 4.9 亿参数，按 bfloat16 存，权重约 0.98 GB。批量为 1 时写一个 token：

```text
搬运  权重读一遍                    ≈ 0.98 GB
计算  每个参数约 2 次运算，一个 token  ≈ 2 × 4.9 亿 ≈ 0.98 GFLOP
比值  0.98 GFLOP ÷ 0.98 GB          ≈ 1 FLOP/byte
```

这个 1 不是巧合。每个参数在一个 token 上做约 2 次运算（一次乘、一次加），而 bfloat16 每个参数占 2 字节，两者相除恒等于 1，与模型多大无关。

换成 8 位权重，每个参数只占 1 字节，比值就变成 2。**批量为 1 的 Decode，算术强度几乎被钉死在个位数。**

**这里用的是总参数量，而第 11.5 节用的是非嵌入参数量，两处都对，差别值得说一句。** Prefill 的 lm_head 只作用在最后一个位置，几千个 token 里只有一个要过它，所以那一项在 GEMM 里可以忽略；Decode 每一步都要把 lm_head 整张矩阵读一遍算出全词表的 logits，权重绑定时它和嵌入是同一张表，所以这一份字节必须算进来。

顺带一个推论：小模型配大词表时，Decode 的相对开销会明显更高。Qwen2.5-0.5B 的词表占了总参数的 28%，也就是说**每生成一个 token，有近三成的搬运花在最后那一层上**，而这一层在 Prefill 里几乎不算数。

硬件那一侧也有一个比值：峰值算力除以峰值带宽，它是这张卡“搬得动多少、算得完多少”的分界点。以 A100 80GB SXM 为例，稠密口径的 FP16 峰值算力 312 TFLOPS、显存带宽 2039 GB/s（带稀疏的 624 TFLOPS 是另一种口径，两种口径不能混用）[A100 数据手册](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/a100-80gb-datasheet-update-a4-nvidia-1485612-r12-web.pdf)：

```text
分界点  312 × 10^12 FLOPS ÷ 2039 × 10^9 B/s ≈ 153 FLOP/byte
```

不同卡的分界点不一样，但都在几十到几百这个量级。把两个数放在一起，结论就很直接：批量 1 的 Decode 是 1 FLOP/byte，卡的分界点是上百，**差了两个数量级，算力在等数据**。

![算术强度数轴上 Decode 的位置](figures/fig15-01_intensity_axis.svg)

图15-1：算术强度数轴上 Prefill 与 Decode 的位置。轴是对数刻度，A100 的 153 FLOP/byte 分界点把它分成带宽受限与算力受限两段。Decode 批量 1 在 FP16、INT8、INT4 下分别是 1、2、4，全部在左侧；Prefill 处理 8000 token 时在 8000，落在右侧。

这条判断有三处边界。分子只算了权重，长上下文下还要加上 KV Cache 的读取，分母变大、比值更低（第 16 章）；峰值算力和峰值带宽都是规格值，实际达不到，用它们算出的分界点只能当量级（附录 A《GPU 性能心智模型》的“算力”一节有 Roofline 与 Ridge Point 的完整推导和有效值的取法）；批量会改变这个比值，下一节就是这件事。

## 15.3 单步耗时的下限

第 0 章用一句话概括过这件事：每写一个 token，都要把整份权重搬一遍。带宽受限时，这句话可以直接写成式子，也就是本篇开头那条搬运下限：

```text
单步耗时下限 ≈ 模型权重字节数 ÷ 显存带宽
```

上一节用的是课程模型 0.5B，从这里开始换成一个更接近生产规模的通用 7B 模型。**换模型不影响上一节那个结论**，因为算术强度那个比值与参数量无关，7B 的批量 1 Decode 同样是 1 FLOP/byte。换过来只是为了让后面几章的显存和延迟数字落在更常见的量级上。

以一个 7B 模型、FP16 权重、显存带宽 1000 GB/s 为例：

```text
权重  7 × 10^9 × 2 字节 = 14 GB
单步  14 GB ÷ 1000 GB/s = 14 ms
TPOT  下限约 14 ms，对应每秒约 71 个 token
```

**这里的 GB 是十进制的。** 带宽是厂商规格，按 10⁹ 标；权重字节数是参数量乘位宽，也是十进制。两个十进制数相除，单位正好约掉。下一章算显存容量时换成二进制（GiB），因为那边对的是分配器和框架日志的口径，第 16.2 节会把这件事说清楚。

这个数字有几层含义：

**它是下限，不是实测值。** 实际还要加上 KV Cache 的读取、采样和调度开销，实测通常比它大。差得不多说明系统效率不错，差出好几倍说明有别的问题，比如后面要讲的调度开销。

**它几乎不随 prompt 长度变化。** 权重字节数是固定的，和输入多长没关系。所以 Prefill 慢可以靠缩短 prompt 解决，Decode 慢不行。

**降低它只有两条路**：让权重变小，或者让带宽变大。前者是第 17 章的量化，后者是换硬件。这解释了为什么量化在 Decode 侧的收益远大于 Prefill 侧。

> **显存带宽**（Memory Bandwidth）：GPU 显存与计算单元之间每秒能传输的字节数。它和算力是两个独立的规格，一张卡可能算力很强但带宽一般，这时带宽受限的负载就吃不到算力的好处。

## 15.4 批量：Decode 唯一的免费午餐

上一节那个估算里藏着一个机会。

如果同时有 32 条请求在生成，它们共用同一份权重。权重还是只读一遍，但这一遍服务了 32 个 token 而不是 1 个。

```text
批量 1    读 14 GB → 产出 1 个 token    → 14 ms/token
批量 32   读 14 GB → 产出 32 个 token   → 约 0.44 ms/token（摊薄后）
```

吞吐提升了三十多倍，而单条请求的 TPOT **几乎没有变差**。这在性能工程里很少见：通常增加并发意味着每条请求变慢，而 Decode 的批量在带宽受限区间内近乎免费。

这就是 Continuous Batching 存在的根本原因，第 20 章会讲它怎么实现。这里只需要理解为什么它值得做。

![批量的免费区间与三处边界](figures/fig15-03_batch_free_lunch.svg)

图15-3：批量的免费区间与三处边界。两栏共用一根批量横轴：上栏吞吐从 71 涨到八千多，下栏单条 TPOT 只从 14.1 涨到 16.1 ms。交叉批量 153 右侧是灰色的，因为那里估算模型自己已经失效。

**但免费是有边界的。** 三个地方会让它停止免费：

**一是 KV Cache 的显存。** 每条请求都要存自己的 KV，批量越大占用越多。显存装不下时，批量就上不去了。这是第 16 章的主题。

**二是从带宽受限滑向算力受限。** 批量为 B 时，权重仍然只读一遍，却服务了 B 个 token，算术强度大约变成 B FLOP/byte。所以交叉点的量级就是 15.2 那个分界点的量级：在分界点 153 FLOP/byte 的卡上，批量要到一百多才谈得上算力受限。在那之前，加批量基本是免费的；越过之后，再加批量就开始真的变慢。

**三是 Attention 部分不摊薄。** 每条请求的 KV Cache 是各自的，读取量随批量线性增长，摊不掉。所以长上下文场景下批量的收益会缩水：32 条请求各有 8000 token 的 KV，Attention 部分的搬运量是单条的 32 倍。

## 15.5 为什么 GPU 利用率骗人

Decode 阶段常见的一个困惑：`nvidia-smi` 显示 GPU 利用率 95%，看起来已经跑满了，但 TPS 并不高。

这里有个陷阱。**那个百分比统计的是“有 kernel 在执行的时间占比”，不是“算力被用掉了多少”。**

Decode 的每一步都在等数据从显存过来，计算单元大部分时间在空转。但从利用率的统计口径看，kernel 确实在跑，所以显示接近 100%。

第 9 章讲过这类指标的局限。判断 Decode 是不是真的跑满，不能看这个数字，要看：

```text
实测 TPOT  与  15.3 那个带宽下限
```

两者接近，说明带宽确实被吃满了，这时提升的办法只有量化或换卡。两者差很多，说明时间花在了别处，往下查调度开销。

## 15.6 调度开销：被忽略的那一块

理论下限 14 ms，实测 17 ms，中间那 3 ms 去哪了？

Decode 是一个高频循环。每一步引擎都要做一轮准备工作：收集当前 batch、准备输入张量、启动一串 kernel、取回结果、采样、更新状态。**这些工作里有相当一部分在 CPU 上**，而这一轮的时间全部落在同一步里，摊不到别处去。

把这 3 ms 拆开看，是两笔量级不同的账：

```text
kernel 启动    每步几十到上百个 kernel，单个启动几微秒   约 0.5 ms
引擎侧准备     收集 batch、准备张量、采样、更新状态       约 2.5 ms
每步合计                                                约 3 ms
```

![一步 Decode 的时间构成与实测的差](figures/fig15-02_step_breakdown.svg)

图15-2：一步 Decode 的时间构成与实测的差。三段按毫秒成比例：权重搬运 14 ms、kernel 启动 0.5 ms、引擎侧准备 2.5 ms。上方括号是理论下限，下方括号是实测 17 ms，比值 1.21。

**这两个数要分开记，因为治它们的手段不同。** 第一项是第 18 章 CUDA Graph 的目标，第二项要靠减少每步的 Python 工作，两者不能互相代替。

还有一个视角容易和上面这笔账混起来：这 3 ms 是每一步的，而一次生成有几百步。3 ms 乘 500 步就是 1.5 秒，这是用户能直接感知的量级，而它完全不在权重搬运里。**算每步耗时时看毫秒，算用户等待时看总和，两个视角都要有，但不能互相冒充。**

第 9 章那个概念在这里派上用场：

> **Kernel Launch Gap**：两个连续 kernel 之间 GPU 空闲的间隙。单个 kernel 的启动开销是微秒级，但 Decode 每步要启动几十到上百个 kernel，且每步的间隙都会累加，在高频循环里总量不可忽略。

判断方法是看 Timeline：GPU 上的 kernel 密集且连续，说明瓶颈在带宽；kernel 之间有明显空隙，说明卡在调度和启动上。

第 18 章的 CUDA Graph 正是针对上面那 0.5 ms，它把一串 kernel 的启动过程预先录下来，每步只需要重放一次。**它治不了那 2.5 ms**，所以实测远高于下限时不要指望它一项就能补上全部缺口。

## 15.7 生成长度：第 100 个和第 1000 个 token

回到开头那个问题：生成第 1000 个 token 比第 100 个慢吗？

**权重读取那部分完全一样**，和生成到第几个没关系。

**Attention 那部分会变慢**，因为每生成一个 token，KV Cache 就长一点，下一步要读的 KV 就多一点。第 1000 步要读的 KV 是第 100 步的十倍。

所以单步时间是缓慢上升的。上升幅度取决于 KV 读取在总时间里的占比：

```text
短上下文   权重读取占绝对主导，KV 那点增量看不出来
长上下文   KV 读取量可以和权重相当甚至超过，单步时间明显爬升
```

一个 7B 模型、GQA 下每 token 约 128 KiB 的 KV，生成到第 8000 个 token 时这条请求的 KV 已经有 1000 MiB，和 13 GiB 的权重比是个不小的比例；而如果批量是 32，32 条请求的 KV 加起来是 31 GiB，超过权重本身，这时 Attention 成了主导。

![单步耗时随生成长度的爬升](figures/fig15-04_context_climb.svg)

图15-4：单步耗时随生成长度的爬升，以及批量怎么放大它。三条曲线是批量 1、8、32；虚线是不随长度变化的权重下限。批量 32 在 8000 token 处被圈出，那里 KV 的 31 GiB 已超过权重的 13 GiB。

**所以“长上下文让 Decode 变慢”不是错觉，但机制和 Prefill 那边完全不同**：Prefill 那边是计算量的平方项，Decode 这边是 KV 读取量的线性增长，且会被批量放大。

## 15.8 Demo：Decode 性能估算器

本章 Demo 位于 `code/ch15/decode_model.py`，不需要 GPU。

```bash
python3 code/ch15/decode_model.py \
  --params 7e9 --dtype fp16 \
  --bandwidth 1000 \
  --batch 1,8,32,64 \
  --context 512,4096,16384
```

输出结构：

```text
weight_bytes      权重字节数
step_floor_ms     纯权重读取的单步下限
kv_bytes_per_step 当前批量与上下文下，每步要读的 KV 量
step_estimate_ms  权重 + KV 的估算单步耗时
tpot_ms           对应的 TPOT
throughput_tps    对应的总吞吐
crossover_batch   估算的带宽受限转算力受限的批量位置
```

三个用法：

**看批量的边际收益。** 从 1 到 8 吞吐涨得很猛，从 32 到 64 就明显缓了。这条曲线决定了批量该设多大。

**看上下文对批量收益的侵蚀。** 固定批量，把 `--context` 拉大，会看到 `kv_bytes_per_step` 逐渐逼近并超过 `weight_bytes`。超过之后再加批量几乎没有好处。

**和实测对照。** 拿 `tpot_ms` 和线上实测比，差得远就说明时间花在了估算模型没有覆盖的地方，往调度开销方向查。

和第 11 章那个估算器一样，它算的是量级，不是精确值。**本章的真机数据尚未采集**，GX10 恢复后补齐实测对照。

## 15.9 课堂案例与常见误区

### 案例一：加卡没用

某服务 TPOT 偏高，团队把 GPU 从一张换成两张做张量并行，期望 TPOT 减半。实测只降了两成多。

原因是张量并行把权重切开，每张卡读一半，理论上搬运时间减半，但引入了每层之后的通信同步。Decode 是高频循环，这个同步每步都要做一次，开销被放大了 500 倍。

更要命的是，团队后来发现真正的瓶颈根本不在带宽，实测 TPOT 是理论下限的两倍多，中间那部分是调度开销。加卡不解决调度开销。

讨论：如果当初先做 15.5 那个对照，会得出什么不同的行动？

### 案例二：批量从 8 调到 64，用户投诉变多

运维为了提升吞吐把最大批量调到 64，总 TPS 确实涨了四成。但用户开始抱怨卡顿。

查 ITL 序列发现：平均值变化不大，但抖动大了很多，P99 的 ITL 从 40 ms 涨到 210 ms。大批量下调度的一步要处理更多请求，单步时间变长且不稳定，用户端就表现为一顿一顿的。

平均 TPOT 掩盖了这个问题。第 5.3 节说过，逐 token 的体验要看 ITL 的分布，不是平均值。

讨论：吞吐和 ITL 抖动之间怎么取舍？这个取舍该由谁来定？

### 案例三：同一个模型，两台机器差三倍

同样的模型、同样的框架版本、同样的批量配置，两台机器的 TPOT 差了三倍。

查规格才发现一台是 HBM 显存，一台是 GDDR，带宽差了将近三倍。TPOT 的差距和带宽的差距几乎完全对应。

这个案例的价值在于：**它验证了带宽受限这个判断本身。** 如果 Decode 真的是带宽受限，那么 TPOT 就该和带宽成反比。差距对不上，说明瓶颈另有其人。

讨论：还有什么现成的对照能用来验证“当前确实是带宽受限”？

### 两个不写在估算表里的误区

误区一：GPU 利用率高就说明榨干了硬件。

见 15.5：那个百分比统计的是有没有 kernel 在跑，不是算力用了多少。判断该看实测 TPOT 和带宽下限的比值。

误区二：Decode 慢就去优化生成的内容。

缩短输出长度确实能减少总时间，但那改变的是 token 数，不是每个 token 的耗时。如果问题是 TPOT 本身偏高，让模型少说话治标不治本，而且通常会损害回答质量。先分清是“token 太多”还是“每个 token 太慢”。

## 本章总结

回到开头的三个问题。

**第 100 个和第 1000 个 token 哪个更慢？** 第 1000 个，但慢得不多，且原因很具体：权重读取那部分完全一样，变化的只有 KV Cache 的读取量，它随已生成长度线性增长。短上下文下这点增量被权重读取淹没，看不出来；长上下文加大批量时，KV 读取量可以超过权重本身，这时单步时间明显爬升。和 Prefill 那边的平方项不是一回事。

**为什么利用率高却快不起来？** 因为 Decode 一次只处理一个 token，却要把整个模型的权重完整读一遍。同样的搬运，八千分之一的计算，计算单元大量时间在等数据。而 GPU 利用率统计的是有没有 kernel 在执行，不是算力用了多少，所以它照样显示 95%。真正该看的是实测 TPOT 和带宽下限的比值。

**TPOT 大概应该是多少？** 下限约等于模型权重字节数除以显存带宽，7B 的 FP16 模型在 1000 GB/s 的卡上约 14 ms。实测比它大是正常的，差出好几倍就要往调度开销方向查，看 Timeline 上 kernel 之间有没有空隙。降低这个下限只有两条路：权重变小（第 17 章的量化）或带宽变大（换卡）。批量是 Decode 少见的免费午餐，在带宽受限区间内能大幅提升吞吐而几乎不损害单条 TPOT，但它受三件事限制：KV Cache 占的显存、带宽受限向算力受限的翻转，以及 Attention 部分摊不薄。

下一章处理其中最紧的那个约束：KV Cache 到底占多少显存，怎么估，以及它为什么会碎。

## 课后练习

1. 用你手上模型的参数量和卡的带宽，算出单步耗时下限和对应的 TPOT。
2. 实测单条请求的 TPOT，和上一题的下限比，算出比值并解释差异。
3. 固定上下文长度，把批量从 1 加到 64，画出吞吐曲线，找出边际收益明显变缓的位置。
4. 固定批量，把上下文从 512 加到 16384，记录 KV 读取量与权重字节数的比例变化。
5. 采集一段 Decode 的 Timeline，判断 kernel 是密集连续还是有明显空隙。
6. 记录一条长回答的完整 ITL 序列，看单步时间有没有随生成长度上升。
7. 把最大批量调大一档，对比 TPOT 平均值和 P99 ITL 的变化，说明平均值掩盖了什么。
8. 找一份声称“提升 GPU 利用率就能提升吞吐”的建议，用本章的口径判断它在什么情况下不成立。
