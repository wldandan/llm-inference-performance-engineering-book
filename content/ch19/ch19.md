# 第 19 章 Decode 优化实验：五个指标要一起看

## 学习目标

读完这一章，你应该能回答三个问题：

1. Decode 侧的实验，为什么不能只盯 TPOT？
2. 吞吐和单条延迟冲突时，按什么标准取舍？
3. 一组优化叠加起来，怎么知道它们有没有互相抵消？

跟着做完，你会产出本篇的交付物：一份 Decode 优化报告，同时覆盖 TPOT、吞吐、显存、接受率和质量五个维度。

第 14 章讲过实验方法：先写预期、一次只改一项、护栏必须记录、结论要标边界。那些在这里全部适用，不重复。这一章的新内容是：**Decode 侧的指标之间互相牵制，单看一个必然误判。**

## 19.1 为什么 Prefill 那套记分方式在这里不够用

第 14 章的实验主要看 TTFT，护栏是质量和显存。指标少，关系简单。

Decode 这边不一样。前四章的每一项手段都在同时动好几个指标：

```text
批量调大      吞吐涨    TPOT 略升   显存涨   抢占风险涨
KV 量化       并发涨    TPOT 略降   质量降
权重量化      TPOT 降   并发略涨    质量降
投机解码      TPOT 降   显存涨      质量不变（但高批量下反向）
CUDA Graph    TPOT 降   显存涨
```

**没有一项是单向的。** 只看 TPOT，会把“吞吐掉了三成”当成成功；只看吞吐，会把“用户明显卡顿”当成成功。

所以这一章的实验记分卡有五个维度，缺一个结论就不完整：

| 维度 | 指标 | 为什么必须看 |
|---|---|---|
| 单条体验 | TPOT 平均值与 P95 ITL | 用户感知的是间隔和抖动 |
| 系统吞吐 | 总 TPS、并发请求数 | 决定要几张卡 |
| 容量 | 显存占用、抢占计数 | 决定能不能稳住 |
| 加速有效性 | 投机解码接受率 | 收益是否真的兑现 |
| 质量 | 评测集得分 | 量化是否越界 |

后两项按实验内容取舍：没启用投机解码就不看接受率，没动精度就不跑质量评测。前三项每次都要看。

## 19.2 TPOT 平均值掩盖了什么

第 15 章那个案例出现过：批量从 8 调到 64，平均 TPOT 变化不大，P99 ITL 从 40 ms 涨到 210 ms。

原因是 Decode 的每一步要处理整个批次。批次越大，单步越长，且随批次内容波动。用户端看到的是一顿一顿的输出。

**所以 Decode 实验必须记录 ITL 的分布，不只是 TPOT 的平均值。** 具体要记三个数：

```text
TPOT 平均   整条请求的平均间隔，反映总时长
P95 ITL     逐个间隔的 95 分位，反映抖动
最大 ITL    最大的单个间隔，通常对应抢占或调度尖峰
```

第三个数特别有用，因为它和前两个不在一个量级上。一条正常请求和一条被抢占过的请求，三个数长这样：

```text
正常        平均 45 ms   P95 80 ms    最大 190 ms     最大是平均的 4 倍
被抢占过     平均 52 ms   P95 95 ms    最大 2400 ms    最大是平均的 46 倍
```

注意平均值只从 45 涨到 52，**前两个数几乎看不出差别，第三个数差了一个数量级**。所以看到一个孤立的巨大尖峰，先去查抢占计数，不要当成噪声。

## 19.3 吞吐和延迟的取舍该由谁定

批量是这一篇里唯一一个能大幅提升吞吐的旋钮，而它的代价是 ITL 抖动。

这个取舍不是技术问题。**它取决于业务能接受多大的抖动**，而这个数字应该来自 SLO，不是来自工程师的判断。

第 6 章那份 workload 描述里有 SLO 字段，Decode 实验要把它用起来：

```text
metric: ITL
quantile: P95
threshold: 80 ms
```

有了这条线，取舍就变成一个明确的规则：

```text
在 P95 ITL 不超过 80 ms 的前提下，把吞吐做到最大
```

这就是 Goodput 的思路。按第 5.4 节的定义，它数的是单位时间内的 good request，而 good request 要同时满足成功、质量达标、延迟在 SLO 之内三个条件。一个 TPS 很高但半数请求超时的系统，Goodput 可能低于一个 TPS 中等但全部达标的系统；同理，一个靠降精度把 TPS 拉上去、质量却掉到底线以下的配置，Goodput 一分不涨，因为那一列是否决项。

**用 Goodput 而不是 TPS 作为主指标，这个取舍就自动完成了。** 批量调到超出 SLO 的档位时，Goodput 会掉下来，不需要人去权衡。

所以批量扫描实验的正确做法是：

```text
批量 4, 8, 16, 32, 64, 128 各跑一轮
每轮记录 TPS、P95 ITL、Goodput
画出曲线，找 Goodput 的峰值
```

峰值那个批量就是当前配置下的最优点。它通常不在 TPS 的峰值上。

![TPS 峰值与 Goodput 峰值不在同一处](figures/fig19-01_goodput_vs_tps.svg)

图19-1：TPS 峰值与 Goodput 峰值不在同一个批量上。上栏虚线是名义 TPS，在批量 128 达到峰值；实线是 Goodput，峰值在批量 32。下栏 P95 ITL 在批量 64 越过 SLO 那条 80 ms 的线。数据出自那份合成样例。

用 Goodput 收敛成一个数之后，还要留一句话给没被它收进去的那些指标。

> **帕累托前沿（Pareto frontier）**：多个指标一起看时，那些“不可能在不牺牲任何一个指标的前提下再改进”的配置组成的边界。前沿上的点之间没有优劣，只有取舍；前沿以内的点是真的差，可以直接淘汰。
> 它给出的判断只有一句：一个配置如果在所有指标上都不优于另一个，就把它删掉；剩下的那些，靠 SLO 而不是靠比较来选。

这一章的记分卡有五列，批量 32 和批量 64 常常一个 TPS 高、一个 P95 ITL 好，它们都在前沿上，问“哪个更好”没有答案。Goodput 之所以能自动完成取舍，是因为它把 SLO 那条线当成了选择规则：前沿上只有一个点满足“达标前提下吞吐最大”。**所以 SLO 变了，最优点就会换一个，而前沿本身不变。** 报告里要把前沿上的几个候选都留着，别只留最后选中的那一个，因为下一次 SLO 调整时它们就是现成的答案。

## 19.4 五轮实验的安排

用同一份负载，按第 15 到 18 章的顺序逐项验证。

**负载沿用第 6 章的写法**，但和第 14 章那份不同：Prefill 实验需要长 prompt，Decode 实验需要长输出。

```text
identity   name: decode-long-output
           type: chat

length     prompt  P50 600 / P90 1200 / P99 2000
           output  P50 400 / P90 900 / P99 1600

arrival    mode: poisson
           rate: 12 req/s
           duration: 180 s
           seed: 固定

slo        metric: ITL
           quantile: P95
           threshold: 80 ms
```

输出长度是这份负载的关键。**输出短了测不出 Decode 的问题**，因为总时长会被 TTFT 主导。

五轮：

| 轮次 | 改动 | 主要看 | 护栏 |
|---|---|---|---|
| 0 | Baseline，批量扫描 | Goodput 曲线，找峰值批量 | P95 ITL |
| 1 | KV Cache INT8 | 并发上限、显存 | 质量评测、TPOT |
| 2 | 权重 INT8 | TPOT、P95 ITL | 质量评测、并发 |
| 3 | 投机解码 | TPOT、接受率 | 显存、高批量下的吞吐 |
| 4 | CUDA Graph 档位调整 | TPOT、显存 | 填充浪费、批量覆盖率 |

**第 0 轮不是可选的。** 没有批量扫描就不知道当前在曲线的哪个位置，后面四轮的收益无从解释。一个在批量 8 上测出的改善，可能在批量 32 上完全不存在。

**第 1、2 轮必须跑质量评测。** 按第 17 章的要求，评测集在实验前固定，底线在实验前写死。

**第 3 轮要在两个批量下各测一次。** 第 18 章说过投机解码在高批量下会反向，只在低批量下测会得出过于乐观的结论。

![五轮实验的五维记分卡](figures/fig19-02_five_round_scorecard.svg)

图19-2：五轮实验的五维记分卡。第 2 轮权重 INT8 的前三个维度全部改善，质量越界，结论是失败回滚。第 4 轮主指标测不出来，而收益全在容量那一列。数据出自那份合成样例。

## 19.5 叠加起来会互相抵消吗

前四章的手段可以叠加，但叠加不是简单相加。几组典型的相互作用：

**量化和投机解码：显存互相挤。** KV 量化腾出显存，投机解码的草稿模型又占回去一部分。这一组能算，算完就知道“不能相加”是什么意思：

```text
基线            KV 预算 60 GiB，每 token 128 KiB   →  49.2 万 token   并发 213
KV INT8         每 token 降到 64 KiB              →  98.3 万 token   并发 427
草稿模型常驻     1.3 GiB 从 KV 预算里扣，按 64 KiB 算是 2.1 万 token
两者一起          净 96.2 万 token                  →  并发 418
```

单看 KV 量化是并发翻倍（213 → 427），叠上投机解码之后是 418，**草稿模型吃掉了这次翻倍里的 4%**。这个例子里折损不大，但比例随草稿模型大小变：草稿换成目标模型的四分之一大，扣掉的就不是 2.1 万而是 5.3 万 token。所以净变化要重新测，不能把各自的数字相加。

**批量和投机解码：直接冲突。** 前者靠大批量提吞吐，后者在大批量下失效。同时追求两者，通常意味着两边都没做好。先确定这个服务优先吞吐还是优先单条延迟，再选其中一条路。

**CUDA Graph 和批量扫描：档位要对齐。** 图是按批量档位捕获的，实际批量落在档位之间时要填充。第 0 轮找出的峰值批量应该是一个被捕获的档位，否则每步都在浪费算力做填充。

**权重量化和 CUDA Graph：收益不重叠，反而互相放大。** 两者都缩短单步时间，但针对的是不同部分：权重量化压缩的是读权重的时间，CUDA Graph 压缩的是启动开销。如果 CUDA Graph 已经把启动开销消掉了，那权重量化的相对收益会比预期大，因为分母变小了。

**判断有没有抵消的方法**，就是第 14 章那条纪律的延伸：一次只叠加一项，每叠一项就重测全部五个维度。发现某一项叠加后总收益反而下降，那就是抵消，退回去单独用。

## 19.6 Demo：Decode 实验记分卡

本章 Demo 位于 `code/ch19/decode_experiment.py`。它复用第 14 章那份检查器的纪律，不重写；采数据需要真实 vLLM 服务，检查器本身可以直接拿仓库里那份合成样例跑一遍。

```bash
python3 code/ch19/decode_experiment.py \
  --report content/ch19/evidence/decode-experiment-sample.json
```

报告结构在第 14 章那份的基础上扩了三块：

```text
expectation   实验前写下的预期（沿用 Ch14）
fixed         固定的 workload、protocol、environment（沿用 Ch14）
changed       本次唯一改动项（沿用 Ch14）
scorecard     五维记分卡：latency / throughput / capacity / acceptance / quality
sweep         批量扫描结果与 Goodput 曲线，标出峰值批量
interaction   与已启用项的相互作用检查
verdict       与预期对照的结论（沿用 Ch14）
boundary      模型、负载、硬件、配置四项边界（沿用 Ch14）
```

三条硬性检查：

`scorecard` 的 latency、throughput、capacity 三项不可为空，缺一项拒绝出报告。`changed` 里包含精度改动时，`quality` 必须有值，且必须给出实验前记录的底线。`changed` 里包含投机解码时，必须提供两个批量档位的结果。

中间那条是这一章最重要的一道闸。**动了精度却没有质量数据的报告，不该被接受**，哪怕 TPOT 数字很漂亮。

还有两处设计值得单独说，它们都是 Decode 侧才有的问题。

**一是指标方向要写清楚。** 第 14 章只判 TTFT，越小越好；这一章的记分卡里 TPOT 越小越好、并发越大越好，同一份报告里两种方向并存。所以 `results` 里有一个 `direction` 字段，写错了会把改善读成劣化，检查器不认没写清楚的容量类指标。

**二是“成立”和“保留”是两件事。** 一轮实验可以结论有效而这项改动仍然不留下，比如第 3 轮那样：收益真实，但不值得付出草稿模型那 2.1 万 token 的容量。所以 `verdict` 里 `passed` 和 `kept` 分开，后面几轮才算得对自己叠加在什么之上。判失败却写着保留，检查器会拒。

`decode-experiment-sample.json` 是**合成样例，不是真机结果**，`synthetic` 字段和 `_note` 都写明了。五轮各演示一种情形：

```text
第 0 轮  批量扫描              只出 Goodput 曲线，不写四种结论里的任何一种
第 1 轮  KV Cache INT8         符合预期，并发 213 → 419
第 2 轮  权重 INT8             四个维度全部改善，质量越界，判失败
第 3 轮  投机解码              低于预期，暴露离线与线上接受率的差
第 4 轮  CUDA Graph 档位裁剪    主指标在波动内不可分辨，收益全在容量一列
```

第 2 轮是这份样例的核心。TPOT 降 40.3%、正好符合预期，吞吐涨、并发涨、显存降，五个维度里四个都在改善，而结构化输出那一维掉了 3.9 个百分点，越过了 1 个百分点的底线。检查器判这一轮失败并要求回滚：四个维度改善抵不过一个越界，**记分卡不是投票**。

第 4 轮是另一头。主指标测不出来是一个合法且诚实的结论，而这一轮仍然值得保留，因为省回的 11 GiB 让并发从 419 涨到 497。结论写在 `capacity` 而不是 `latency`，这正是五维记分卡存在的理由：**收益出现在哪一列，就写在哪一列，不往主指标上凑。**

**本章的真机实验尚未完成。** GX10 恢复后，Part 4 的交付是：跑完批量扫描找出峰值批量，再按五轮逐项验证，产出一份五维齐全的报告，替换掉这份合成样例。

## 19.7 课堂案例与常见误区

### 案例一：TPOT 降了 40%，用户投诉翻倍

团队做了权重 INT8 量化，TPOT 从 22 ms 降到 13 ms，报告写“Decode 延迟改善 41%”。

上线两周后客诉上升。查下来 TPOT 确实降了，但因为显存腾出来了，运维顺手把最大批量从 32 调到 96，P95 ITL 从 55 ms 涨到 130 ms，超过了 SLO 那条 80 ms 的线。

**两个改动混在一起上，且只记了一个指标。** 量化本身是成功的，批量调整是失败的，但报告里看不出来。

讨论：如果当时用 Goodput 作为主指标，这个问题会在什么时候暴露？

### 案例二：接受率 3.8，但吞吐掉了

投机解码在离线测试中接受率 3.8，TPOT 降了六成，团队很满意。

上线后单条请求确实快了，但系统总吞吐掉了 25%。原因是线上的实际批量是 48，而离线测试是单请求。大批量下算力本来就不空闲，投机解码的额外计算挤占了真实吞吐。

单条更快、总吞吐更低，这在只服务少量 VIP 用户时是划算的，在通用服务上不是。

讨论：这个结论该怎么写进报告，才不会被误用到别的服务上？

### 案例三：批量 128 的 TPS 最高，但没人用它

批量扫描显示 TPS 在 128 时达到峰值，比 32 时高 18%。

但 P95 ITL 在 128 时是 240 ms，远超 SLO 的 80 ms。按 Goodput 算：

```text
批量 32    TPS 基准      达标率 98%    Goodput 0.98
批量 128   TPS × 1.18    达标率 55%    Goodput 0.65
```

**128 档位的 Goodput 比 32 低了三成多**，因为那 18% 的吞吐增量是靠让四成多的请求超时换来的。

最终选了 32。**TPS 峰值和 Goodput 峰值不在同一个位置，这是常态而不是例外。**

讨论：如果业务愿意把 SLO 放宽到 150 ms，最优批量会移到哪里？该由谁来做这个决定？

### 两个不写在记分卡里的误区

误区一：五个指标里有三个变好了就算成功。

不是投票。质量那一项是否决项，超过底线就是失败，哪怕另外四项全部改善。抢占计数也接近否决项，因为它意味着系统在不稳定区运行，当前的数字随时可能崩。

误区二：离线单请求测出来的加速能代表线上。

Decode 侧几乎所有手段的收益都随批量变化，而离线测试通常是单请求。批量是这一篇里最强的变量，任何不说明批量的 Decode 收益数字都是不完整的。

## 本章总结

回到开头的三个问题。

**为什么不能只盯 TPOT？** 因为 Decode 侧没有一项手段是单向的。批量调大提吞吐但拉高 ITL 抖动，量化降 TPOT 但损质量，投机解码降 TPOT 但占显存且在高批量下反向。记分卡要五个维度：单条体验看 TPOT 平均值和 P95 ITL，系统吞吐看 TPS 和并发，容量看显存和抢占计数，加速有效性看接受率，质量看评测集。其中 TPOT 平均值尤其会掩盖问题，必须同时记 P95 ITL 和最大 ITL，后者出现几十倍的孤立尖峰时先去查抢占。

**吞吐和延迟冲突时按什么取舍？** 用 SLO 把它变成规则，用 Goodput 把规则变成单一指标：在 P95 ITL 不超过阈值的前提下把吞吐做到最大。批量扫描时画 Goodput 曲线找峰值，而不是找 TPS 峰值，两者不在同一个位置是常态。这个取舍的标准来自业务 SLO，不该由工程师临时判断。

**叠加会不会抵消？** 会，而且有几组是可预期的。量化腾出的显存被草稿模型占回去；批量和投机解码方向相反，同时追求两者通常两边都做不好；CUDA Graph 的批量档位要和扫描出的峰值批量对齐，否则每步都在填充；权重量化和 CUDA Graph 压缩的是不同部分，叠加后相对收益会比单独测时更大。判断方法是一次只叠加一项，每叠一项重测全部五个维度。

Part 4 到此结束。前面四篇都在单个服务实例内部做文章：Prefill 的计算量、Decode 的带宽、KV Cache 的显存。下一篇跨出实例，看请求在进入模型之前经历了什么：调度、排队、限流、路由，以及一条 RAG 或 Agent 链路上那些不在 GPU 上的时间。
