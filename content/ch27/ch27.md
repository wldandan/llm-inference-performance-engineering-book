# 第 27 章 多副本、路由与 Autoscaling：弹性为什么救不了突发

## 学习目标

读完这一章，你应该能回答三个问题：

1. 加一倍的卡，能不能扛一倍的流量？
2. 自动扩缩容该按什么指标触发，为什么常用的那个指标是错的？
3. 冷启动几分钟的服务，弹性还有什么用？

跟着做完，你会得到一份扩缩容配置：触发指标、阈值、步长、冷却时间，以及一份说明弹性覆盖不了哪些场景的边界文档。

## 27.1 卡数定了，然后呢

第 26 章算出需要 21 张卡。但“21 张卡”不是一个部署方案。

```text
21 张卡怎么组织？        一个实例 21 卡，还是 21 个单卡实例？
流量低的时候呢？          21 张全开着还是关一部分？
突然涨到 3 倍呢？         自动扩，还是拒绝？
某一张卡挂了呢？          剩下 20 张扛得住吗？
```

这四个问题的答案互相牵制，而且都和前面几章的结论有关。这一章逐个处理。

**先说结论里最反直觉的一条：自动扩缩容解决的不是突发流量。** 这一点在第 22 章提过一句，这一章展开。

## 27.2 加一倍的卡，扛不住一倍的流量

第 22 章说过多副本容量不是线性叠加，实际按 0.8 到 0.9 折算。这一节说清楚那部分损失去了哪里。

**损失一：路由不均。** 请求长度差异大，即使请求数均分，负载也不均。某个实例分到几条超长请求就会明显慢于其他。而 P99 由最慢的实例决定。

**损失二：缓存分散。** 第 22 章那个案例：轮询把相同前缀打散，命中率从 91% 掉到不足三成。实例越多，同一个前缀被分到的份数越多，单实例的缓存效率越低。

**损失三：余量不能共享。** 单实例时所有余量在一个池子里；拆成多个实例后，A 的空闲帮不了 B 的拥挤，除非路由能实时感知并倾斜。

**损失四：故障域变大。** 实例越多，任一时刻有实例处于异常状态的概率越高。

**这四项里前三项都能通过路由缓解**，所以路由设计在多副本场景下不是可选项。

**一个实用的结论：** 副本数从 1 到 4 的边际收益很好，从 4 到 16 开始明显衰减，超过 16 之后路由和一致性的复杂度会吃掉相当一部分收益。需要更大规模时，通常要引入分层（按场景或按模型分组），而不是继续扩同一个池子。

## 27.3 单实例几张卡

另一个维度的问题：21 张卡是拆成 21 个单卡实例，还是 3 个 7 卡实例？

判据是模型能不能装进一张卡：

```text
装得下   优先单卡实例。没有通信开销，故障域小，扩缩容粒度细
装不下   必须多卡，用张量并行把权重切开
```

**装得下却用多卡并行，通常是亏的。** 第 15 章那个案例说明了原因：张量并行在每层之后要通信同步，而 Decode 是高频循环，这个同步每步都要做一次。单条请求的延迟可能改善，但吞吐和成本效率会下降。

**必须多卡时，要知道扩展效率不是 1。** 两卡的吞吐通常是单卡的 1.6 到 1.8 倍，不是 2 倍。卡数越多，效率越低，且对卡间带宽非常敏感。

> **张量并行**（Tensor Parallelism）：把模型每一层的权重矩阵切开，分到多张卡上各算一部分，再通过通信合并结果。它让单张卡装不下的模型能跑起来，代价是每层都要一次跨卡通信。

多卡的实现细节和扩展效率的实测方法在附录 C，正文不展开。

**扩缩容粒度是一个容易忽略的因素：** 单卡实例时，扩容的最小单位是 1 张卡；8 卡实例时，最小单位是 8 张卡。后者意味着你要么浪费，要么不够。

## 27.4 Autoscaling 该看哪个指标

自动扩缩容的触发指标，选错的代价很大。

**最常用也最错的是 GPU 利用率。** 第 15 章讲过，那个百分比统计的是有没有 kernel 在执行，不是算力用了多少。Decode 阶段计算单元大量时间在等数据，利用率照样接近 100%。**按它触发扩容，会在系统还很空闲时就扩，也会在真正拥挤时无动于衷。**

**次常用也不太对的是 QPS。** 请求数不能反映负载，一个 8000 token 的请求和一个 300 token 的请求差几十倍。按 QPS 扩容，长请求变多时会扩不够。

**应该用的是第 20 章那三个指标：**

```text
主指标   Running 集合占上限的比例
辅助     Waiting 队列长度
辅助     KV Cache 使用率
```

**Running 占比是最好的单一指标**，因为它直接反映“还能不能接更多请求”，而且它比排队和抢占都动得早，能留出扩容需要的时间。

还有一个更好但更难实现的选择：

```text
SLO 达成率   P95 延迟相对 SLO 阈值的比值
```

**它的好处是直接对齐业务目标**：延迟还没逼近 SLO 就不需要扩，逼近了才扩，无论原因是什么。坏处是它是滞后指标，等它动的时候用户已经在受影响了。

**实践上的折中是用 Running 占比做主触发，用 SLO 达成率做兜底。**

## 27.5 冷启动决定了弹性能做什么

这是这一章最重要的一节。

一个新实例从创建到能接请求，要经过：

```text
调度到节点      秒级到分钟级，取决于有没有空闲资源
拉取镜像        如果没有本地缓存，可能几分钟
加载模型权重    几十秒到几分钟，取决于模型大小和存储介质
预热            捕获 CUDA Graph、跑几次 warmup，十几秒到一分钟
就绪检查通过    可以接流量
```

**总计通常是 3 到 10 分钟。**

而突发流量是秒级的。一次营销推送、一次热点事件，几十秒内流量翻三倍。等新实例起来，高峰已经过去了，或者服务已经垮了。

**所以要把流量变化分成两类，用不同手段应对：**

| 变化类型 | 时间尺度 | 应对手段 |
|---|---|---|
| 趋势性增长 | 小时到天 | Autoscaling |
| 可预测的周期 | 日内波峰 | 定时扩缩容 |
| 突发 | 秒到分钟 | 准入控制 + 预留余量 |

**第三行是关键。** 第 21 章那套准入控制不是弹性不足时的补丁，而是唯一能在秒级尺度上生效的手段。**指望 Autoscaling 来救突发，是一个时间尺度上的错配。**

**缩短冷启动的几个手段：**

```text
镜像预拉取      节点上常驻镜像缓存
权重本地缓存    避免每次从远端对象存储拉
减少预热档位    第 18 章那个 CUDA Graph 的档位，捕获越多启动越慢
预热实例池      保持若干已加载但不接流量的实例待命，最快但最贵
```

**最后一项本质上是用钱换时间。** 它能把扩容时间压到秒级，但那些实例一直在付费。值不值取决于突发的频率和代价。

## 27.6 缩容比扩容更容易出事

扩容慢但安全，缩容快但危险。

**缩容的三个陷阱：**

**一、正在处理的请求被中断。** 一条生成到一半的长请求，实例被回收就没了。缩容必须先摘流量、等在途请求处理完、再回收。这个优雅退出的等待时间要设得比最长请求还长。

**二、缩完之后立刻又要扩。** 流量有波动，刚缩完一个实例流量就回来了，于是又扩，形成抖动。防抖的手段是冷却时间和不对称阈值：

```text
扩容阈值   Running 占比 > 70%
缩容阈值   Running 占比 < 40%      （不是 70%，留出滞回区间）
缩容冷却   30 分钟                  （远长于扩容冷却）
```

**三、缩容把缓存也缩掉了。** 第 22 章那个一致性哈希的意义在这里：实例数变化时，如果用的是简单取模哈希，几乎所有前缀的归属都会变，缓存整体失效。一致性哈希能把影响限制在一小部分。

**缩容应该比扩容保守得多。** 扩错了只是多花钱，缩错了会直接影响可用性。

## 27.7 灰度与滚动：容量在这期间是降的

第 22 章提过一句：滚动升级期间容量下降。这里给出具体的算法。

```text
实例总数 N，每次替换 k 个
升级期间可用容量 = (N - k) / N
```

N=6、k=1 时，升级期间容量是 83%。如果平时利用率就在 85%，升级期间必然过载。

**两条纪律：**

**一、平时的利用率上限要为升级留出空间。** 如果按每次替换 1 个规划，平时利用率不该超过 `(N-1)/N` 再打个折。N 越小，这个约束越紧。

**二、升级窗口要选在波谷。** 这不是习惯，是容量算出来的要求。

**灰度发布还有一个 LLM 特有的问题：** 新旧版本的模型可能行为不同，而 Prefix Cache 是按版本隔离的。灰度期间两个版本各自维护缓存，命中率都会下降。所以灰度期间的性能数据不能直接和全量后的对比，第 28 章会展开这一点。

## 27.8 Demo：扩缩容策略模拟

本章 Demo 位于 `code/ch27/autoscale_sim.py`，不需要 GPU。

```bash
python3 code/ch27/autoscale_sim.py \
  --traffic traffic-trace.csv \
  --capacity-per-instance 150 \
  --scale-up-threshold 0.7 --scale-down-threshold 0.4 \
  --cold-start 300 --scale-up-cooldown 180 --scale-down-cooldown 1800 \
  --min-instances 3 --max-instances 30 \
  --output autoscale-report.json
```

它用一段真实或合成的流量轨迹模拟扩缩容行为，输出：

```text
instance_timeline   实例数随时间的变化
unmet_demand        超出当时容量的请求量及其时长
scale_events        每次扩缩容的触发时刻、原因和生效时刻
lag                 从触发到生效的延迟分布
thrash_count        抖动次数：缩容后短时间内又扩容
cost                按实例小时数算的成本
verdict             这套参数在这段流量下是否可用
```

关键在 `unmet_demand` 和 `lag` 的配合：

```text
lag 远小于流量变化的时间尺度   弹性有效
lag 远大于流量变化的时间尺度   弹性无效，unmet_demand 会很大
```

对比模式：

```bash
python3 code/ch27/autoscale_sim.py compare \
  --traffic traffic-trace.csv \
  --strategy reactive --strategy scheduled --strategy warm-pool \
  --strategy admission-only
```

四种策略在同一段流量上对比，输出各自的 `unmet_demand` 和成本。

**`admission-only` 这一项是刻意加进来的对照。** 它不做任何扩缩容，只靠准入控制。在突发为主的流量上，它的表现常常好于纯反应式弹性，而成本更低。**这个对照能防止“弹性一定更好”的直觉。**

**本章的模拟尚未用真实流量轨迹跑过。** GX10 恢复后要做的是：用一段真实的日内流量重跑四种策略，验证结论。

## 27.9 课堂案例与常见误区

### 案例一：配了自动扩容，突发时照样挂

服务配了基于 GPU 利用率的自动扩容，阈值 80%，最大 30 个实例。

一次热点事件让流量在 90 秒内涨到 4 倍。扩容确实触发了，但第一个新实例 6 分钟后才就绪。这 6 分钟里服务完全不可用，而且因为没有准入控制，所有请求都堆在队列里一起超时。

事后加了准入控制，同样量级的突发只影响了约 35% 的请求，其余正常返回。

讨论：这个场景下，把最小实例数调高能解决问题吗？代价是什么？

### 案例二：缩容之后延迟全面上升

夜间流量下降，自动缩容从 12 个实例缩到 4 个。第二天早高峰扩回 12 个后，P95 TTFT 比前一天高了 60%，持续了近两小时。

原因是缩容和扩容都用简单取模哈希做路由，实例数每次变化前缀归属就全变，Prefix Cache 从零开始重建。12 个实例各自预热缓存要很久。

换成一致性哈希后，同样的扩缩容只影响约六分之一的前缀，恢复时间从两小时降到十几分钟。

讨论：除了一致性哈希，还有什么办法能减少扩缩容对缓存的冲击？

### 案例三：加了一倍的卡，吞吐只涨了六成

从 8 个实例扩到 16 个，期望吞吐翻倍，实测只涨 62%。

拆开看有三处损失：轮询路由下长请求分布不均，最慢实例拖累 P99；缓存分散让命中率从 71% 降到 44%，平均 prompt 的 Prefill 变重；以及新增实例分布在另一个可用区，跨区调用增加了几十毫秒。

改成带溢出的前缀亲和路由并把实例集中到同区后，吞吐增益回到 84%。

讨论：84% 是不是就到顶了？剩下的 16% 还能再找回来吗？

### 两个不写在配置里的误区

误区一：自动扩缩容是弹性的全部。

它只覆盖小时到天尺度的趋势性变化。日内周期用定时扩缩容更好，因为可预测；秒级突发只能靠准入控制和预留余量。把三类变化混在一起用一套机制应对，结果是每一类都应对不好。

误区二：缩容和扩容用同一套参数就行。

扩错了多花钱，缩错了影响可用性，两者的风险不对称，参数也该不对称：缩容阈值要更低、冷却时间要更长、优雅退出的等待要比最长请求还长。用对称参数的系统会持续抖动。

## 本章总结

回到开头的三个问题。

**加一倍的卡能扛一倍流量吗？** 不能，实际按 0.8 到 0.9 折算。损失来自四处：路由不均导致最慢实例决定 P99、缓存分散让命中率下降、余量不能在实例间共享、故障域变大。前三项都能通过路由缓解，所以多副本场景下路由设计不是可选项。副本数从 1 到 4 边际收益好，超过 16 之后复杂度会吃掉相当一部分收益，那时该分层而不是继续扩同一个池子。另外模型装得下一张卡时优先单卡实例，多卡并行的通信同步在 Decode 的高频循环里会被放大。

**Autoscaling 该看什么指标？** 不是 GPU 利用率，它统计的是有没有 kernel 在跑而不是算力用了多少；也不是 QPS，因为请求长度差几十倍。应该用 Running 集合占上限的比例做主触发，它直接反映还能不能接更多请求，且比排队和抢占动得早；再用 SLO 达成率做兜底，它对齐业务目标但滞后。

**冷启动几分钟时弹性还有什么用？** 它只对趋势性增长有用。冷启动 3 到 10 分钟，而突发是秒级的，这是时间尺度上的错配。三类流量变化要用三种手段：趋势性用 Autoscaling，日内周期用定时扩缩容，突发只能靠准入控制加预留余量。缩容还要比扩容保守得多，因为风险不对称：阈值要有滞回区间、冷却时间要长得多、优雅退出要等到最长请求结束，而且实例数变化会冲击缓存，路由必须用一致性哈希。

下一章处理另一类风险：版本变了、配置变了、模型变了，怎么在上线之前就发现性能回归。

### 本章 Checklist

- [ ] 知道当前副本数下的实际扩展效率，而不是假设线性。
- [ ] 模型装得下单卡时用的是单卡实例，多卡有明确理由。
- [ ] 扩缩容的触发指标是 Running 占比，不是 GPU 利用率或 QPS。
- [ ] 知道一个新实例从触发到就绪需要多久。
- [ ] 三类流量变化各有对应手段，突发靠的是准入而非弹性。
- [ ] 缩容阈值和扩容阈值之间有滞回区间，缩容冷却时间明显更长。
- [ ] 优雅退出的等待时间大于最长请求的耗时。
- [ ] 路由用一致性哈希，实例数变化时缓存不会整体失效。
- [ ] 平时的利用率上限为滚动升级期间的容量下降留了空间。

## 课后练习

1. 把副本数从 1 加到 8，每档测吞吐，画出实际扩展效率曲线。
2. 分别用轮询和前缀亲和路由重做上一题，对比两条曲线。
3. 量出一个新实例从创建到就绪的各段耗时，找出最长的那一段。
4. 对比 GPU 利用率、QPS 和 Running 占比三个指标在一段压测中的走势，说明前两个为什么会误导。
5. 用一段真实流量轨迹跑扩缩容模拟，记录 `unmet_demand` 和抖动次数。
6. 在同一段流量上对比反应式弹性和纯准入控制两种策略的结果。
7. 做一次缩容，测量 Prefix Cache 命中率的恢复曲线。
8. 按你的实例数算出滚动升级期间的可用容量，据此定出平时的利用率上限。
