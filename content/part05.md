# Part 5 Serving、RAG 与 Agent 性能工程（Serving & Applications）

## 本篇导读

前四篇都在回答同一个问题：这一条请求在 GPU 上花了多少时间。

但线上的等待有相当一部分根本不在 GPU 上。请求在队列里排着、被限流挡着、被路由到了缓存对不上的实例；或者它压根不是一次调用，而是一条 RAG 链路上的最后一段，前面还有改写、检索和重排；再或者它是一个 Agent 任务里的第 9 步，前 8 步已经等了十几秒。

一个很常见的现象是：单次调用的监控面板全绿，P95 TTFT 480 ms、P95 E2E 3.2 秒，全部达标，而用户在投诉任务要等几分钟。

**这一篇处理的就是那段监控看不见的时间。**

## 本篇靠哪条道理

主线位置：优化，第四步里 GPU 之外的那一块，前两块动的是 GPU 上的时间。和第 0 章的关系：本篇的排队那一面是第 0 章第二条规律后半句的定量形式，“越接近满载，等待涨得越快”在这里变成一条能代入负载率的式子；放大那一面是第 0 章没有提到的一层，它说明到达量本身会被重试和多步推高，于是系统会自己往满载走。

这一篇处理 GPU 之外的时间，它依赖的道理有两面，其实是同一件事：**接近饱和时等待非线性上升；而重试和多步会放大到达量，把系统往饱和推。** 本书称之为排队与放大。

两个式子。等待那一面是 `W_q ≈ S × ρ/(1−ρ)`：ρ 是负载率（到达速率除以整个实例的满载吞吐），S 是满载吞吐的倒数，第 20.6 节会把这两个量定义清楚。ρ = 0.75 时平均排队 3 个 S，0.9 时 9 个；在 0.9 的位置上到达再多 5%，ρ 变成 0.945，排队从 9 个 S 涨到约 17 个，接近翻倍。所以“负载只多了 5%”和“延迟翻倍”可以同时成立，前提是本来就离满载很近。放大那一面是重试：首次失败率为 p、最多重试 r 次时，各次独立的放大倍数是 `1 + p + p² + … + p^r`，速记成上界 `1 + p·r`；无限重试下是 `1/(1−p)`，p 趋近 1 时发散。第 20 章讲第一面，第 21 章讲第二面，第 24 章的 Agent 把同一条请求乘上每个任务的模型调用次数，是放大的另一种形态（步数里还含纯工具步，它们不打到模型服务上）。

它在什么地方失效：两个式子给的都是形状，不是预测值。连续批处理让服务端更像多服务台而不是单服务台，曲线没有单服务台那么陡；而长输出请求把服务时间的尾部拉长，又比它更陡。用它们判断该不该留余量，别用它们承诺毫秒数。

## 本篇贯穿的三条纪律

**一、分解在优化之前，而且要在压测状态下分解。** 空闲时排队为零，分解表会完全是另一个样子，然后你会去优化一个高峰期根本不是瓶颈的环节。第 25 章那个案例里，团队花两周把单次调用的计算缩短了将近一半，端到端只改善约 7%，因为 GPU 计算只占总时长的 16%，而他们缩短的是延迟，不是满载吞吐，排队一点没动。

**二、按任务算账，不按调用算账。** Agent 场景下每次调用的指标全部达标，任务仍然可能要几分钟。累计 token 按步数的平方增长，第 6 章那个“账单是估算六倍”的案例就出在这里：六倍是步数估少 1.6 倍乘上累积 3.8 倍，第 24.3 节给出完整的账。

**三、拒绝比全员劣化好。** 过载时全部接受，结果是所有人都等很久然后都失败。准入控制把损失限制在一部分请求上，保护其余请求。一个没有准入的系统，前面四篇优化出来的余量会在第一次流量高峰时全部还回去。

- 画出 Waiting/Running/Finished 三态图，并从请求级追踪里把排队时间和 GPU 时间分开；
- 解释 Continuous Batching 为什么同时提升吞吐和增加 ITL 抖动；
- 说出四个调度参数各自管什么、正确的调整顺序，以及为什么顺序不能颠倒；
- 用排队论的敏感度解释“负载没变 P99 却跳了几倍”；
- 设计一套分层超时，并用抢占的恢复时间校准流间隔阈值；
- 说明重试为什么是过载的放大器，以及三条约束各自防住什么；
- 验证取消信号能端到端传播，量出资源释放的时间；
- 算全自建的四项成本，找出与 API 的盈亏平衡点；
- 分清全体共享的前缀和会话级前缀，解释轮询路由如何把会话级前缀的 Prefix Cache 命中率打到三成上下，并设计带溢出的前缀亲和路由；
- 做出一张 RAG 链路的时间分解表，指出查询改写和重排候选数这两处常被低估的开销；
- 说明检索质量为什么是收益最大的一类性能优化；
- 统计 Agent 的步数分布和累计 token，从长尾任务里找出浪费模式；
- 把端到端 SLO 拆成各层预算，并在预算不可达成时及早发现；
- 写出能在部署流程里自动跑的防回退断言。
