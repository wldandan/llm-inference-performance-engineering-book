# Part 1 从一个请求理解 LLM 推理系统（Understanding One LLM Request）

## 本篇导读

第 0 章交出了一条主线：运行 → 测量 → 诊断 → 优化 → 验证 → 上线守护。本篇走前两步，把服务跑起来，再把跑出来的东西变成别人能引用的数字。后面每一篇的“本篇靠哪条道理”都会先说明自己走到了哪一步，以及那一篇的道理和第 0 章三条规律是什么关系。

性能优化不能从参数表开始。工程师首先要确认服务确实能运行，再把一次请求拆成可观察的生命周期，理解模型在执行什么、Serving 系统由谁负责，最后统一性能指标。缺少这张地图，后面看到 TTFT 上升、吞吐下降或 GPU 利用率变化时，很容易把现象误判成原因。

本篇坚持“先遇到问题，再引入技术”。第 1 章先用同步请求跑通链路，再让长回答暴露出没有任何反馈的等待，从而引入流式调用。流式同时改变了“快”的含义，把一个总时长裂成“多久看到第一个字”和“字出得稳不稳”两个问题。第 2 章接着追问：当第一个问题的答案偏大时，时间究竟花在哪一段？客户端事件回答不了，于是转向服务端证据。第 3、4 章分别解释模型生成机制与 Serving 组件；第 5 章建立整门课程共用的性能语言。

读者不需要先掌握 CUDA、GPU 微架构或分布式通信。正文只在解释 Prefill、Decode 和资源指标时引入必要的硬件直觉；GPU/CUDA、NCCL、多 GPU、MoE 和 PD Disaggregation 留在附录。五个附录里目前只有附录 A《GPU 性能心智模型》写完了，正文对它的引用都能读到内容；附录 B 到 E 还只有占位文件，上面写着计划覆盖什么和正文在哪里引用了它，`content/advanced/README.md` 有完整状态表。正文引用未写的附录时，那一处的结论都已经在正文里给全，附录补的是推导和实现细节。

## 本篇主线

```text
启动真实 vLLM 服务
  -> 用同步请求跑通链路
  -> 发现没有反馈的等待，引入流式，得到多个客户端观测点
  -> 追问首包等待花在哪一段，转向服务端证据，还原请求生命周期
  -> 理解 Transformer 如何生成 token
  -> 理解 Serving 组件如何承接请求
  -> 用统一指标描述体验、产能、可靠性与成本
```

这不是六条彼此独立的知识点，而是同一个 Reference System 的逐层展开。第 1 章证明“链路通了”并留下客户端观测；第 2 章回答“请求在服务端经历了什么”；第 3 章回答“模型算了什么”；第 4 章回答“谁组织这些计算”；第 5 章回答“怎样准确描述结果”。第 3～5 章可以复用前面采集的真实报告，但必须尊重证据边界；离线工具只用于核对机制、架构合同和公式，不能替代真实服务数据。

## 本篇章节关系

| 章节 | 本章完成什么 | 明确不做什么 |
|---|---|---|
| 第 1 章 第一个 LLM 服务 | 启动 vLLM，用同步与流式两种方式完成调用，留下客户端运行记录 | 不分析服务端内部阶段，不定义性能指标 |
| 第 2 章 真实请求生命周期 | 用归一化事件描述请求在服务端的经历，采集请求级指标和 Prometheus 增量并标注证据等级 | 不用聚合指标伪造单请求时间线，不做压测 |
| 第 3 章 Transformer 生成机制 | 解释 Tokenizer、Attention、Prefill、Sampling、Decode 与 KV Cache | 不评价速度，不教授优化算法 |
| 第 4 章 LLM Serving 架构 | 解释 Gateway、Router、Admission、Scheduler、Worker、Runtime 和 GPU 的职责 | 不把架构契约检查当成运行态验证 |
| 第 5 章 性能指标与延迟预算 | 定义 TTFT、TPOT/ITL、成功输出/请求速率、分位数、SLO-aware Goodput 与成本口径 | 不设计正式 Benchmark，不做根因分析 |

五章的边界刻意收紧。特别是第 1 章与第 2 章：第 1 章的产物是客户端运行记录，它能说明调用是否成功、用户多久看到第一个字，但所有时间戳都打在客户端；第 2 章的产物是“带证据等级的生命周期报告”，它回答同一段等待在服务端如何分解。后者必须明确哪些字段来自客户端、哪些来自 vLLM、哪些只是根据缺失边界做出的推断。

## 本篇靠哪条道理

主线位置：运行与测量，第一步和第二步。和第 0 章的关系：三条规律在这一篇一条都用不上，本篇要立的是使用它们的前提。第 0 章 0.6 说过“规律只给假设，结论要靠测量”，这一篇就是把那句话变成一条可执行的判据。

五章看起来在讲五件不同的事，底下只有一条道理：**你只能相信测到的那一段，而边界决定了这个数字的作用域。** 这条道理本书称为观测边界。

它的判据很具体：一个性能数字要能写出三件事，从哪个事件开始、到哪个事件结束、由谁记录。三样齐了它才是一个可以被引用的数字；缺一样，它只是一个长得像数字的东西。第 1 章客户端那四个时刻、第 2 章那张四级证据表、第 5 章的指标合同，是同一条判据的三种写法。

它在什么地方失效：边界之外的事，这条道理不许你猜，但也确实不告诉你答案。客户端只能看到首个分片，服务端的排队和 Prefill 各占多少，客户端的证据永远推不出来；反过来，服务端指标也说不出用户实际等了多久。两边都要采，且不能互相冒充。

## 本篇贯穿的三条纪律

**一、每个数字旁边写着它的边界。** 起止事件、记录方、统计窗口，这三样跟着数字走，不跟着章节走。第 5 章那份指标合同是它的成文形式，但纪律从第 1 章的第一条 curl 就开始生效：那一行 `total` 是客户端的墙钟时间，不是服务端的处理时间。

**二、不可得就写不可得。** 没采到的阶段写成 `null` 或 `unavailable`，不写 0。写成 0 的那一刻，这个字段就从“缺证据”变成了“证据表明为零”，后面每一个读这份报告的人都会被它误导，包括三个月后的你自己。

**三、客户端观测不冒充服务端事实。** 首个分片到达不等于服务端首 token，客户端与服务端的时长差值不叫网络耗时。两边各采各的，采到的归各自，中间那段说不清就写说不清。

## 学完本篇你应该能做到什么

读完 Part 1，你应该能够：

- 独立启动 OpenAI-compatible vLLM 服务，完成同步与流式两种调用，并说明流式改变了哪些可测的量；
- 区分 token、流式 chunk、请求级指标和服务端聚合指标；
- 画出 Request Received、Queue、Prefill、Decode、Streaming 和终态清理；
- 对每个生命周期结论标注“直接观测、计算得到、推断或当前不可得”；
- 解释 Transformer 的自回归生成过程，以及 KV Cache 在 Prefill/Decode 间的作用；
- 画出 LLM Serving 的核心组件与责任交接关系；
- 为 TTFT、TPOT/ITL、成功输出/请求速率、P95/P99、Goodput 和成本写出测量合同；
- 拒绝用单请求结果、GPU Utilization 或聚合直方图增量直接证明根因。
