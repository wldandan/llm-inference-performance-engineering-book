# 第 3 章 Transformer 生成机制：模型怎样生成下一个 token

## 学习目标

读完这一章，你应该能回答三个问题：

1. 一段文本怎样变成模型能算的数字数组，模型又怎样把它变回一个 token？
2. 同一个模型，为什么 Prefill 一次吃完整段 prompt，Decode 每次只吃一个 token？KV Cache 在中间起什么作用？
3. 拿到一份真实请求的 token 与分片计数，怎样把它落回这条机制路径？

跟着做完，你会得到一张从文本到下一个 token 的数据流图，以及一份把真实请求的 token 计数落回 Prefill 与 Decode 的机制说明。

## 3.1 从文本到下一个 token

第 2 章从请求视角给生命周期划了阶段：首次调度之后先是 Prefill，首 token 之后是 Decode。那一章只说了它们在时间线上的边界，没有说模型在这两段里到底算了什么，也没有说为什么非得分成两段。本章暂时越过 Serving 组件，直接观察模型计算；第 4 章再把这些计算放回 Gateway、Scheduler、Worker 与 Runtime 的职责关系中。

本章只讲机制，不评价速度。TTFT、TPOT 和成功输出 token 速率怎样定义，放到第 5 章；这些计算为什么会慢、怎样优化，放在后续 Part 与 GPU 架构附录。

一次模型调用可以先压缩成一条七个环节的链：两端是输入的文本和输出的 token，中间五个是动作。右边标的是每个动作交出什么。

```text
文本
  -> Tokenizer / Chat Template      交出 Token IDs
  -> Embedding                      交出 Hidden States
  -> N 个 Transformer Blocks        交出 Hidden States
  -> Final Norm + LM Head           交出 Logits
  -> Sampling                       交出 一个 token ID
  -> 下一个 token
```

Token IDs、Hidden States 和 Logits 是数据，不是步骤。把它们数成环节，这条链就会变成九个，和图 3-1 对不上。

Tokenizer 把字符串切分并映射成整数 ID。Embedding 根据每个 ID 查表，得到 hidden state。随后，hidden state 依次穿过多层 Transformer Block。最后的 LM Head 把 hidden state 投影到词表维度，为词表中的每个 token 产生一个 Logit。Sampling 再从这组分数中选出一个 token。

模型并不是直接输出“字”。它每次输出 token ID，客户端最后看到的文本来自 Tokenizer 的反向解码。中文字符、英文单词、空格和标点如何组合，取决于模型使用的词表。

后面的讲解都用课程 Demo 的模型 Qwen2.5-0.5B-Instruct 举例，它的主要配置是：

| 配置项 | 数值 | 在本章哪里出现 |
|---|---:|---|
| Transformer 层数 | 24 | 3.3，同样的 Block 重复 24 次 |
| hidden size | 896 | 3.2，每个 token 的向量长度 |
| MLP 中间维度 | 4864 | 3.3，MLP 先扩展再投影回来 |
| Query 头数 | 14 | 3.4、3.5 |
| KV 头数 | 2 | 3.5，GQA |
| 每个头的维度 | 64 | 3.4、3.5 |
| 词表大小 | 151936 | 3.1，LM Head 为每个 token 打一个分 |

最后一行意味着，模型每生成一个 token，LM Head 都要给 15 万多个候选各打一个分，Sampling 再从里面挑一个。

推理时会同时遇到三类数据。把它们分开，后面理解显存、并发和请求隔离会容易很多：

| 数据 | 生命周期 | 典型内容 | 是否随请求变化 |
|---|---|---|---|
| 模型参数 | 模型加载后长期存在 | Embedding、Attention、MLP、LM Head 权重 | 通常不随请求变化 |
| 临时激活 | 一次 forward 内产生和消费 | hidden states、Q/K/V、Attention 输出、Logits | 随 batch、序列和执行步骤变化 |
| 请求状态 | 从 Prefill 延续到 Decode | KV Cache、采样状态、已生成 token | 每条请求独立增长并在终态交接或回收 |

模型参数回答“模型学到了什么变换”，临时激活回答“这一轮正在算什么”，KV Cache 回答“这条请求已经处理过哪些历史位置”。KV Cache 由模型计算产生，却属于在线请求状态，不应和模型权重混成一类。

## 3.2 Tokenizer、Chat Template 与 Embedding

聊天模型收到的输入通常是 messages，而不是一段已经拼好的纯文本。Chat Template 会插入角色标记、分隔符和生成起始标记，然后 Tokenizer 才把序列编码成 token IDs。

例如，同样一句“你好”，作为 system、user 或 assistant 内容时，最终输入序列可能不同。服务端看到的 prompt_tokens 因此不只取决于用户可见字符，还包括模板添加的控制 token。第 1 章那次请求只发了一句“请用三句话介绍 LLM 在线推理。”，服务端报告的输入却是 30 个 token，模板加进去的控制 token 就在其中。

得到 token IDs 后，模型使用 Embedding 矩阵查找向量。若 batch 为 B、序列长度为 S、hidden size 为 H，那么：

```text
token_ids:      [B, S]
hidden_states:  [B, S, H]
```

放到那次请求上，B 是 1，S 是 30，H 是 896：30 个整数变成了 30 个长度为 896 的向量。

Embedding 不理解词义，它只是一个可训练查找表。上下文关系要等 hidden states 进入 Transformer Blocks 后才逐层形成。

现代模型还需要位置信息。Qwen2.5 使用 RoPE，它不像 GPT-2 那样再查一张绝对位置 Embedding 表并与 Token Embedding 相加，而是在下一步的 Attention 里直接作用到 Query 和 Key 上。

> **RoPE**（Rotary Position Embedding）：旋转位置编码，按 token 所在位置把 Query 和 Key 向量旋转一个角度。
> 两个位置做点积时，结果自然带上了它们的相对距离，模型因此知道“谁在谁前面、隔了多远”。它只改 Query 和 Key，不改 Value。

## 3.3 Decoder-only Transformer Block

在线生成常用 Decoder-only Transformer。以 Qwen2.5 一类现代模型为例，一个 Block 可以写成：

```text
x = x + Attention(RMSNorm(x))
x = x + MLP(RMSNorm(x))
```

两次 RMSNorm（Root Mean Square Normalization）按向量自身的均方根做缩放，把输入拉到更稳定的数值范围。Attention 让当前位置读取允许访问的上下文，MLP 则对每个位置的表示单独做一次非线性变换。两个子层外面的 Residual Connection 把输入直接加回输出，让前面各层的信息能一路传下去。

MLP 的数据流很简单：把每个位置 896 维的向量扩展到 4864 维，做非线性变换，再投影回 896 维。Qwen2.5 在这里用的结构叫 SwiGLU，扩展这一步并行走两路，其中一路经过激活函数后当作开关，逐元素乘到另一路上，再投影回去。本章只需要认出“先扩展、再投影回来”这条数据流，中间维度 4864 决定了这部分的计算量，第 11 章会用到它。

一个模型有 N 层 Block，同样的结构会重复 N 次，Qwen2.5-0.5B 是 24 次，但每层使用自己的参数。最后再经过 Final RMSNorm 和 LM Head，得到 Logits。

## 3.4 Causal Self-Attention

读这句话：“小明把书借给了小红，因为她明天要考试。”要理解“她”指谁，读者会回头在前文里找一个合适的名字。Attention 做的是同一件事：让每个位置去前文里找和自己相关的位置，把那里的信息取回来。

为此，模型从当前层的 hidden states X 生成三组向量：

```text
Q = X Wq
K = X Wk
V = X Wv
```

Query 是当前位置发出的“我在找什么”，Key 是每个位置挂出的“我能被什么匹配”，Value 是匹配上之后真正要取走的内容。“她”这个位置的 Query 与“小红”位置的 Key 点积较大，于是“小红”的 Value 在加权求和里占的比重也更大。单个 Attention Head 的核心计算可以写成：

```text
Attention(Q, K, V)
  = softmax(Q Kᵀ / sqrt(d) + causal_mask) V
```

Q 与 K 的点积产生相关性分数。这里的 `d` 是每个头的维度，维度越大，点积累加出来的数值也越大；除以 `sqrt(d)` 是把分数拉回一个稳定的范围，否则 Softmax 会被少数几个特别大的分数占满，其余位置的权重被压到接近零。缩放、加上掩码、经过 Softmax 变成权重之后，再对 V 做加权求和。

Decoder-only 模型必须使用 Causal Mask。第 i 个位置只能访问自己和之前的位置，不能偷看未来 token。对 Prompt 做 Prefill 时，所有位置虽然可以并行计算，但每个位置仍受同一个因果约束。

这条约束有一个对推理非常关键的推论：**历史位置的 K 和 V 一旦算出来，就不会再变。** 第 j 个位置的 K 和 V 只取决于第 j 个及之前的 token，后面再追加多少个新 token，都影响不到它。所以生成下一个 token 时，前面所有位置的 K 和 V 可以直接从上一次的计算里拿来用，不必重算。把它们按层保存下来的那块存储，就是 KV Cache。它怎样被写入、怎样被读取，3.6 和 3.8 会逐步展开。

## 3.5 GQA：为什么 K/V 的头数比 Query 少

Multi-Head Attention 把 hidden dimension 切成多个 Head。不同 Query Heads 可以关注不同模式，再把各 Head 输出拼接并投影回 hidden size。

在标准 MHA 中，Query、Key、Value 的 Head 数相同：

```text
Q heads = 14
K heads = 14
V heads = 14
```

上一节说，历史 K/V 可以存下来反复用。代价是这份存储要按每一层、每个 KV 头、每个历史位置保留，而且每生成一个新 token，都要把它们读一遍。以 Qwen2.5-0.5B 的尺寸、每个数占 2 字节算，如果 K/V 也有 14 个头，每个 token 在 24 层里要存的 K/V 是 84 KiB（2 × 24 × 14 × 64 × 2 = 86016 字节，开头的 2 是 K 和 V 各一份）；上下文一长、并发一多，这部分很快会超过模型权重本身。

> 本书凡是讲显存占用的数字，一律用二进制单位（KiB、MiB、GiB），因为显存分配器和框架日志就是按这个口径报的；带宽和权重字节数用十进制单位（GB、GB/s），因为厂商规格书是十进制。这条口径在第 11.3 节展开，本章先照着用。

Grouped Query Attention 针对的正是这一点：既然 K/V 的存储和读取是负担，那就少留几组，让多个 Query Heads 共享同一组 K/V。Query 侧的表达能力基本保留，K/V 侧的数量成倍下降。

以课程 Demo 的配置为例：

```text
num_attention_heads = 14
num_kv_heads        = 2
queries_per_kv_head = 14 / 2 = 7
```

因此一共有 2 个 KV Heads，每个 KV Head 被 7 个 Query Heads 共享。这里的 `7` 是每个 KV Head 对应的 Query Head 数，不是 KV 组数。若 batch 为 B、序列长度为 S、head dimension 为 D，逻辑形状是：

```text
Q: [B, 14, S, D]
K: [B,  2, S, D]
V: [B,  2, S, D]
```

每个 token 要存的 K/V 随之从 84 KiB 降到 12 KiB（2 × 24 × 2 × 64 × 2 = 12288 字节），正好少了七倍。第 11 章按上下文长度放大的就是这个 12 KiB。GQA 不代表只有两个 Attention Heads，Query 仍有 14 个 Head，只是需要保存和读取的 K/V Head 更少。这笔账按上下文长度和并发数怎样放大，第 11 章会算完整；它对生成速度和容量的影响，要到第 15、16 章结合真实测量才能回答。

## 3.6 Prefill：一次处理整段 Prompt

模型第一次看到请求时，输入不是一个 token，而是完整 Prompt 的 S 个 tokens。所有 Prompt 位置依次通过 Embedding 和 N 层 Transformer Block，这次前向过程称为 Prefill。

它之所以能一次处理整段，是因为 Prompt 里的每个 token 在请求到达时就已经全部知道了。因果掩码只规定“谁能看谁”，并不要求一个位置算完再算下一个，所以 30 个 Prompt 位置可以放进同一次前向计算里一起算。

Prefill 做两件关键事情：

1. 为每一层、每个 Prompt 位置计算 Key 和 Value，并写入 KV Cache。
2. 取得最后一个 Prompt 位置的 Logits，用于选择第一个输出 token。

模型实际上会为每个输入位置产生 Logits，但自回归生成只需要最后一个有效位置的 Logits 来继续。经过 Sampling 后得到第一个输出 token。

需要注意顺序：

```text
Prompt tokens
  -> Prefill forward
  -> last-position logits
  -> Sampling
  -> first generated token
```

所以“Prefill 完成”与“第一个 token 已被选出”并不是同一个计算动作。前者产生 Logits，后者由 Sampling 决定具体 token。服务端何时记录 first_token 事件，还会受到框架埋点位置影响，这正是第 2 章把这一段叫作 Scheduled-to-First-Token 的原因。

![Prefill](figures/fig03-05_prefill_execution.svg)

图3-5：Prefill 写入整段 Prompt 的 K/V，并为首个输出 token 产生 Logits。

## 3.7 Sampling：从 Logits 选择 token

Logits 是一组未归一化分数，长度等于词表大小。Sampling Pipeline 通常先做温度缩放，再根据 Top-k、Top-p 等规则缩小候选集合，最后选出一个 token。

Temperature 的简化公式是：

```text
p_i = softmax(logit_i / temperature)
```

温度较低时，较大的 Logit 会获得更集中的概率；温度较高时，概率分布更平。部分推理 API 把 Temperature 等于零约定为 Greedy Decoding；本章教学 Demo 为避免把“约定”混入 Softmax 数学，只接受大于零的 Temperature。需要 Greedy 时，直接选择最大 Logit，而不是执行除零。

Top-k 只保留分数最高的 k 个候选，Top-p 则保留累计概率达到阈值的一组候选。两者可以单独使用，也可以组合。采样规则会影响输出多样性和可复现性，但本章不讨论答案质量评测。

Sampling 每一步都要执行。Prefill 后采样出第一个输出 token；每个 Decode step 又产生新 Logits，再采样下一个 token。直到遇到 EOS、Stop Sequence、最大输出长度或取消信号，生成才结束。

## 3.8 Decode：一次消费一个新 token

Prompt 可以一起算，输出却不行。第 2 个输出 token 该是什么，取决于第 1 个输出 token 是什么，而第 1 个要等 Sampling 选出来才知道。每个新 token 都卡在上一个 token 的选择上，所以生成只能一步一步来：选出一个，把它送回模型，再算下一个。这就是 Decode。

第一个输出 token 被选出后，它成为下一次模型前向的输入。此时不需要重新计算整个 Prompt，因为 3.4 说过，历史位置的 K/V 不会变，Prefill 已经把它们存进了 KV Cache。

普通 Decode step 的数据流是：

```text
new token
  + past_key_values
  -> one-token forward
  -> append this token's K/V
  -> next-token logits
  -> Sampling
  -> next token
```

假设 Prompt 长度为 8：

| 执行 | 本次输入 token 数 | 执行后 KV Cache 长度 | 产生的输出 |
|---|---:|---:|---|
| Prefill | 8 | 8 | 第 1 个输出 token |
| Decode step 1 | 1 | 9 | 第 2 个输出 token |
| Decode step 2 | 1 | 10 | 第 3 个输出 token |
| Decode step 3 | 1 | 11 | 第 4 个输出 token |

KV Cache 保存的是每一层历史 token 的 Key 和 Value，不是完整 hidden states，也不是已经生成的文本。新一步仍然要计算当前 token 的 Q/K/V、Attention、MLP 和 LM Head，只是历史 K/V 可以复用。

这张表也解释了一个容易混淆的计数：Prefill 后已经采样出第一个 token，再执行 3 个 Decode steps，总共会得到 4 个输出 tokens。Decode step 数不总是等于最终输出 token 数。

KV Cache 省下了多少，可以换一种算法看出来。假设没有它，每生成一个 token 都要把 Prompt 和已经生成的内容整段重新过一遍模型。以第 1 章那次请求为例，Prompt 30 个 token，输出 256 个：

| 要得到的输出 | 没有 KV Cache，这一步要算的位置数 | 有 KV Cache，这一步要算的位置数 |
|---|---:|---:|
| 第 1 个（Prefill） | 30 | 30 |
| 第 2 个 | 31 | 1 |
| 第 100 个 | 129 | 1 |
| 第 256 个 | 285 | 1 |
| 256 个合计 | 40320 | 285 |

没有缓存时，越往后生成，每一步重算的前缀越长；有了缓存，Prefill 之后每一步只算 1 个新位置。

表里那两个 285 不是巧合，是同一个式子 `30 + 255`：**用了缓存，整整 256 步加起来的计算量，正好等于不用缓存时光算最后那一步的量。** 换句话说，KV Cache 把这次生成的计算量压到了原来的 0.7%。

代价是 KV Cache 要占显存，并且随生成长度一路增长，这就是 3.5 那笔账的来源。

## 3.9 这些机制在后面会变成哪些性能问题

本章没有评价任何速度，但前面几节已经埋下了后面各章要处理的几个问题：

| 本章的机制 | 后面会遇到的问题 | 在哪一章展开 |
|---|---|---|
| Prefill 一次算完整段 Prompt，每个位置都要和前面所有位置做 Attention | Prompt 越长，首 token 前的计算越多，Attention 这部分增长得比长度更快 | 第 11 章 |
| Decode 每一步只算 1 个位置，却要把整个模型过一遍 | 每一步都要读一遍全部权重，瓶颈常在搬数据，而不在计算 | 第 15 章 |
| KV Cache 按层、按 KV 头、按位置保存 | 显存随上下文长度和并发数线性增长，决定能同时服务多少请求 | 第 16 章 |

这张表只做指引，不给数字。数字要等后面的章节在真实服务上测出来。

## 3.10 Demo：用机制检查器核对形状与执行步

`code/ch03/mechanics.py` 是辅助机制检查器，只依赖 Python 标准库。它不会加载模型，也不生成真机性能数据；它负责把配置关系转换成可核对的张量形状、采样候选和 KV Cache 长度变化。

从 Git 仓库根目录运行：

```bash
python3 code/ch03/mechanics.py \
  --prompt-tokens 8 \
  --decode-steps 4 \
  --temperature 1.0 \
  --top-k 3 \
  --seed 7
```

输出分为三部分：

- shapes：Token IDs、Hidden States、Q/K/V、Attention Output、MLP Intermediate 和 Logits 的形状。例如 query 是 `[1, 14, 8, 64]`，key 是 `[1, 2, 8, 64]`，MLP 中间结果是 `[1, 8, 4864]`，与 3.1 的配置表一一对应。

## 3.11 课堂案例与常见误区

### 案例一：把一次真实请求还原成模型动作

打开第 1.8 节那份 GX10 客户端流式报告 `content/ch01/evidence/gx10-streaming-client-report.json`，只读取三个字段：`prompt_tokens=30`、`output_tokens=256`、`stream_chunks=254`。前两个来自服务端 usage，第三个是客户端计数。课堂任务不是评价速度，而是把它们放回本章的数据流。

先画出一次 Prefill：30 个输入 token 经过 Embedding 和全部 24 层 Block，KV Cache 长度先覆盖 30 个历史位置，最后一个 Prompt 位置的 Logits 经过 Sampling 产生第一个输出 token。随后画出自回归循环：新 token 成为下一步输入，历史 K/V 被读取，新 K/V 被追加，再产生下一组 Logits。

```text
30 个 Prompt tokens
  -> 1 次 Prefill
  -> 采样得到第 1 个输出 token
  -> 继续生成其余 255 个输出 tokens
  -> KV Cache 最终覆盖 285 个位置
```

这不是说服务端一定执行了 255 次彼此独立的 GPU 提交。Serving 引擎会组织 batch 和 iteration，某些生成技术也可能让一次模型执行接受多个 token。本章能确定的是模型输出 token 的逻辑依赖；引擎怎样调度这些计算属于第 4 章和后续优化章节。254 这个数则不属于模型，它是第 2 章 2.7 说的网络分片结果。

讨论：

1. 为什么 256 个输出 tokens 不等于 256 个 Decode steps？
2. 这份报告没有模型内部张量，哪些结论来自 Transformer 的定义，哪些来自报告的直接观测？
3. 按 3.5 的尺寸，这次请求结束时 KV Cache 大约占多少？这个数能不能说明显存够用？

### 案例二：同一个问题问两遍，答案从第三句开始不一样

一名工程师用同一段 Prompt、`temperature=0.8` 连续调用两次，前两句完全相同，从第三句开始分叉，之后越走越远。他怀疑服务出了问题。

服务没有问题。非零温度下，每一步都是按概率抽样，Logits 相同也不保证选中同一个 token。某一步选出不同 token 之后，它就成了下一步的输入，后面的上下文全都变了，于是整段答案一路分叉。

讨论：改成 Greedy Decoding 后，同样的输入是否一定得到同样的输出？还需要固定哪些模型、运行时和请求条件？

### 两个不写在数据流图里的误区

误区一：Decode 每一步只算一个 token，所以每一步的计算量是固定的。

新 token 的 Query 要和 KV Cache 里所有历史位置的 Key 做点积，还要按权重汇总所有历史 Value。上下文越长，这一部分的工作量越大。“只输入一个 token”说的是输入长度，不是计算量；第 15 章会把这笔账和读权重的那部分放在一起算。

误区二：Agent 发起下一次 LLM 调用时，上一次调用的 KV Cache 会自动接着用。

对模型来说，把工具结果拼进上下文后发起的新调用，就是一段新的 Prompt，要重新经过 Tokenizer、Prefill、Sampling 和 Decode。前一次调用算出的 K/V 能不能复用，取决于 Serving 系统有没有做前缀缓存、缓存有没有被回收，而不是模型机制自带的能力。第 13 章讲 Prefix Cache，第 24 章讲 Agent 场景下的调用链。

## 本章总结

回到开头的三个问题。

**文本怎样变成张量，又怎样变回一个 token？** Tokenizer 和 Chat Template 把 messages 切成 token IDs，Embedding 查表得到 hidden states，随后穿过 N 层 Transformer Block。每层里 Attention 让当前位置去前文里找相关的位置并取回信息，MLP 做逐位置变换，残差和 RMSNorm 保证信息能跨层传下去。最后 Final Norm 与 LM Head 把 hidden state 投影到词表维度得到 Logits，Sampling 再从中选出一个 token。以 Qwen2.5-0.5B 为例，30 个 token 变成 30 个 896 维向量，穿过 24 层，最后为 15 万多个候选各打一个分。模型每次只输出 token ID，文本是 Tokenizer 反向解码出来的。

**为什么 Prefill 和 Decode 是两种执行形态？** 两者用的是同一组参数，差别在于输入是不是事先知道。Prompt 的 token 在请求到达时就全部已知，可以放进一次前向计算一起算完，同时为每层每个位置写入 K/V，并取最后一个位置的 Logits 采样出第一个输出 token。输出的每个 token 都要等上一个被选出来才知道，所以只能一步一步生成。因果掩码保证了历史位置的 K/V 不会被后面的 token 改变，这才让它们可以存进 KV Cache 反复使用：第 1 章那次请求如果不缓存，256 个输出要算 40320 个位置，缓存后只要 285 个。KV Cache 保存的是每层历史 token 的 Key 和 Value，不是完整 hidden states，也不是已生成的文本；GQA 让它的体积在 Qwen2.5-0.5B 上少了七倍。

**真实计数怎样落回这条路径？** 第 1 章报告里的 `prompt_tokens=30`、`output_tokens=256`、`stream_chunks=254` 分别对应三件不同的事：30 个 token 进入一次 Prefill；256 是模型产出的 token 总数，其中第 1 个来自 Prefill 后的采样，其余 255 个来自 Decode；254 个分片则是网络行为的结果，不能反推模型执行了多少次。能确定的是 token 之间的逻辑依赖，引擎实际怎样调度这些计算属于第 4 章。

下一章把这些计算放回 LLM Serving，解释 Gateway、Scheduler、Worker、Runtime 和 GPU 如何把一条请求组织成多轮模型执行。
