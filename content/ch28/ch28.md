# 第 28 章 性能回归与发布门禁：让变慢在上线前就被拦住

## 学习目标

读完这一章，你应该能回答三个问题：

1. 性能回归为什么大多是悄悄发生的？
2. 一次自动化 Benchmark 要满足什么条件，结论才能用来卡上线？
3. 门禁阈值该怎么定，才不会天天误报又漏掉真问题？

跟着做完，你会得到一套可接进 CI 的发布门禁：自动 Benchmark 脚本、阈值定义、Shadow 与 Canary 的判据，以及阻断规则。

## 28.1 变慢从来不是一次发生的

第 25 章那个案例：优化完成后端到端 7.8 秒，三个月后回到 15 秒，而这期间没有任何告警触发。

这不是意外，是常态。**性能退化的典型形态是持续的小幅累积，而不是一次跳变。**

```text
一次框架升级     某个默认值变了，某条快速路径失效，慢 8%
一次业务变更     prompt 里多加了一段说明，慢 5%
一次知识库扩容   检索变慢，片段变长，慢 12%
一次模型升级     层数多了两层，慢 6%
一次配置调整     有人为了排查问题关了某个开关，忘了打开，慢 9%
```

每一项单独看都在噪声范围内，都不会触发告警。但半年下来是两倍。

**告警发现不了这类问题**，因为告警的阈值是按“当前正常水平”设的，而当前正常水平自己在漂移。

**能发现它的只有一件事：每次变更都和一个固定的基准对比。** 这就是发布门禁。

## 28.2 门禁 Benchmark 的三个硬条件

第 7 章那套 Baseline 方法在这里要加严，因为结论要用来阻断上线。

**条件一：可复现，且波动已知。**

第 7 章讲过：不可复现的 Baseline 比没有更糟。用于门禁时更严重：波动大意味着要么天天误报，要么阈值被迫放宽到漏掉真问题。

所以门禁 Benchmark 要先解决波动：固定随机种子、独占测试机、固定 GPU 频率、足够的重复轮次。**变异系数压到 3% 以内，门禁才有意义。**

**条件二：环境完全固定，且被记录。**

```text
模型 revision、框架版本、驱动版本、GPU 型号
所有启动参数
workload 描述文件及其哈希
测试机标识
```

**其中最容易漏的是 workload 的哈希。** 有人改了测试数据集，性能数字变了，但没人知道是数据变了还是代码变了。

**条件三：跑得够快，但不能太短。**

门禁要接进 CI，跑两小时没人会用。但跑太短会让波动变大。

实践上的折中是分层：

```text
每次提交     快速检查，3 到 5 分钟，只跑核心场景，宽阈值
每日         完整 Benchmark，30 到 60 分钟，全场景，严阈值
每次发布     完整 + Shadow 对比
```

**快速检查的作用是拦住明显的问题，不是拦住所有问题。** 把它和完整 Benchmark 混为一谈，结果通常是两边都做不好。

## 28.3 阈值怎么定

阈值太紧天天误报，太松形同虚设。定阈值有三条可操作的原则。

**一、阈值必须大于实测波动。**

变异系数 3%，阈值就不能设在 3% 以内，否则正常波动会持续触发。经验做法是设在两到三倍波动处，比如 8%。

**二、不同指标用不同阈值。**

```text
P50 延迟      波动小，阈值可以严，5%
P95 延迟      波动大，阈值放宽，10%
P99 延迟      波动很大，用作观察不用作阻断
吞吐          波动小，5%
显存峰值      几乎不波动，阈值可以很严，2%
```

**显存那一项值得单独说。** 它波动极小，所以任何超过 2% 的变化都是真实的变化，非常适合用来发现“某个配置悄悄改了”这类问题。

**三、绝对值和相对值都要有。**

```text
相对   比基线慢超过 8%     → 阻断
绝对   P95 TTFT 超过 SLO   → 阻断
```

只有相对阈值时，性能会以每次 7% 的速度慢慢退化而永不触发。加上绝对阈值能兜住这个。

**基线怎么更新是一个容易出错的地方。** 如果每次通过就把基线更新成当前值，那 7% 的退化会被逐次接受，绝对阈值也救不了太久。

**推荐的做法是基线只在两种情况下更新：** 一次明确的性能改进被验收，或者一次明确的、被接受的退化（比如为了新功能付出的代价）。**两种情况都需要人工确认，不能自动。**

## 28.4 静默回归：只看延迟发现不了的那些

有一类回归不体现在延迟上，但后果同样严重。第 17 章和第 18 章各出现过一例。

**一、输出质量悄然下降。**

第 17 章那个案例：量化后通用评测只掉 0.3 个百分点，但结构化输出的 JSON 格式错误率从 0.2% 涨到 4.1%。延迟、吞吐、显存全部正常。

**门禁必须包含质量检查项**，且要覆盖格式遵循、长回答、专业领域这几个容易先坏的维度。

**二、配置在不知不觉中改变。**

某次升级后框架对某个参数的默认值做了调整，Attention 退回朴素实现。第 18 章那个案例里性能掉一半，但如果那次只掉 6%，就会被当成噪声。

**能发现这类问题的是断言，不是阈值：**

```text
实际走的 Attention kernel 名称在白名单内
Prefix Cache 处于启用状态
量化配置与声明一致
CUDA Graph 捕获的档位数在预期范围
显存占用在预期区间
```

**这些断言检查的是“系统是不是按我以为的方式在跑”**，和性能数字是两回事。第 25 章那份 `guard` 规则就是这个。

**三、高峰期才显现的退化。**

一个改动让排队行为变差，但在门禁的中等压力下完全看不出来，只在接近饱和时爆发。第 20 章那条排队敏感度曲线解释了原因：饱和区附近，很小的容量变化会导致延迟大幅变化。

**所以门禁 Benchmark 至少要包含一档接近饱和的压力**，而不只是测舒适区。

## 28.5 Shadow 与 Canary：用真实流量验证

门禁 Benchmark 用的是合成负载，而合成负载不可能覆盖真实流量的全部形态。

**Shadow（影子流量）：** 把生产流量复制一份发给新版本，结果丢弃，只看性能和质量指标。

```text
优点   零用户风险，能用真实流量分布
限制   新版本要有独立资源，成本翻倍
注意   有副作用的操作必须屏蔽，否则会重复写入
```

**Shadow 特别适合验证第 28.4 那三类静默回归**，因为真实流量里才有那些边缘形态。

**Canary（金丝雀）：** 把一小部分真实流量切给新版本，正常返回结果。

```text
优点   能观察真实用户行为和端到端影响
风险   受影响的是真实用户
判据   小流量下的指标能不能代表全量
```

**Canary 有一个 LLM 特有的陷阱：缓存效率。** 第 27 章提过：新旧版本各自维护 Prefix Cache，5% 流量的 Canary 实例缓存命中率会远低于全量时的水平。

```text
Canary 命中率低  →  TTFT 看起来更差
实际全量后       →  命中率恢复，TTFT 可能比旧版还好
```

**所以 Canary 期间的性能数字不能直接和旧版对比**，要么等缓存预热稳定后再看，要么把缓存命中率作为协变量一起分析。这是一个非常容易得出错误结论的地方。

**两者的分工：** Shadow 先跑，用来发现性能和质量问题；Shadow 通过之后再 Canary，用来验证真实用户路径。

## 28.6 门禁怎么接进流程

门禁要产生作用，必须能真的阻断，而不是发一封没人看的邮件。

```text
提交       快速检查，失败则 CI 红
合并前     完整 Benchmark，失败则不能合并
发布前     Shadow 对比 + 断言检查，失败则不能发布
发布中     Canary 指标监控，异常则自动回滚
```

**三条让门禁不被绕过的设计：**

**一、失败信息要能定位。** 只说“性能回归 12%”没人会去查。要给出是哪个指标、和哪个基线比、变化了多少、以及可能相关的变更。**门禁的可用性直接决定它会不会被绕过。**

**二、要有明确的豁免流程，而不是默认可跳过。** 有时确实需要接受一次退化，这时该走的是记录在案的豁免，包含原因和基线更新的决定，而不是“加个 skip 标签”。

**三、误报要被当成 bug 修。** 连续几次误报之后，团队就会开始习惯性忽略门禁结果，这时门禁就已经死了。误报率高说明波动没压住或阈值定得不对，要修的是门禁本身。

## 28.7 Demo：性能门禁

本章 Demo 位于 `code/ch28/perf_gate.py`，需要真实服务。

```bash
python3 code/ch28/perf_gate.py run \
  --mode quick \
  --workload workload-gate.json \
  --baseline baseline.json \
  --thresholds thresholds.json \
  --assertions guard-rules.json \
  --evalset evalset-gate.jsonl \
  --output gate-result.json
```

`--mode` 取 `quick`、`full`、`release` 三档，对应 28.2 那三层。

输出：

```text
environment     完整环境指纹，含 workload 哈希
metrics         各指标的本次值、基线值、变化率
threshold_check 逐项通过或失败，失败项标出超出多少
assertions      逐条断言的结果
quality         评测集得分与基线对比
saturation      接近饱和档位的结果
verdict         pass / fail / warn
blocking_reason 失败时的可定位说明
exit_code       0 通过，1 阻断，2 警告
```

基线管理：

```bash
python3 code/ch28/perf_gate.py baseline promote \
  --result gate-result.json \
  --reason "Ch17 KV 量化验收，TPOT 改善 41%" \
  --approver <名字>
```

**`promote` 强制要求 `--reason` 和 `--approver`，且拒绝在 `verdict` 为 `fail` 时执行。** 这就是 28.3 那条“基线不能自动更新”的实现。

Shadow 对比：

```bash
python3 code/ch28/perf_gate.py shadow \
  --primary http://prod:8000 --candidate http://canary:8000 \
  --duration 1800 --sample-rate 0.1 \
  --output shadow-report.json
```

它复制流量到候选版本，对比两边的延迟分布、质量得分和断言结果，并**单列缓存命中率作为协变量**，防止 28.5 那个陷阱。

**本章的门禁尚未接入真实 CI。** GX10 恢复后要做的是：压低 Benchmark 的波动到 3% 以内，定出各指标阈值，把 `quick` 模式接进提交流程。

## 28.8 课堂案例与常见误区

### 案例一：门禁天天红，一个月后没人看

团队上了性能门禁，阈值统一设成 5%。

Benchmark 的变异系数是 9%，于是正常波动经常触发失败。两周后大家开始习惯性点重试，一个月后有人在 CI 配置里加了跳过条件。

真正的问题不是阈值，是波动。测试机上跑着其他任务、GPU 频率没锁、重复轮次只有 2。修掉这三项后变异系数降到 2.6%，阈值设 8% 就很稳。

讨论：波动实在压不下去时，门禁还能怎么设计？

### 案例二：每次通过就更新基线，半年慢了一倍

门禁配置成通过即更新基线。每次变更慢 4% 到 6%，都在 8% 的阈值内，于是每次都通过，每次都成为新基线。

半年后端到端时间是最初的 2.1 倍，而门禁从未失败过。

后来改成基线只在人工确认时更新，并加了绝对阈值兜底。

讨论：绝对阈值该设在哪里？SLO 那条线合适吗？

### 案例三：Canary 显示变慢了，全量后反而变快

新版本 Canary 到 5% 流量，P95 TTFT 比旧版高 34%，团队准备回滚。

有人查了缓存命中率：Canary 实例只有 21%，而生产实例是 83%。因为 5% 的流量分散在同样的前缀上，每个前缀在 Canary 上出现的频率太低，缓存建不起来。

把 Canary 比例提到 25% 并等待 40 分钟后，命中率升到 76%，TTFT 比旧版低 11%。全量后是 14%。

讨论：小流量 Canary 还能怎么排除缓存因素的干扰？

### 两个不写在门禁配置里的误区

误区一：门禁就是跑一次 Benchmark 比一下数字。

只比数字会漏掉三类静默回归：质量下降、配置悄悄改变、只在饱和区显现的退化。这三类都不体现在常规延迟指标上，需要质量评测、断言检查和饱和档位压力三样额外的手段。

误区二：门禁是 CI 的事，和性能工程无关。

阈值定在哪、基线什么时候更新、Canary 的数字怎么解读，这些都需要对系统的理解。案例三那个缓存命中率的问题，没有前面几章的铺垫根本想不到去查。门禁的配置质量决定了它是保护网还是绊脚石。

## 本章总结

回到开头的三个问题。

**为什么大多是悄悄发生的？** 因为退化的典型形态是持续的小幅累积：一次升级慢 8%、一次业务变更慢 5%、一次知识库扩容慢 12%，每一项单独看都在噪声范围内，都不会触发告警，而告警的阈值本身又是按当前正常水平设的，会跟着一起漂移。能发现它的只有一件事：每次变更都和一个固定的基准对比。

**门禁 Benchmark 要满足什么条件？** 三条。可复现且波动已知，变异系数压到 3% 以内，否则要么天天误报要么阈值被迫放宽；环境完全固定并记录，最容易漏的是 workload 的哈希；跑得快但不能太短，所以要分层，快速检查拦明显问题、完整 Benchmark 每日跑、发布前加 Shadow。另外还要包含三样常规延迟指标之外的东西：质量评测、配置断言，以及一档接近饱和的压力。

**阈值怎么定？** 必须大于实测波动，通常设在两到三倍波动处；不同指标用不同阈值，显存因为波动极小可以设得很严，很适合发现配置被悄悄改动；相对和绝对阈值都要有，否则会以每次 7% 的速度慢慢退化而永不触发。基线不能自动更新，只在明确的改进被验收或明确的退化被接受时人工更新。最后，误报要当成 bug 来修，因为连续误报之后门禁就会被绕过，那时它已经死了。

下一章把这一章的门禁、前面几章的容量与成本，合并成一次上线前的完整评审。

### 本章 Checklist

- [ ] Benchmark 的变异系数压到 3% 以内，且知道这个数字。
- [ ] 环境指纹包含 workload 文件的哈希。
- [ ] 门禁分层，快速检查和完整 Benchmark 的目标不同。
- [ ] 阈值大于实测波动，且不同指标有不同阈值。
- [ ] 同时有相对阈值和绝对阈值。
- [ ] 基线只在人工确认时更新，更新要记录原因和审批人。
- [ ] 门禁包含质量评测项，覆盖格式遵循和长回答。
- [ ] 门禁包含配置断言，能发现静默回退。
- [ ] Benchmark 包含一档接近饱和的压力。
- [ ] Canary 的性能数字排除了缓存命中率的干扰。

## 课后练习

1. 测出当前 Benchmark 的变异系数，如果超过 3%，找出三个波动来源并逐个消除。
2. 为五个关键指标各定一个阈值，说明每个阈值的依据。
3. 检查你的基线更新策略，如果是自动的，估算半年后可能累积多少退化。
4. 写出至少五条配置断言，覆盖 kernel 路径、缓存状态和显存区间。
5. 构造一份门禁用的质量评测集，说明它覆盖哪些容易先坏的维度。
6. 在门禁里加一档接近饱和的压力，对比它和舒适区档位的判别能力。
7. 做一次 Shadow 对比，记录两边的延迟、质量和断言结果。
8. 在一次 Canary 中同时记录缓存命中率，分析它对性能数字的影响有多大。
