# 前言

一个模型训练完成之后，真正每天发生的是推理。账单每天结一次，用户的等待在每一次调用里发生。把服务跑起来不难，难的是有人说它慢的时候，你能说清楚慢在哪一段、该改什么、以及改完之后凭什么说它真的快了。

这几年能用的材料不少，大致分三类。框架文档讲怎么用，论文和技术博客讲某一项技术为什么快，经验帖讲某个团队把某个参数调成了多少。三类都有用，但它们中间那条线很少有人当成一条线完整写出来：从“用户说慢”到“我能证明改完真的更快”，这段路该怎么走。写这本书，是为了补上这条线，以及它上面的三个缺口。

**第一个缺口是，别人的结论换到你的场景还成不成立，得你自己判断。** 同一项优化在长 Prompt 上是大杠杆，在短输入长输出的负载上几乎不动；同一个参数在批量 8 和批量 64 下是两个方向。配方给得再多，不如给出算式和它的适用边界。所以这本书不收录推荐参数表，只给能自己重算的式子、能自己重跑的 Demo，和一条固定的顺序：运行、测量、诊断、优化、验证、上线守护。

**第二个缺口是，性能数字普遍缺前提。** 一句“快了 40%”，不说批量、长度分布、负载水平和统计口径，换个场景就不成立；更常见的情形是，那点改善本来就落在测量波动里，而没有人发现。所以这本书要求每个数字写出产生它的条件，每条式子标出自己的失效点，并且专门用一节回答那个最朴素的问题：这次改善到底算不算数。

**第三个缺口是，RAG 和 Agent 把链路拉长之后，“推理优化”这个范围不够用了。** 单次调用的指标可以全绿，用户仍然等上几十秒：时间花在改写、检索、重排、工具等待和排队上，而这些通常不被算进推理。所以这本书把这半条链路算进来，并且按任务而不是按调用算账。

一本讲证据纪律的书，自己先得守住它。这本书给自己定了五条约束：每条式子都写出前提和它什么时候不成立，并汇总在附录 F；每个数字都带着产生它的条件，缺一项就不写进结论；样例数据凡是构造出来的一律标明合成设定，真机记录连同硬件、驱动和版本一起登记；每章的 Demo 都带单元测试，而且测试钉住的正是正文引用的那些数，改了正文忘了同步，测试会红；术语表由脚本从正文的注释生成，不手工维护。**这些约束不是为了显得严谨，而是因为这本书反复要求读者做的事，作者没有理由替自己豁免。**

性能工程是一件要在自己的服务上才算数的事。读完一遍不如把其中一章用上一次：拿你自己的负载跑一遍 Baseline，或者把一次“我觉得变快了”换成一份别人能复核的报告。第 0 章讲三条贯穿全书的规律，不启动服务也能读完；想直接动手，就从 Part 1 开始。
