# 第 21 章 流量治理与可靠性：顶不住的时候该怎么垮

## 学习目标

读完这一章，你应该能回答三个问题：

1. 流量超过容量时，系统应该怎么表现？
2. 超时和重试为什么常常让情况更糟？
3. 客户端的哪些写法会凭空放大服务端的压力？

跟着做完，你会得到一套流量治理配置：准入、超时、取消、重试、背压五项的取值和相互约束，以及一份过载演练记录。

## 21.1 容量总有被超过的一天

前面五章都在提升容量：Prefill 更快、Decode 更省、批量更满、参数更优。

但容量再高也是有限的。促销活动、上游故障后的流量回灌、某个客户的批量任务，都会让实际流量超过设计容量。

**问题不是能不能避免，而是超过的时候系统怎么表现。**

两种截然不同的表现：

```text
A. 全部接受   队列越堆越长，所有请求的延迟一起劣化
              最终全员超时，没有一个请求成功
B. 部分拒绝   超出容量的请求立即被拒
              被接受的请求延迟正常，成功返回
```

A 是默认行为，也是最坏的行为。**它把“一部分用户失败”变成了“所有用户失败”，而且失败得很慢，用户要等到超时才知道。**

这一章讲怎么让系统按 B 的方式表现。

## 21.2 准入：在门口就说不

准入控制的逻辑很简单：请求到达时，判断系统还有没有余量，没有就立即拒绝。

判据用第 20 章那三个指标：

```text
Running 占上限的比例 > 阈值   且   Waiting 队列长度 > 阈值
  → 拒绝新请求，返回 429
```

**为什么要两个条件同时满足？** 只看 Running 会在正常满载时误拒（满载但队列为空说明处理得过来），只看队列会拒得太晚（队列一旦堆起来，已经有请求在受害了）。

几个实现上的要点：

**拒绝要快。** 准入判断应该在请求进入任何昂贵操作之前完成，不要先做 tokenize 再拒绝。

**返回的信息要可用。** 429 要带上 `Retry-After`，告诉客户端多久之后再试。不给这个信息，客户端只能立刻重试，而立刻重试会加剧过载。

**要能按来源区分。** 同样是过载，内部批量任务被拒的代价远低于线上交互请求。准入策略应该支持按优先级区分，把容量留给更重要的流量。

**阈值要留出余量。** 拒绝的目的是保护被接受的请求，所以阈值要设在系统还有余力的位置，而不是已经崩了的位置。第 20 章那个 `lead_time` 就是用来定这个位置的。

## 21.3 超时：LLM 场景下不能照搬

普通 HTTP 服务设超时很直接：一个请求该在多少毫秒内返回，超了就断。

LLM 服务有两处不一样。

**第一，正常请求的耗时分布极宽。** 生成 50 个 token 和 2000 个 token，耗时差四十倍。设一个固定的总超时，要么把长请求全砍了，要么对短请求形同虚设。

**第二，流式响应下“没返回”和“卡住了”不是一回事。** 一条流式请求可能已经吐了 300 个 token，还在正常生成。按总时长判断会误杀。

所以 LLM 服务需要分层的超时：

```text
排队超时     从到达到进入 Running。超了说明系统过载，该拒绝
首包超时     从进入 Running 到第一个 token。超了说明 Prefill 异常
流间隔超时   两个 token 之间的最大间隔。超了说明卡住或被抢占
总超时       兜底，设得很宽松
```

**中间那两个才是真正有用的。** 排队超时对应准入，流间隔超时对应第 16 章的抢占，两者都能定位到具体原因。而总超时只能告诉你“慢”，不能告诉你慢在哪。

**流间隔超时的阈值要参考抢占的恢复时间。** 第 16 章说过抢占后要重算 Prefill，可能是几秒。阈值设得比它短，会把正常恢复中的请求误杀。

## 21.4 取消：省下的是真金白银

客户端断开连接后，服务端还在继续生成，这是 LLM 服务里一笔很大的隐性浪费。

和普通服务不同的是，**这里浪费的是最稀缺的资源**：那条请求占着 KV Cache 的显存，占着 Running 集合的一个位置，每一步都在消耗算力，而结果没有任何人会看到。

浪费量取决于两件事：用户中途放弃的比例，和放弃时平均已生成了多少。交互式产品里用户看到前几句话就关掉的情况很常见，这个比例可能超过一成。

**要让取消真的生效，链路上每一段都要支持传播：**

```text
浏览器/客户端断开
  → 网关感知并关闭上游连接
  → 服务端框架感知
  → 推理引擎收到取消信号
  → 请求移出 Running，KV 立即释放
```

**任何一段断了，取消就不生效。** 常见的断点是网关：很多网关在收到完整响应之前不会主动关闭上游连接，客户端断开它并不知道。

验证方法很直接：发一条长生成请求，几秒后客户端断开，观察服务端的 Running 集合大小和 KV 使用率有没有立即下降。没有下降，说明链路上有一段没传播。

## 21.5 重试：过载时最危险的那个开关

重试是可靠性的常规手段，但在过载场景下它是放大器。

```text
系统过载 → 请求超时 → 客户端重试 → 负载变成两倍 → 更过载 → 更多超时
```

这个正反馈可以在几十秒内把一个只是略微过载的系统彻底压垮。

三条纪律：

**一、只重试明确可重试的错误。** 连接失败、503、429 带 `Retry-After` 的，可以重试。超时不能无条件重试，因为你不知道服务端是不是还在处理。LLM 请求尤其如此，一次超时的请求可能已经消耗了几秒的 GPU 时间，重试等于让它算两遍。

**二、退避必须带抖动。** 固定间隔重试会让所有失败的客户端在同一时刻再次涌入，形成脉冲。指数退避加随机抖动能把这个脉冲摊开。

**三、要有熔断。** 连续失败达到阈值后，客户端应该停止重试一段时间。没有熔断的重试策略，在服务端完全不可用时会持续打满带宽，让恢复更困难。

**还有一条针对 LLM 的特殊考虑：流式请求已经吐出部分内容后失败，重试意味着从头再来。** 用户会看到已经出现的文字消失又重新生成，体验很差，而且成本翻倍。这类情况通常应该直接报错，而不是静默重试。

## 21.6 背压：让上游知道你顶不住

准入是拒绝，背压是减速。两者的区别在于背压面向的是能够调整发送速率的上游。

典型的场景是内部服务之间的调用，或者批量任务的消费端：

```text
无背压   上游按固定速率发，服务端来不及处理，队列堆积
有背压   服务端把当前余量反馈给上游，上游相应降速
```

实现方式有几种：

```text
显式信号   响应头里带当前负载水位，上游据此调整
隐式信号   限制连接数或并发数，上游自然被阻塞
配额       给每个上游分配速率配额，超了排队
```

**背压只对“能降速的上游”有意义。** 面向终端用户的服务没法让用户少点几次，那里只能用准入。所以这一节主要适用于 Agent 编排层调用模型服务、离线批处理任务这类内部链路。

**一个常见的错误是把背压和准入混用。** 对能降速的上游做硬拒绝，会触发它的重试逻辑，反而更糟；对不能降速的用户做背压，只是把等待从服务端挪到了客户端，用户感受不到区别。

## 21.7 客户端的三个写法会放大压力

第 2 章讲过客户端观测和服务端事实的区别。这里讲客户端写法对服务端的实际影响。

**一、不复用连接。** 每次请求新建 TCP 加 TLS 握手，在高频调用下这部分开销可观，而且会消耗服务端的连接资源。用连接池，且池大小要和并发匹配。

**二、同步阻塞调用。** 一个 Agent 要串行调五次模型，每次都同步等待，总耗时是五次之和。其中某些步骤本可以并行。这不增加服务端压力，但会让端到端延迟变成不必要的累加，第 24 章会展开。

**三、不设客户端超时或设得过长。** 客户端一直等着，服务端的请求就一直占着资源。客户端超时应该比服务端的总超时略长一点，让服务端有机会先做清理，但不能长太多。

**还有一个容易忽略的：流式请求的消费速度。** 如果客户端读取 SSE 流的速度跟不上生成速度，TCP 缓冲区满了之后会反压到服务端，那条请求的生成会被拖慢，而它占着的资源不会释放。客户端侧做耗时处理时，应该先把流读完再处理，不要边读边阻塞。

## 21.8 Demo：过载演练

本章 Demo 位于 `code/ch21/overload_drill.py`，需要真实服务。

```bash
python3 code/ch21/overload_drill.py \
  --url http://localhost:8000 \
  --workload workload.json \
  --ramp 0.5,1,1.5,2,3 \
  --slo-ttft 1500 --slo-itl 80 \
  --output drill-report.json
```

它按容量的倍数阶梯加压，每档记录：

```text
offered_qps      施加的请求速率
accepted_qps     被接受的速率
rejected_qps     被拒绝的速率
goodput          满足 SLO 的成功请求速率
p95_ttft         被接受请求的 TTFT
error_breakdown  错误类型分布：429 / 超时 / 连接失败
```

另外两个子命令：

```bash
python3 code/ch21/overload_drill.py cancel-check --url ...
python3 code/ch21/overload_drill.py retry-storm --url ... --retries 3
```

`cancel-check` 发一条长生成请求后主动断开，检查服务端资源是否在秒级内释放，直接验证 21.4 那条链路。

`retry-storm` 模拟带重试的客户端在过载下的行为，对比有无退避抖动时的曲线形态。

**这份演练最该看的是 `goodput` 曲线的形状：**

```text
健康   超过容量后 goodput 保持平稳，多余流量被拒
危险   超过容量后 goodput 下降，甚至跌到接近零
```

第二种形态说明准入没有生效，系统正在用全员失败的方式回应过载。

**本章的演练尚未在真机上执行。** GX10 恢复后要做的是：跑完三个子命令，确认 goodput 曲线是平稳形态，并量出取消的生效时间。

## 21.9 课堂案例与常见误区

### 案例一：加了重试，可用性反而下降

团队为提高可靠性，在客户端加了三次重试，固定间隔 1 秒。

上线后一次小的流量高峰导致部分请求超时，重试让实际负载变成三倍多，系统彻底过载，可用性从 99.5% 掉到 71%。而如果不重试，那次高峰只会影响约 4% 的请求。

改成指数退避加抖动、加上熔断、且只对 429 和连接失败重试之后，同样的高峰下可用性保持在 98% 以上。

讨论：重试策略该怎么测？在什么条件下测才能暴露这个问题？

### 案例二：用户早就走了，GPU 还在算

某对话产品统计发现，约 14% 的请求在生成过程中被用户放弃，但服务端仍然把它们生成完了。

排查发现网关在收到完整响应前不会关闭上游连接。修复后，同样的流量下并发请求数下降约一成，相当于白捡了一成容量。

讨论：除了网关，链路上还有哪些位置可能吞掉取消信号？

### 案例三：超时设成 30 秒，长请求全被砍

服务设了统一的 30 秒超时。上线后发现长文档摘要任务大量失败，因为它们本来就需要 40 到 60 秒。

把超时调到 120 秒之后，长任务正常了，但真正卡住的请求也要占 120 秒才释放，过载时恢复变得非常慢。

最终改成分层超时：排队 5 秒、首包 10 秒、流间隔 15 秒、总超时 180 秒。长任务不再被误杀，卡住的请求 15 秒内就能被识别。

讨论：这四个阈值分别该依据什么数据来定？

### 两个不写在配置里的误区

误区一：拒绝请求是失败，要尽量避免。

在过载场景下，拒绝是正确行为。它把损失限制在一部分请求上，保护了其余请求。真正的失败是全员超时：所有用户都等了很久，然后都没拿到结果，而且系统资源全部浪费在这些注定失败的请求上。

误区二：这些是运维配置，和性能优化无关。

第 20 章那个排队论的结果说明，接近饱和时延迟对负载极度敏感。准入和背压的作用是让系统不进入那个区域，这比任何单点优化对 P99 的影响都大。一个没有准入的系统，前面几章优化出来的余量会在第一次流量高峰时全部还回去。

## 本章总结

回到开头的三个问题。

**流量超过容量时该怎么表现？** 部分拒绝，而不是全部接受。全部接受会让队列越堆越长，最终所有请求一起超时，把“一部分用户失败”变成“所有用户失败”，而且失败得很慢。准入判据用第 20 章那两个指标同时满足：Running 占比高且队列有积压；阈值设在系统还有余力的位置，位置由 `lead_time` 决定。拒绝要快、要带 `Retry-After`、要能按优先级区分。

**超时和重试为什么会更糟？** 超时的问题在于 LLM 请求的耗时分布极宽，统一阈值要么砍长请求要么形同虚设，所以需要分层：排队、首包、流间隔、总超时，其中中间两项才真正能定位原因，而流间隔的阈值要留出抢占恢复的时间。重试的问题在于它是过载的放大器，超时后无条件重试尤其危险，因为服务端可能还在处理那条请求。三条纪律：只重试明确可重试的错误、退避带抖动、必须有熔断。流式已吐出部分内容后的失败通常该直接报错而非重试。

**客户端哪些写法放大压力？** 不复用连接消耗服务端连接资源；不设或设得过长的客户端超时让服务端资源迟迟不能回收；读取 SSE 流太慢会通过 TCP 反压拖慢生成而资源照占。此外还有一件不在客户端而在链路上的事：取消信号必须端到端传播，任何一段断了，用户走了 GPU 还在算，而那条请求占着最稀缺的 KV 显存。

### 本章 Checklist

- [ ] 服务有准入控制，判据基于 Running 占比和队列长度两个条件。
- [ ] 拒绝响应带 `Retry-After`，且拒绝发生在昂贵操作之前。
- [ ] 超时是分层的，至少有排队、首包、流间隔三层。
- [ ] 流间隔超时的阈值大于抢占恢复所需的时间。
