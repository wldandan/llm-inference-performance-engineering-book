# 第 30 章 端到端性能工程项目：把二十九章用在一件事上

## 学习目标

读完这一章，你应该能回答三个问题：

1. 一个完整的性能工程项目要交付什么，怎么算完成？
2. 从零开始做，二十九章的内容该按什么顺序用？
3. 怎么判断自己做出来的东西是真的站得住，而不是自己觉得好？

跟着做完，你会得到全书的最终交付物：一套可运行、可观测、可解释、可优化、有门禁的 LLM 服务，以及一份能交给别人复核的完整报告。

## 30.1 这个项目要做什么

前二十九章是分开讲的，每一章都在一个干净的前提下讨论一个孤立的问题。真实的工作不是这样：有人说“这个服务慢，你看看”，所有的前提都要你自己去建。这一章把前面的内容用在同一件事上。

项目要求是交付一个 RAG 或 Agent 服务，满足一组事先定义的 SLO，并提供完整的证据链。规模不重要，完整性重要。单卡、小模型、几百条文档的知识库完全可以，重要的是这条链上每一环都真实存在，而不是某几环用假数据糊过去。五项交付物如下：

```text
1. 可运行   服务能起来，能处理请求，有明确的启动和验收步骤
2. 可观测   请求级追踪、关键指标、能从聚合下钻到单条
3. 可解释   每个性能数字都能说清它测的是什么、在什么条件下得到的
4. 可优化   至少完成一轮完整的"定位 → 改动 → 验证"闭环
5. 有门禁   自动 Benchmark 加断言，能拦住性能回归
```

**第三项是最容易被低估的。** 前面二十九章反复出现的那些错误，绝大多数的根源都是某个数字的含义没说清：分片数当成 token 数、客户端时长差当成网络耗时、满载成本当成实际成本、Canary 的 TTFT 当成全量表现。第 5 章那份指标合同就是“可解释”的验收标准：一个数字报出来时，问题、负载、边界、时钟、窗口、单位、聚合算法、分母、失败如何计入、样本量这十项都答得上，它才算被解释了。

## 30.2 七个阶段

推荐的推进顺序如下，每个阶段对应前面的若干章，各带一组产出和一条验收判据。

阶段一，跑起来并说清楚（Ch0–Ch5）。验收判据是能说出每个阶段的时间戳来自哪里，以及哪些阶段必须写 `unavailable`。

```text
产出   一个能接请求的服务
       一份请求生命周期的时间线
       一张组件职责图
       统一的指标口径说明
       第 0 章那三条规律在你这条链路上各自对应到哪一步
```

阶段二，把负载和基准立住（Ch6–Ch7）。验收判据是同事拿着这两份文件能重跑出同一批请求和相近的数字。

```text
产出   一份含长度分布、到达模式、并发和 SLO 的 workload 描述
       一份可复现的 Baseline，含环境指纹
       Baseline 的波动数据与可识别线
```

阶段三，让系统可观测（Ch8–Ch10）。验收判据是随便指一条慢请求，能说出它慢在哪一段。

```text
产出   Request ID 贯通客户端与服务端，Trace ID 串起下游调用
       能从一条告警下钻到具体的慢请求
       一份走完假设与排除流程的根因报告
```

阶段四，Prefill 与上下文（Ch11–Ch14）。验收判据是实验报告里有“在波动内不可分辨”这类诚实结论的空间。

```text
产出   Prefill 的算术强度与量级估算，以及实测对照
       上下文成本账：TTFT 和 token 两笔
       （并发那一笔第 12 章不算，它在阶段五的容量表里）
       至少一轮含预期、护栏和边界的优化实验
```

阶段五，Decode 与显存（Ch15–Ch19）。验收判据是每个收益数字都标注了对应的批量。

```text
产出   TPOT 下限估算与实测比值
       一张容量表，含上下文长度对并发上限的影响
       一张容量表：从模型参数推到单卡并发
       Goodput 曲线与峰值批量
       五维记分卡的优化报告
```

阶段六，服务与链路（Ch20–Ch25）。验收判据是过载演练的 goodput 曲线在超容量后保持平稳。

```text
产出   部署形态的决策记录（第 22 章）
       调度参数说明与调整顺序
       流量治理五项配置与一次过载演练
       全链路时间分解表（目标负载下采集）
       Agent 项目还要一份任务级档案：步数分布与每任务模型调用次数
       （第 24 章），它是阶段七容量链的输入
       端到端优化报告与防回退断言
```

阶段七，容量、门禁与评审（Ch26–Ch29）。验收判据是门禁能真的拦住一次人为制造的回归。

```text
产出   容量与成本模型：哪个约束先满、峰值与下限卡数、
       按有用产出算的单位成本，能做假设分析
       扩缩容配置与边界说明
       可运行的性能门禁
       上线评审材料与回滚预案
```

第 0 章那三条规律不是开场白，这些验收判据就是从它们来的：

```text
规律一  写比读贵                    阶段四、五        Prefill 算术强度，TPOT 实测与搬运下限之比
规律二  批量摊薄搬运，满载拉长等待  阶段五、六、七    Goodput 峰值批量，负载率与放大，余量
规律三  只有有用的产出才算数        阶段六、七与报告  过载后 goodput 平稳，成本按有用产出算，质量是否决项
```

规律一告诉阶段四、五拿什么当下限去比，实测离下限多远，决定了还有多少可挖。规律二告诉阶段五到七为什么不能把卡用满，峰值批量、目标负载率和余量都是在这条规律的曲线上取的点。规律三决定了每一步的分母：吞吐、成本和收益都只数有用的那部分，所以过载演练看 goodput 而不是吞吐，单位成本除的是有用产出。Part 4、5、6 开篇那三个名字，搬运下限、排队与放大、稳态与余量，是这几条规律在具体阶段上的定量形式，不是另外三条。

**这个顺序不能大幅打乱。** 后面每个阶段都依赖前面的产出：没有 workload 就没有 Baseline，没有 Baseline 就没有门禁，没有容量模型就没有成本讨论。打乱的代价不是返工，是前面那一步没有可用的验收判据。

## 30.3 报告契约

> **报告契约**（report contract）：事先约定好一份性能报告必须包含哪几块，缺任何一块这份报告就不接收。
> 它和“报告模板”的区别在于强制力：模板是建议怎么写，契约是不写就不算交付。它的价值不在格式统一，而在于把那些人们不愿意写的部分变成必填项，比如护栏指标、边界条件、以及“在波动内不可分辨”这类不好看的结论。

无论项目规模大小，最终报告要包含同样的几块。这是全书各章那些报告格式的合并：前六块来自 Part 1 到 Part 5，第 7、8 块把 Part 6 的容量、弹性、门禁和上线评审并了进来，第 9 块是第 14、25 章那套边界纪律。

```text
1. 系统说明
   模型、硬件、框架版本、部署形态、链路结构

2. Workload
   长度分布、到达模式、并发、SLO、随机种子、文件哈希

3. Baseline
   四块字段齐全、重复轮次、波动数据、可识别线、环境指纹

4. 观测能力
   哪些指标可用（含 SLO 达成率与拒绝率）、采集开销、哪些阶段只能写 unavailable

5. 根因分析
   假设列表、证据、排除项、结论、残留不确定性

6. 优化记录
   每轮：预期、唯一改动、主指标、护栏、判定、边界
   叠加时额外记录相互作用

7. 容量、成本与弹性
   卡数推导（哪个约束先满、峰值与下限）、余量构成、
   按有用产出算的单位成本、假设分析、
   扩缩容区间与触发指标、回路滞后与冷启动实测（第 27 章）

8. 门禁与上线
   阈值及其依据（误报率与检出率）、断言清单、基线更新规则、
   回滚预案（触发条件、执行步骤、演练量出的耗时、不可回滚项、
   缓存恢复期）、观察窗口与负责人（第 29 章）

9. 边界与未验证项
   模型、负载、硬件、配置、链路结构五项边界
   明确列出这次没有验证的场景
```

**第九块是整份报告里最能体现水平的一块。** 一份只写成果不写边界的报告，读的人无法判断这些结论在他的场景下还成不成立。

契约里有三处是规律三的落点：第 6 块的护栏和质量底线，第 7 块的有用产出口径，第 9 块的边界。少了它们，报告只能证明机器更忙了，证明不了有用的产出变多了。

## 30.4 自查：怎么知道自己做得对

交出去之前，用这八条自己过一遍。它们对应全书出现频率最高的几类错误。

一、有没有把“不可用”写成 0。第 2 章那条纪律：缺失的阶段写 `unavailable`，它和 `0 ms` 是两回事。

二、有没有把客户端观测当成服务端事实。客户端时长减服务端时长不叫“网络耗时”，分片数不等于 token 数。

三、每个性能数字有没有对应的条件：批量多少、上下文多长、缓存是开是关、冷还是热。没有条件的数字会被拿去用在不该用的地方。

四、有没有“测不出来”这个结论。如果所有实验都得出了明确的收益，反而可疑。第 14 章说过，“在当前实验精度下不可分辨”是一个合法且诚实的结论。

五、护栏指标是不是每轮都记了。主指标改善而护栏恶化，那是交换不是优化。

六、有没有一次改了多项。改动记录里如果有某一轮包含两项改动，那一轮的结论不可用。

七、质量有没有被当成否决项。动了精度就必须有质量数据，且底线在实验前写死。

八、边界写了没有。每个结论都绑定在模型、负载、硬件、配置和链路结构上。

**这八条里任何一条不过关，整份报告的可信度都要打折**，因为读的人会开始怀疑其他部分。

八条分成两组。第三、五、六、七、八这五条在查同一件事，就是 Part 7 开篇那条折中不可消除：条件标注、护栏指标、一次只改一项、质量否决、边界说明，都是在逼着报告写出这次改动换走了什么。报告里出现一项“只有收益、没有代价”的改动时，先按这五条回头查一遍，通常不是白拿，是代价没被测到。剩下的第一、二、四条查的是第 0.6 节那件事：规律只给假设，结论要靠测量。把不可用写成 0、把客户端口径当成服务端事实、不肯写“测不出来”，都是让测量说了它没说过的话。

## 30.5 换一种部署形态

前面的项目用单卡和小模型即可。有条件的可以换成更复杂的形态，但沿用同一份 workload、同一组 SLO 和同一份报告契约。几个可选方向：

```text
多 GPU 部署     张量并行的扩展效率实测          第 27.3 节，附录 C
MoE 模型        显存按总参数，计算按激活参数    附录 D
PD 分离架构     Prefill 与 Decode 独立资源池    第 13.5 节，附录 E
Kernel 级分析   Nsight 与自定义算子             附录 B
```

这四个方向本书正文最多只给到定义和接口，附录 B 到 E 只列出了各自要回答的问题，做法要靠你自己补，做法要靠你自己补。所以 30.6 的扩展验收只检查对照数据在不在、报告契约是不是同一份；PD 分离那一项暂不要求。

**替换形态之后，前面那套方法一条都不变。** 仍然是先建 Baseline、先定位再优化、一次只改一项、记录护栏和边界。具体技术会换代，估算公式里的常数会变，框架的参数名会改，方法比它们活得久。

## 30.6 Demo：项目脚手架与验收

本章 Demo 位于 `code/ch30/project/`，是一套脚手架而非单个脚本。

```text
project/
  workload/        workload 描述模板与生成器
  baseline/        Baseline 采集与对比
  observe/         请求级追踪与指标采集
  experiment/      实验记录与报告生成
  capacity/        容量与成本模型
  gate/            门禁与断言
  report/          报告契约模板与渲染
  verify.py        总验收脚本
```

脚手架本身不产生数据，数据来自前二十九章那些脚本。每个目录下的 README 写清了这一阶段读写哪个文件、复用哪一章的 Demo。验收命令：

```bash
python3 code/ch30/project/verify.py \
  --project-dir ./my-project \
  --level base
```

它检查四件事，任何一件不过关就不算通过：

```text
deliverables      30.1 那五项交付物的存在性
report_contract   30.3 那九块的齐全度，缺一块不算，写成空的也不算；
                  第 7、8 块里来自 Part 6 的那几项（扩缩容触发指标、冷启动、
                  回路滞后、回滚预案、观察窗口、负责人）缺了同样不算
self_check        30.4 那八条，逐条出结论
cross_check       第 29 章那五处接缝，直接复用 code/ch29/release_check.py
```

八条自查分两类，脚本会标明每条属于哪一类。前一类是结构判定，从实验记录和报告的字段里直接读得出来，不过关就是失败：

```text
某轮 guardrails 为空                    → 失败（第五条）
某轮 changed 多于一项                   → 失败（第六条）
changed 含精度改动而 quality 为空        → 失败（第七条）
boundary 少于五项                       → 失败（第八条）
```

这四条都在 30.4 末尾点名的那五条里，查的是同一件事：这次改动换走了什么，所以它们是失败而不是告警。五条里剩下的第三条（数字带不带条件）读不出确定的字段，只能归到下一类。

后一类只能靠关键词和缺失来猜，所以报的是告警，并且在文案里直接写“需人工确认”：

```text
采集能力清单里标为不可用的阶段，报告里出现了对应的 0   → 告警（第一条）
报告里出现“网络耗时”这类客户端口径的说法             → 告警（第二条）
某轮的 conditions 里没有批量或上下文                  → 告警（第三条）
三轮以上实验全是明确结论，没有一轮不可分辨             → 告警（第四条）
```

**把启发式判定伪装成确定性判定，比不判更糟。** 读的人会以为绿灯代表查过了，而它其实只代表没命中那几个关键词。

交叉检查那一段直接用第 29 章那份脚本，包括它那个换算。样例的容量模型写明了显存先满，所以上下文和实际长度对不上时，报出来的不是“对不上”，而是“2 张卡实际要 3 张”；吞吐先满时，它会要求用第 26 章的模型按新长度重算。把接缝换算成卡数，是让它从格式问题变成容量问题的那一步。

仓库里有两份样例项目，`samples/sample-pass` 通过，`samples/sample-incomplete` 是它的“差一点”版本，两份只在四个文件上不同，却一次踩中八条自查的全部八条，外加一处接缝和两项契约缺口（回滚预案没写演练耗时和缓存恢复期）。拿后一份跑一遍，比读这一节更快。

`--level extended` 是扩展验收，在同一份报告契约之上额外要求一项换了部署形态的对照数据：多卡扩展效率、MoE 激活或 Kernel 分析，PD 分离给了也计入但暂不要求。这是 30.5 那句话的机器版：形态可以换，方法不换。

用在自己的项目上时，验收的终点是三件事：按七个阶段走完一遍，用 `verify.py` 通过基本验收，并且让门禁真的拦住一次人为制造的回归。

## 30.7 常见的项目失败形态

不是案例，是四种反复出现的走偏方式。

一、从最熟悉的地方开始。第 25 章那个案例：直接优化推理，两周把单次调用的计算从 480 ms 降到 260 ms，端到端只改善约 7%。按第 10 章的 Amdahl 定律，GPU 计算只占总时长的 16%，加速 1.85 倍最多省 16% × (1 − 1/1.85) ≈ 7%，账算得一分不差；占 31% 的排队一点没动，因为它要靠满载吞吐上去、负载率下来才会塌。阶段顺序存在的意义就是对抗这个本能：先做阶段三的分解，再决定动哪一层。

二、跳过 Baseline 直接优化。后果不是“少了一份文档”，而是所有后续结论都无法验证。改完之后快了，但快了多少、是不是波动、换个负载还成不成立，全都答不上来。

三、只保留成功的实验。失败的实验和“测不出来”的实验同样有价值，它们划定了边界。一份全是成功的报告，读的人会怀疑失败的那些去哪了。

四、把报告写成成果展示。报告的读者是要复核和复用的人，不是要被说服的人。**边界、未验证项、残留不确定性这三样写清楚，报告才有长期价值。**

## 本章总结

回到开头的三个问题。

**要交付什么？** 五项：可运行、可观测、可解释、可优化、有门禁。规模不重要，完整性重要，单卡小模型完全可以，重要的是每一环真实存在。其中可解释最容易被低估，而前面二十九章的错误绝大多数都源于某个数字的含义没说清。报告要按九块的契约组织，最后一块（边界与未验证项）最能体现水平；护栏、有用产出口径和边界这三处是规律三在报告里的落点。

**按什么顺序做？** 七个阶段，各自对应前面的若干章：跑起来并说清楚、把负载和基准立住、让系统可观测、Prefill 与上下文、Decode 与显存、服务与链路、容量门禁与评审。顺序不能大幅打乱，因为后面每个阶段都依赖前面的产出；各阶段的验收判据来自第 0 章那三条规律。最常见的走偏是从最熟悉的地方开始动手，阶段顺序存在的意义就是对抗这个本能。

**怎么判断站得住？** 八条自查：没把不可用写成 0、没把客户端观测当服务端事实、每个数字都带条件、允许“测不出来”这个结论、每轮都记了护栏、一次只改一项、质量是否决项、边界写清楚了。其中五条查的是改动换走了什么，三条查的是测量有没有说它没说过的话。任何一条不过关，整份报告的可信度都要打折。

全书到此结束。回到第 0 章那句话：性能是快、省、好三者之间的一个位置，优化就是在证据支持下移动它。三条规律说明这个位置为什么难挪：写比读贵，所以输出那一侧有一条搬运下限；批量摊薄搬运而满载拉长等待，所以省和快互相拉扯；只有有用的产出才算数，所以挪动之后要数的是分母里有用的那部分。第 0.6 节那条方法说明怎么证明它挪动了：规律只给假设，结论要靠测量。具体的技术会换代，公式里的常数会变，参数名会改，留下来的是这几条，以及从它们引出的四条纪律：不可复现的数据比没有更糟，证据不足就写不足，测不出来也是结论，任何收益都绑定在它成立的边界上。

### 本章 Checklist

- [ ] 五项交付物齐全，每一项都能演示。
- [ ] 报告包含九块内容，没有留空。
- [ ] 七个阶段都有对应的产出物，且顺序没有大幅打乱。
- [ ] 八条自查逐条过关。
- [ ] 报告里保留了失败的和“测不出来”的实验。
- [ ] 每个性能数字旁边都有条件说明。

## 课后练习

1. 按七个阶段列出你的项目计划，标出每个阶段的产出物和验收判据。
2. 完成阶段一到三，让一位同事按你的文档重跑，记录他卡在哪里。
3. 在阶段四或五中，刻意保留一次“测不出来”的实验，写清它为什么不可分辨。
4. 用 30.4 那八条自查你的报告，记录每一条的结果。
5. 请一位没参与的人复核你的报告，记录他提出的每一个“这个数字是在什么条件下得到的”。
6. 人为制造一次性能回归，验证门禁能否拦住。
7. 写出你这套结论的五项边界，以及每项变化时需要重新验证什么。
8. 列出这次项目中没有验证的场景，按风险高低排序。
