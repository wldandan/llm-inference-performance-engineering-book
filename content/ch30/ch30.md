# 第 30 章 端到端性能工程项目：把二十九章用在一件事上

## 学习目标

读完这一章，你应该能回答三个问题：

1. 一个完整的性能工程项目要交付什么，怎么算完成？
2. 从零开始做，二十九章的内容该按什么顺序用？
3. 怎么判断自己做出来的东西是真的站得住，而不是自己觉得好？

跟着做完，你会得到本课程的最终交付物：一套可运行、可观测、可解释、可优化、有门禁的 LLM 服务，以及一份能交给别人复核的完整报告。

## 30.1 这个项目要做什么

前二十九章是分开学的。这一章把它们用在同一件事上。

**项目要求：** 交付一个 RAG 或 Agent 服务，满足一组事先定义的 SLO，并提供完整的证据链。

**规模不重要，完整性重要。** 单卡、小模型、几百条文档的知识库完全可以，重要的是这条链上每一环都真实存在，而不是某几环用假数据糊过去。

**五项交付物：**

```text
1. 可运行   服务能起来，能处理请求，有明确的启动和验收步骤
2. 可观测   请求级追踪、关键指标、能从聚合下钻到单条
3. 可解释   每个性能数字都能说清它测的是什么、在什么条件下得到的
4. 可优化   至少完成一轮完整的"定位 → 改动 → 验证"闭环
5. 有门禁   自动 Benchmark 加断言，能拦住性能回归
```

**第三项是最容易被低估的。** 前面二十九章反复出现的那些错误，绝大多数的根源都是某个数字的含义没说清：分片数当成 token 数、客户端时长差当成网络耗时、满载成本当成实际成本、Canary 的 TTFT 当成全量表现。

## 30.2 七个阶段

推荐的推进顺序，每个阶段对应前面的若干章。

**阶段一：跑起来并说清楚（Ch1–Ch5）**

```text
产出   一个能接请求的服务
       一份请求生命周期的时间线
       一张组件职责图
       统一的指标口径说明
```

**验收判据：能说出每个阶段的时间戳来自哪里，以及哪些阶段必须写 `unavailable`。**

**阶段二：把负载和基准立住（Ch6–Ch7）**

```text
产出   一份含长度分布、到达模式、并发和 SLO 的 workload 描述
       一份可复现的 Baseline，含环境指纹
       Baseline 的波动数据
```

**验收判据：同事拿着这两份文件能重跑出同一批请求和相近的数字。**

**阶段三：让系统可观测（Ch8–Ch10）**

```text
产出   Request ID 贯通客户端、服务端、下游调用
       能从一条告警下钻到具体的慢请求
       一份走完假设与排除流程的根因报告
```

**验收判据：随便指一条慢请求，能说出它慢在哪一段。**

**阶段四：Prefill 与上下文（Ch11–Ch14）**

```text
产出   Prefill 的量级估算与实测对照
       上下文成本账：TTFT、token、并发上限三笔
       至少一轮含预期、护栏和边界的优化实验
```

**验收判据：实验报告里有“在波动内不可分辨”这类诚实结论的空间。**

**阶段五：Decode 与显存（Ch15–Ch19）**

```text
产出   TPOT 下限估算与实测比值
       一张容量表：从模型参数推到单卡并发
       Goodput 曲线与峰值批量
       五维记分卡的优化报告
```

**验收判据：每个收益数字都标注了对应的批量。**

**阶段六：服务与链路（Ch20–Ch25）**

```text
产出   调度参数说明与调整顺序
       流量治理五项配置与一次过载演练
       全链路时间分解表（压测状态下采集）
       端到端优化报告与防回退断言
```

**验收判据：过载演练的 goodput 曲线在超容量后保持平稳。**

**阶段七：容量、门禁与评审（Ch26–Ch29）**

```text
产出   容量与成本模型，能做假设分析
       扩缩容配置与边界说明
       可运行的性能门禁
       上线评审材料与回滚预案
```

**验收判据：门禁能真的拦住一次人为制造的回归。**

**这个顺序不能大幅打乱。** 后面每个阶段都依赖前面的产出：没有 workload 就没有 Baseline，没有 Baseline 就没有门禁，没有容量模型就没有成本讨论。

## 30.3 报告契约

无论项目规模大小，最终报告要包含同样的几块。这是全书所有报告格式的合并。

```text
1. 系统说明
   模型、硬件、框架版本、部署形态、链路结构

2. Workload
   长度分布、到达模式、并发、SLO、随机种子、文件哈希

3. Baseline
   四块字段齐全、重复轮次、波动数据、环境指纹

4. 观测能力
   哪些指标可用、采集开销、哪些阶段只能写 unavailable

5. 根因分析
   假设列表、证据、排除项、结论、残留不确定性

6. 优化记录
   每轮：预期、唯一改动、主指标、护栏、判定、边界
   叠加时额外记录相互作用

7. 容量与成本
   卡数推导、余量构成、实际单位成本、假设分析

8. 门禁
   阈值及其依据、断言清单、基线更新规则

9. 边界与未验证项
   模型、负载、硬件、配置、链路结构五项边界
   明确列出这次没有验证的场景
```

**第九块是整份报告里最能体现水平的一块。** 一份只写成果不写边界的报告，读的人无法判断这些结论在他的场景下还成不成立。

## 30.4 自查：怎么知道自己做得对

交出去之前，用这几条自己过一遍。它们对应全书出现频率最高的几类错误。

**一、有没有把“不可用”写成 0。**

第 1 章那条纪律。缺失的阶段写 `unavailable`，它和 `0 ms` 是两回事。

**二、有没有把客户端观测当成服务端事实。**

客户端时长减服务端时长不叫“网络耗时”，分片数不等于 token 数。

**三、每个性能数字有没有对应的条件。**

批量多少、上下文多长、缓存是开是关、冷还是热。**没有条件的数字会被拿去用在不该用的地方。**

**四、有没有“测不出来”这个结论。**

如果所有实验都得出了明确的收益，反而可疑。第 14 章说过，“在当前实验精度下不可分辨”是一个合法且诚实的结论。

**五、护栏指标是不是每轮都记了。**

主指标改善而护栏恶化，那是交换不是优化。

**六、有没有一次改了多项。**

改动记录里如果有某一轮包含两项改动，那一轮的结论不可用。

**七、质量有没有被当成否决项。**

动了精度就必须有质量数据，且底线在实验前写死。

**八、边界写了没有。**

每个结论都绑定在模型、负载、硬件、配置和链路结构上。

**这八条里任何一条不过关，整份报告的可信度都要打折**，因为读的人会开始怀疑其他部分。

## 30.5 Advanced 路线

Core 项目用单卡和小模型即可。有条件的可以替换成更复杂的形态，但**沿用同一份 workload、同一组 SLO 和同一份报告契约**。

几个可选方向，实现细节在附录：

```text
多 GPU 部署       张量并行的扩展效率实测            附录 C
MoE 模型          按激活参数而非总参数算容量         附录 D
PD 分离架构       Prefill 与 Decode 独立资源池       附录 E
Kernel 级分析     Nsight 与自定义算子                附录 B
```

**替换形态之后，前面那套方法一条都不变。** 仍然是先建 Baseline、先定位再优化、一次只改一项、记录护栏和边界。**这正是这门课想传达的东西：方法比具体技术活得久。**

具体技术会换代，估算公式里的常数会变，框架的参数名会改。但“不可复现的数据比没有更糟”“证据不足就写不足”“测不出来也是结论”这些不会。

## 30.6 Demo：项目脚手架与验收

本章 Demo 位于 `code/ch30/project/`，是一套脚手架而非单个脚本。

```text
project/
  workload/        workload 描述模板与生成器
  baseline/        Baseline 采集与对比
  observe/         请求级追踪与指标采集
  experiment/      实验记录与报告生成
  capacity/        容量与成本模型
  gate/            门禁与断言
  report/          报告契约模板与渲染
  verify.py        总验收脚本
```

验收：

```bash
python3 code/ch30/project/verify.py \
  --project-dir ./my-project \
  --level core
```

它检查五项交付物是否齐全，并跑 30.4 那八条自查：

```text
deliverables    五项交付物的存在性与完整性
report_contract 报告九块内容的齐全度
self_check      八条自查逐条结果
cross_check     Ch29 那五项交叉一致性
missing         缺失项清单
verdict         pass / incomplete
```

**`self_check` 里有几条是能自动判的：**

```text
报告中出现 "0 ms" 而对应阶段在采集能力清单里标为不可用  → 告警
性能数字所在的段落中没有出现批量或上下文的说明          → 告警
某轮实验的 changed 字段包含多于一项                     → 失败
changed 含精度改动而 quality 为空                       → 失败
boundary 段落为空或少于五项                             → 失败
```

**`--level advanced` 会额外要求多卡扩展效率或 PD 分离的对照数据**，但报告契约完全相同。

**本项目的完整验收尚未在真机上执行。** GX10 恢复后，课程的最终交付是：按七个阶段走完一遍，用 `verify.py` 通过 Core 级验收。

## 30.7 常见的项目失败形态

不是案例，是四种反复出现的走偏方式。

**一、从最熟悉的地方开始。**

第 25 章那个案例：直接优化推理，两周把 GPU 计算降一半，端到端改善 8%。**阶段顺序存在的意义就是对抗这个本能。**

**二、跳过 Baseline 直接优化。**

后果不是“少了一份文档”，而是所有后续结论都无法验证。改完之后快了，但快了多少、是不是波动、换个负载还成不成立，全都答不上来。

**三、只保留成功的实验。**

失败的实验和“测不出来”的实验同样有价值，它们划定了边界。一份全是成功的报告，读的人会怀疑失败的那些去哪了。

**四、把报告写成成果展示。**

报告的读者是要复核和复用的人，不是要被说服的人。**边界、未验证项、残留不确定性这三样写清楚，报告才有长期价值。**

## 本章总结

回到开头的三个问题。

**要交付什么？** 五项：可运行、可观测、可解释、可优化、有门禁。规模不重要，完整性重要，单卡小模型完全可以，重要的是每一环真实存在。其中可解释最容易被低估，而前面二十九章的错误绝大多数都源于某个数字的含义没说清。报告要按九块的契约组织，最后一块（边界与未验证项）最能体现水平。

**按什么顺序做？** 七个阶段，各自对应前面的若干章：跑起来并说清楚、把负载和基准立住、让系统可观测、Prefill 与上下文、Decode 与显存、服务与链路、容量门禁与评审。顺序不能大幅打乱，因为后面每个阶段都依赖前面的产出。最常见的走偏是从最熟悉的地方开始动手，阶段顺序存在的意义就是对抗这个本能。

**怎么判断站得住？** 八条自查：没把不可用写成 0、没把客户端观测当服务端事实、每个数字都带条件、允许“测不出来”这个结论、每轮都记了护栏、一次只改一项、质量是否决项、边界写清楚了。任何一条不过关，整份报告的可信度都要打折。

全书到此结束。具体的技术会换代，公式里的常数会变，参数名会改。留下来的是几条更硬的东西：不可复现的数据比没有更糟，证据不足就写不足，测不出来也是结论，以及任何收益都绑定在它成立的边界上。

## 课后练习

1. 按七个阶段列出你的项目计划，标出每个阶段的产出物和验收判据。
2. 完成阶段一到三，让一位同事按你的文档重跑，记录他卡在哪里。
3. 在阶段四或五中，刻意保留一次“测不出来”的实验，写清它为什么不可分辨。
4. 用 30.4 那八条自查你的报告，记录每一条的结果。
5. 请一位没参与的人复核你的报告，记录他提出的每一个“这个数字是在什么条件下得到的”。
6. 人为制造一次性能回归，验证门禁能否拦住。
7. 写出你这套结论的五项边界，以及每项变化时需要重新验证什么。
8. 列出这次项目中没有验证的场景，按风险高低排序。
